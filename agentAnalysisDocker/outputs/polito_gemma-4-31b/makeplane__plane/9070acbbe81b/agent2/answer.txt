The provided changes fix an Insecure Direct Object Reference (IDOR) vulnerability in two different API endpoints: `ProjectAssetEndpoint.patch` and `IssueAttachmentEndpoint.delete`.

1.  **`ProjectAssetEndpoint.patch`**: In the `before` state, the endpoint retrieved a `FileAsset` object using only the `pk` (primary key) provided in the URL (`FileAsset.objects.get(id=pk)`). This allowed any authenticated user with the required role (`ADMIN`, `MEMBER`, or `GUEST`) to modify any asset in the system, regardless of which workspace or project it belonged to, simply by guessing or providing a valid `pk`. The `after` state fixes this by adding filters for `workspace__slug=slug` and `project_id=project_id`, ensuring the asset belongs to the specified workspace and project.

2.  **`IssueAttachmentEndpoint.delete`**: Similarly, the `delete` method retrieved a `FileAsset` using only the `pk` (`FileAsset.objects.get(pk=pk)`). This allowed an attacker with `ADMIN` permissions in *their own* workspace to delete any `FileAsset` in the entire database by providing its `pk`. The `after` state fixes this by filtering the query with `workspace__slug=slug`, `project_id=project_id`, and `issue_id=issue_id`, restricting the deletion to assets that actually belong to the target issue, project, and workspace.

Both of these issues are classic examples of IDOR, where an application provides direct access to objects based on user-supplied input without sufficient authorization checks to ensure the user has permission to access that specific object.
