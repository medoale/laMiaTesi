The commit changes the implementation of the `cache` in `DefaultHtmlErrorResponseBodyProvider` from a `ConcurrentHashMap` to a `ConcurrentLinkedHashMap` with a maximum size of 100.

In the `before.txt` version, `cache` is an unbounded `ConcurrentHashMap`:
```java
private final Map<HtmlErrorPage, String> cache = new ConcurrentHashMap<>();
```

The `body` method uses `computeIfAbsent` to populate this cache:
```java
public String body(@NonNull ErrorContext errorContext, @NonNull HttpResponse<?> response) {
    HtmlErrorPage key = error(errorContext, response);
    return cache.computeIfAbsent(key, this::html);
}
```

The `HtmlErrorPage` key depends on various inputs, including the locale, HTTP status code, status reason, and error messages retrieved from `ErrorContext`. If an attacker can trigger an error response with a large number of unique error messages or reasons (e.g., by including unique values in a request that results in an error), they can cause the `cache` to grow indefinitely. This is a classic unbounded cache vulnerability, which can lead to memory exhaustion and a Denial of Service (DoS).

The commit fixes this by introducing a maximum cache size (`MAX_CACHE_SIZE = 100`) using `ConcurrentLinkedHashMap`, which implements an LRU (Least Recently Used) eviction policy. This ensures that the memory used by the cache remains bounded regardless of the number of unique error pages generated.

The accompanying test file `DefaultHtmlErrorResponseBodyProviderCacheMaxSizeTest` verifies this fix by attempting to populate the cache with more than 100 unique entries and asserting that the cache size does not exceed the limit.
