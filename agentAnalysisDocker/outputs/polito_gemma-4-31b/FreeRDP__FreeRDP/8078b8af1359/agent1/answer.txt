The commit modifies multiple files (`file_01` through `file_05`) to ensure that security handles (credentials and security contexts) are invalidated immediately after their internal pointers are retrieved, typically within "Free" or "Delete" functions.

In the `before` state, the code would retrieve the internal pointer using `sspi_SecureHandleGetLowerPointer` and then perform cleanup operations. However, the handle itself remained "valid" (from the perspective of the handle management system) until the end of the function, or in some cases, the `sspi_SecureHandleInvalidate` call was placed at the end of the function or missing from certain error paths.

By moving `sspi_SecureHandleInvalidate(phCredential)` or `sspi_SecureHandleInvalidate(phContext)` to immediately follow the pointer retrieval, the commit prevents a race condition or a "use-after-free" scenario where another thread might attempt to use the same handle while it is being freed. More importantly, it ensures that the handle is marked as invalid as early as possible, preventing any subsequent calls using that handle from succeeding while the cleanup is in progress. This pattern is a classic fix for Use-After-Free (UAF) or Double Free vulnerabilities in handle-based APIs.

Specifically, if a handle is not invalidated before the internal object it points to is destroyed, there is a window where the handle is still considered valid but points to memory that is being freed or has already been freed.
