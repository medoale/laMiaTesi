The change in `RequestInputFilter.java` addresses a security issue related to "Ferret expressions."

In the `before.txt` version, there was an attempt to block "Ferret expressions" at lines 368-373:
```java
368: 					    String expression = lasRequest.getProperty("ferret", "expression");
369:                         if (!expression.isEmpty()) {
370:                             LASAction.logerror(request, "Ferret expressions are no longer allowed.", "");
371:                             response.sendError(404, "Ferret expressions are no longer allowed.");
372:                             return;
373:                         }
```
However, this code was placed *before* the `lasRequest` object was actually instantiated and populated. Looking at the `before.txt` file, `lasRequest` is instantiated at line 381:
```java
381: 			LASUIRequest lasRequest = new LASUIRequest();
382: 			try {
383: 				JDOMUtils.XML2JDOM(requestXML, lasRequest);
```
Because `lasRequest` was used at line 368 before it was declared/initialized (which, in a real Java environment, would actually cause a compilation error unless `lasRequest` was a class member, which it is not), the original check was completely ineffective. Even if it had compiled (e.g., if it was an existing object), it was checking the object before `JDOMUtils.XML2JDOM(requestXML, lasRequest)` had parsed the user-supplied XML into it.

The commit moves the check to lines 380-385 in `after.txt`, *after* the XML has been parsed into the `lasRequest` object:
```java
377: 				JDOMUtils.XML2JDOM(requestXML, lasRequest);
378: 				// Set the lasRequest object in the HttpServletRequest so the product server does not have to rebuild it.
379: 				request.setAttribute("las_request", lasRequest);
380: 					String expression = lasRequest.getProperty("ferret", "expression");
381:                     if (!expression.isEmpty()) {
382:                         LASAction.logerror(request, "Ferret expressions are no longer allowed.", "");
383:                         response.sendError(404, "Ferret expressions are no longer allowed.");
384:                         return;
385:                     }
```

Allowing arbitrary expressions (like "Ferret expressions") to be processed often leads to Remote Code Execution (RCE) or Expression Language (EL) injection vulnerabilities. By correctly implementing the block on these expressions, the commit fixes a vulnerability that allowed potentially malicious expressions to reach the backend.
