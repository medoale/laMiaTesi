The commit addresses a security vulnerability related to Server-Side Request Forgery (SSRF).

Specifically, in `file_03` (`RecursiveUrlLoader`), the previous implementation of `fetchWithTimeout` relied on the default behavior of the `fetch` API, which automatically follows redirects. While the initial URL was validated using `validateSafeUrl`, any subsequent redirects provided by the server were followed without validation. This allowed an attacker to bypass SSRF protections by providing a safe-looking URL that redirected to a restricted internal resource (e.g., `localhost` or cloud metadata services).

The fix introduces:
1.  Manual redirect handling by setting `redirect: "manual"` in the `fetch` options.
2.  A loop that explicitly checks for redirect status codes (`301`, `302`, etc.).
3.  Call to `validateSafeUrl(currentUrl, ...)` for every step of the redirect chain, ensuring that the destination of each redirect is also safe.
4.  A `MAX_REDIRECTS` limit to prevent infinite redirect loops (denial of service).

The tests added in `file_02` specifically verify that redirects to private IPs (`127.0.0.1`), cloud metadata IPs (`169.254.169.254`), and private network ranges (`192.168.1.1`) are now blocked, confirming the fix for the SSRF bypass.
