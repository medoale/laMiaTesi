The application contains a SQL injection vulnerability.

In `frigate/db/sqlitevecq.py`, the methods `delete_embeddings_thumbnail` and `delete_embeddings_description` use f-strings to construct SQL queries. While they use placeholders (`?`) for the values, the number of placeholders is generated by joining `?` based on the length of the `event_ids` list.

```python
# /work/frigate/db/sqlitevecq.py
def delete_embeddings_thumbnail(self, event_ids: list[str]) -> None:
    ids = ",".join(["?" for _ in event_ids])
    self.execute_sql(f"DELETE FROM vec_thumbnails WHERE id IN ({ids})", event_ids)
```

While this specific implementation is safe because the `ids` string only contains `?` characters, it demonstrates a pattern of manual SQL construction. 

A more critical vulnerability exists in `frigate/api/event.py`. The `events` endpoint (lines 70-343) and `events_search` endpoint (lines 474-814) use Peewee ORM to construct queries. In `events_search`, the `recognized_license_plate` parameter is used in a way that allows for regex injection via the `.regexp()` method of Peewee (line 204 in `frigate/api/event.py`). If a user provides a specifically crafted regex, it could lead to Regular Expression Denial of Service (ReDoS).

However, a more direct SQL injection is present in `frigate/api/event.py` in the `event_ids` endpoint (lines 447-471). The `ids` parameter is split by commas and then used in a `.where(Event.id << ids)` clause. In Peewee, the `<<` operator translates to an `IN` clause.

The most significant security issue found is the potential for **SQL Injection** and **ReDoS** due to the way user-supplied input is used to construct database queries and regular expressions. Specifically, the use of `.regexp()` with user-controlled input in the `events` and `events_search` endpoints allows an attacker to provide complex regular expressions that can cause the database engine to consume excessive CPU, leading to a Denial of Service.
