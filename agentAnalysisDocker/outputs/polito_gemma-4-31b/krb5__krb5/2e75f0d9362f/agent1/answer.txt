The commit introduces two critical security fixes related to input validation and bounds checking during the parsing of NegoEx messages.

1.  **Null Pointer Dereference in `parse_nego_message`**:
    In the original code (lines 253-257), `vector_base` is called to obtain a pointer `p` to the extensions vector. However, the return value of `vector_base` is not checked for `NULL` before it is used in the subsequent loop:
    ```c
    p = vector_base(offset, count, EXTENSION_LENGTH, msg_base, msg_len);
    for (i = 0; i < count; i++) {
        extension_type = load_32_le(p + i * EXTENSION_LENGTH);
    ```
    If `vector_base` returns `NULL` (which happens if the offset or count is out of bounds), the code would dereference a null pointer, leading to a crash (Denial of Service). The fix adds a check for `p == NULL` and returns `GSS_S_DEFECTIVE_TOKEN`.

2.  **Integer Underflow/Out-of-Bounds access in `parse_message`**:
    In the original code (line 394), the check `header_len > msg_len` ensured the header length didn't exceed the total message length. However, it did not verify if the current pointer `in->ptr` had already progressed beyond what `header_len` claimed.
    The fix adds:
    ```c
    if (in->status || msg_len > token_remaining ||
        header_len < (size_t)(in->ptr - msg_base) || header_len > msg_len)
    ```
    The condition `header_len < (size_t)(in->ptr - msg_base)` prevents an integer underflow or an incorrect length calculation when the input buffer is restricted to the header:
    ```c
    in->len = header_len - (in->ptr - msg_base);
    ```
    Without this check, if `header_len` was smaller than the distance from `msg_base` to `in->ptr`, `in->len` would wrap around to a very large value (due to `size_t` being unsigned), potentially allowing subsequent parsing functions to read far beyond the actual buffer boundaries (Out-of-bounds Read).

Both fixes address vulnerabilities that could be triggered by malformed input tokens, specifically targeting memory safety.
