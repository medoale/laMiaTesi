The analysis of the provided changes reveals that the commit fixes multiple path traversal vulnerabilities.

The vulnerability was present in several API endpoints and internal functions that handled DAG file names. Specifically, the `FileName` field in API requests (used in `DeleteDAG`, `GetDAGSpec`, `UpdateDAGSpec`, `ExecuteDAG`, `GetDAGDetails`, etc.) was passed directly to the `dagStore` without sufficient validation. An attacker could provide a maliciously crafted `FileName` containing path traversal sequences (e.g., `..%2F..%2Ftmp%2Fsecret`) to access, modify, or delete files outside the intended DAGs directory.

The fix introduces several security measures:
1.  **Centralized Validation**: A new `ValidateDAGName` function in `internal/core/validator.go` was implemented. This function ensures that the DAG name:
    *   Is not `.` or `..`.
    *   Does not exceed a maximum length (`DAGNameMaxLen = 40`).
    *   Matches a strict regular expression (`^[a-zA-Z0-9_.-]+$`), which effectively forbids path traversal characters like `/` and `\`.
2.  **API Middleware**: A new middleware `validateDAGFileNameMiddleware` was added to the API server. This middleware uses reflection to find any `FileName` field in the request object and validates it using `ValidateDAGName` before the request reaches the handler.
3.  **Internal Topic Validation**: The `canonicalizeTopicIdentifier` function was updated to validate identifiers for `TopicTypeDAG` and `TopicTypeDAGHistory`, preventing traversal via SSE topics.
4.  **Regression Tests**: New tests were added (`TestDAGFileNameRejectsEncodedTraversal` and `TestParseTopicRejectsDAGTraversalIdentifiers`) to verify that encoded path traversal attempts are now rejected with a `400 Bad Request` status.

This is a classic case of Improper Limitation of a Pathname to a Restricted Directory, leading to Path Traversal.
