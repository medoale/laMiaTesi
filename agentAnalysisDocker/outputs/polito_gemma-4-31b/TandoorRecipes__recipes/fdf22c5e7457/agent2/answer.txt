The analysis of the provided changes shows that the commit fixes a **Server-Side Request Forgery (SSRF)** vulnerability.

### Vulnerability Analysis:
In the version before the commit, the application used `requests.get()` and `requests.post()` to fetch resources from URLs provided by users (e.g., during recipe import, image fetching, or integration with external services). Although there was a `validate_import_url()` function, it had several deficiencies:
1. **DNS Rebinding / Time-of-Check Time-of-Use (TOCTOU):** The validation happened before the actual request. An attacker could use a DNS record with a very low TTL that initially points to a safe IP (passing validation) and then resolves to a local/private IP when `requests.get()` is called.
2. **Redirect Bypasses:** The `requests` library follows redirects by default. An attacker could provide a URL that points to a safe external server, which then redirects the request to an internal resource (e.g., `http://127.0.0.1/admin`), bypassing the initial validation entirely.
3. **IP Encoding Bypasses:** The original validator did not account for alternative IP representations (DWORD, Hex, Octal), allowing attackers to bypass filters by encoding local IP addresses.

### Fix Analysis:
The commit introduces several critical security improvements:
1. **`safe_request` Wrapper:** It replaces direct `requests` calls with a `safe_request` function. This wrapper handles redirects manually (`allow_redirects=False`), validating every single URL in the redirect chain using `validate_import_url()` before proceeding.
2. **Improved IP Validation:** `validate_import_url()` now explicitly detects and resolves encoded IP formats (Hex, Octal, Decimal/DWORD) to ensure that bypassed representations of local/private IPs are caught.
3. **URL Normalization:** It adds normalization to prevent bypasses using control characters or unusual encoding in the URL.
4. **Comprehensive Integration:** This `safe_request` wrapper is applied across the entire codebase where user-supplied URLs are used.

These changes directly mitigate the risks of SSRF by ensuring that no request (initial or redirected) ever reaches a restricted internal network address, regardless of the encoding or redirect chain used.
