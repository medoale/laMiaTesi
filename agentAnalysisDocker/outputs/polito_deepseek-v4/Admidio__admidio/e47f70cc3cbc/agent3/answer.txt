## Vulnerability 1: SSRF / Arbitrary File Read in `fetch_metadata.php` (CWE-918)

**File**: `/work/modules/sso/fetch_metadata.php` (lines 15-34)

**Severity**: High (requires admin privileges, but impacts: internal network scanning, local file disclosure)

**Summary**: The `fetch_metadata.php` endpoint accepts a URL via `$_GET['url']`, validates it only with `FILTER_VALIDATE_URL` (which checks format, not scheme), then fetches it with `file_get_contents()` and echoes the raw response back to the browser.

```php
$url = filter_var($_GET['url'], FILTER_VALIDATE_URL);
// ...
$metadata = file_get_contents($url);
// ...
echo $metadata;
```

Since `FILTER_VALIDATE_URL` accepts any scheme, an admin can use `file:///etc/passwd` to read local files, `php://filter/convert.base64-encode/resource=...` to read PHP source code, or `http://internal-service/` to probe the internal network. The `file://` wrapper works regardless of PHP's `allow_url_fopen` setting.

**Suggested fix**: Restrict the URL scheme to `https://` only, validate the host against an allowlist, or use `libxml_set_external_entity_loader()` / cURL with safe options instead of `file_get_contents()`.

---

## Vulnerability 2: SQL Injection via String Concatenation in `User::delete()` (CWE-89)

**File**: `/work/src/Users/Entity/User.php` (lines 578-774)

**Severity**: Medium (secondary injection — requires prior DB compromise)

**Summary**: The `delete()` method builds over 30 SQL queries by concatenating `$usrId` directly into query strings:

```php
$usrId = $this->getValue('usr_id');
// ...
$sqlQueries[] = 'UPDATE ' . TBL_ANNOUNCEMENTS . '
                    SET ann_usr_id_create = NULL
                  WHERE ann_usr_id_create = ' . $usrId;
// ... 30+ more such queries
foreach ($sqlQueries as $sqlQuery) {
    $this->db->query($sqlQuery); // TODO add more params
}
```

`$usrId` originates from the database record (`$this->getValue('usr_id')`), not direct user input, making this a **secondary injection** vector. If another vulnerability allows an attacker to control what `usr_id` value is stored in the database, this becomes directly exploitable. The TODO comment (`// TODO add more params`) confirms the developer's awareness.

**Suggested fix**: Use `$this->db->queryPrepared()` with parameterized queries for all SQL statements.

---

## Vulnerability 3: SAML ACS URL Not Validated Against Registered Client URL (CWE-287, CWE-601)

**File**: `/work/src/SSO/Service/SAMLService.php` (lines 438-439, 456, 465)

**Severity**: Medium (compromised/malicious registered SP can redirect SAML response)

**Summary**: In `handleSSORequest()`, the ACS (Assertion Consumer Service) URL is taken directly from the incoming SAML `AuthnRequest` without any validation against the registered client's configured ACS URL:

```php
$clientACS = $request->getAssertionConsumerServiceURL(); // line 439 — from request, no validation
// ...
$response->setDestination($clientACS);                   // line 456
// ...
$subjectConfirmationData->setRecipient($clientACS);      // line 465
```

A registered SP can send an `AuthnRequest` with a different ACS URL than what is stored in its configuration. The IdP will then redirect the SAML assertion (containing authentication tokens and user attributes) to that arbitrary URL. This is a form of **open redirect** via SAML response injection.

**Suggested fix**: Validate `$clientACS` against `$client->getValue('smc_acs_url')` before using it in the response. If they do not match, the request should be rejected.

## Vulnerability 4: Insecure Smarty 5 Configuration (CWE-94)

**File**: `/work/src/UI/Presenter/PagePresenter.php` (lines 396-421) and `/work/system/classes/HtmlPage.php` (lines 381-404)

**Severity**: Medium (potential template injection if user data reaches template variables)

**Summary**: Both `createSmartyObject()` methods create a Smarty 5 engine without enabling any security settings. Neither `setSecuritySettings()` nor `setTrustedTemplateDir()` are called:

```php
$smartyObject = new Smarty();
$smartyObject->setTemplateDir(THEME_PATH . '/templates/');
$smartyObject->setCacheDir(...);
$smartyObject->setCompileDir(...);
// NO security configuration
```

In Smarty 5, `{php}` tags were removed, reducing the direct code-execution risk. However, without security settings enabled, `{fetch}`, `{include}`, and `{extends}` directives could be exploited if user-controlled data enters template variables. If an attacker can control any string assigned to Smarty's `assign()` method (e.g., from user profile data, preferences, or stored XSS), they could potentially achieve server-side template injection.

**Suggested fix**: Enable Smarty security settings, configure trusted template directories, and sanitize any user-controlled data passed to template variables.

## Issues Investigated and Confirmed Not Vulnerable

- **`adm_my_files/config.php`**: Protected by `.htaccess` with `Require all denied` (Apache 2.4+) and `Deny from All` (older).
- **Path traversal in `show_image.php`**: Prevented by `strIsValidFileName()` (`basename($filename) !== $filename` check) and the 'file' datatype regex which blocks `/` and `\`.
- **File uploads**: Extension allowlist (`FileSystemUtils::allowedFileExtension()`) restricts to safe image/document/media types. Additional extension blocklist in `strIsValidFileName()` blocks PHP, HTML, JS, etc.
- **SQL injection in application queries**: All general CRUD operations use `queryPrepared()` with PDO parameterized queries.
- **XSS in CKEditor fields**: HTMLPurifier is applied to rich-text fields (`ann_description`, `dat_description`, etc.) with a restricted HTML 4.01 configuration.
- **CSRF protection**: Token-based validation via `validateCsrfToken()` using `getRandomString(30)` (cryptographically secure).
- **Password hashing**: Uses `password_hash()` with `PASSWORD_DEFAULT` (bcrypt). Client secrets in OIDC are also hashed with `password_hash()`.
- **No `unserialize()` calls**: The codebase does not use `unserialize()` on untrusted data.
- **No direct shell command execution**: `exec()` in third-party UploadHandler uses `escapeshellarg()`. `curl_exec()` in SAML back-channel logout uses database-configured URLs (admin-controlled).
- **OIDC redirect URI validation**: `ClientRepository::isRedirectUriAllowed()` does exact-match lookup against the database. While it only supports one redirect URI per client, it prevents unauthorized redirects.

## Verdict

The most impactful vulnerability is the **SSRF / arbitrary file read in `fetch_metadata.php`** (admin-only but effectively allows reading local files and probing internal network). The **SAML ACS URL validation bypass** (allowing a registered SP to redirect the SAML response to an arbitrary URL) and the **SQL injection pattern in `User::delete()`** (secondary injection) are also genuine vulnerabilities. The **insecure Smarty configuration** is a latent risk that becomes exploitable if any template variable contains user-controlled content.
