## Analysis

The diff shows a single change in the "participate" mode section of an event management script (Admidio). The new code (lines 416–419 in `after.txt`) checks whether the current user is a **leader** of the event before allowing them to act on behalf of another user:

```php
// if user is no leader of the event then only allow to handle their own participation
if (!$participants->isLeader($gCurrentUserId)) {
    $getUserUuid = $gCurrentUser->getValue('usr_uuid');
}
```

**Before the fix:**  
The `$getUserUuid` variable comes directly from the GET parameter `user_uuid` (line 47). A non-leader, authenticated user could supply any `user_uuid` value in the URL (e.g., `?mode=participate&user_uuid=<victim_uuid>`) and the script would modify the participation status of a different user — adding them to an event, canceling their participation, or setting their status to "maybe" — without any authorization check.

**After the fix:**  
If the current user is not an event leader, `$getUserUuid` is forcefully overridden to the current user's own UUID, preventing manipulation of other users' participation records.

This is a textbook **Insecure Direct Object Reference (IDOR)** vulnerability — a user-controlled key (`user_uuid`) is used to access/modify another user's data without verifying authorization. The fix adds the missing authorization check.
