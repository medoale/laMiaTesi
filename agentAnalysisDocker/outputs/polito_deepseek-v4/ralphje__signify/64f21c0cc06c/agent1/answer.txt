## Analysis

The commit introduces **stricter certificate validation** for Authenticode (Windows code signing) signatures. Let me trace through the full chain of changes:

### What changed

**file_01** (`AuthenticodeSignature.verify()`):
- Added `strict_validation: bool = True` parameter.
- In strict mode, sets `key_usages=["digital_signature"]` and `optional_eku=False` in the verification context kwargs.
- This means: the signer's certificate must have the `digitalSignature` key usage bit AND the `codeSigning` extended key usage (EKU) must be present — as required by the Authenticode specification.

**file_02** (`VerificationContext.verify()` / `validate_usage()`):
- Added `optional_ku` parameter (new), and changed `optional_eku` from plain `bool` to `Literal["critical"] | bool`.
- Reworked how `key_usage` and `extended_key_usage` are passed to the underlying `certvalidator`: they are now only enforced when the corresponding extension is present in the certificate (or when the extension is marked as critical).
- Before, these checks were essentially absent: `key_usages` was never set by the caller, and `optional_eku=True` made the EKU check optional.

**file_03** (tests):
- Added sample `17ad1735a13898c978cc6bbe6b2056cb8471329b` to the "invalid signature" list, with comment "This sample has an invalid keyUsage".
- Added a test `test_17ad_valid_without_strict` proving this sample passes validation when `strict_validation=False`.

**file_04** (binary test data): The test binary itself.

### Security impact

**Before the fix**, a certificate that:
- Was cryptographically signed by a trusted CA
- Had a valid chain, not expired, not revoked
- **BUT** was never authorized for code signing (missing `digitalSignature` key usage, missing `codeSigning` EKU)

...would be **accepted as a valid code signing signature**. This is a security bypass: an attacker could use a certificate scoped for a different purpose (e.g., SSL/TLS server authentication, email signing) to sign code, and the library would not reject it.

The Authenticode specification explicitly requires the `codeSigning` EKU and the `digitalSignature` key usage. Without these checks, the library is effectively validating only the cryptographic chain (is the certificate trusted?) but not the authorization (is this certificate *allowed* to sign code?). This is the textbook definition of **Improper Certificate Validation**.

### CWE Classification

**CWE-295: Improper Certificate Validation** — The software does not validate, or incorrectly validates, a certificate. The code was accepting certificates with missing or improper key usage and extended key usage extensions, which violates the certificate's intended purpose. No other CWE maps as precisely (CWE-347 is about the cryptographic signature itself, not about certificate authorization; CWE-703 is too generic).
