### Is it a security vulnerability fix?

**Yes.** Before the commit, the code accepted Authenticode signatures from certificates that lacked the `digitalSignature` key usage or the `code_signing` Extended Key Usage. These are fundamental certificate constraints defined by the X.509 standard and the Authenticode specification:

1. **Key Usage (`digitalSignature`)** was never checked. A certificate intended for other purposes (e.g., key encipherment, certificate signing, email protection) could be used to sign Authenticode code as long as it was otherwise trusted.
2. **Extended Key Usage (`code_signing`)** was passed to the validator but with `optional_eku=True`, meaning a certificate without *any* EKU would still pass. Certificates lacking the `code_signing` EKU are not authorized for code signing.

A certificate that is trusted but not authorized for code signing should not produce a valid Authenticode signature. By adding proper enforcement of these constraints by default, the commit fixes a security vulnerability.
