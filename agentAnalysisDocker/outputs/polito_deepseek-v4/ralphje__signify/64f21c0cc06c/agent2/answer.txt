## Analysis Summary

**Nature of the project:** This is the `signify` library — a Python Authenticode signature verification library used to verify Windows PE executable digital signatures.

**What the commit does:** It adds a `strict_validation` mode (defaulting to `True`) to `AuthenticodeSignature.verify()` and the underlying `VerificationContext`, enabling proper validation of certificate Key Usage (`digitalSignature`) and Extended Key Usage (`codeSigning`) constraints. It also adds `optional_ku` to the `VerificationContext` and expands `optional_eku` to support a `"critical"` mode.

### The security vulnerability (before the fix)

Tracing the call chain from `AuthenticodeSignature.verify()` → `SignedData._create_verification_context()` → `VerificationContext.__init__()` → `VerificationContext.verify()`:

1. **Key Usage was NEVER validated:**
   - In `AuthenticodeSignature.verify()` (before), `verification_context_kwargs` was passed through unmodified. No `key_usages` were ever set.
   - In `VerificationContext.__init__()` (before), `key_usages` defaulted to `None`.
   - In `VerificationContext.verify()` (before), the code was:  
     `key_usage=set(self.key_usages) if self.key_usages else set()`  
     Since `self.key_usages` was always `None`, this always produced an **empty set** — meaning **no key usage requirements at all**.
   - A certificate with keyUsage set to `keyEncipherment`, `emailProtection`, or no keyUsage at all would pass validation perfectly.

2. **Extended Key Usage was OPTIONAL:**
   - `extended_key_usages=["code_signing"]` was passed, but `optional_eku=True` was the default.
   - The `certvalidator` library's `extended_optional=True` means the EKU check passes even if the certificate lacks the `codeSigning` EKU entirely.
   - A certificate issued for "Email Protection" (1.3.6.1.5.5.7.3.4), "Client Authentication" (1.3.6.1.5.5.7.3.2), or with no EKU at all would validate as a code signing certificate.

**Impact:** An attacker could take a certificate that was legitimately issued for a completely different purpose (e.g., email, server authentication, document signing), use it to sign a malicious PE file, and this library would accept the signature as valid. The cryptographically correct signature would appear to come from a trusted CA, yet the certificate was never authorized by that CA for code signing. This defeats the Authenticode trust model, which relies on the `codeSigning` EKU to restrict which certificates can sign executable code.

**Why this is a security fix, not just a feature:** The default behavior changes — `strict_validation=True` now enforces proper EKU checking (`optional_eku=False`) and key usage checking (`key_usages=["digital_signature"]`). The old default was deliberately lax, aligning with Windows' own lax behavior, but that laxness constitutes a missing security control. The specification (Microsoft's Authenticode spec) requires the code_signing EKU, and RFC 5280 mandates that key usage be respected for certificate path validation.

### CWE Classification

**CWE-295: Improper Certificate Validation** is the most precise classification. The vulnerability is that the certificate validation did not properly enforce the X.509 v3 Key Usage and Extended Key Usage extensions. A certificate whose Key Usage does not include `digitalSignature` and whose Extended Key Usage does not include `codeSigning` was accepted for code signing, which is a violation of standard certificate validation practices.
