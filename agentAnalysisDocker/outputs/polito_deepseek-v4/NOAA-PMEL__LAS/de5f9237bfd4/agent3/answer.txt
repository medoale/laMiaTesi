Based on my thorough analysis of the LAS repository, I have identified a clear and exploitable security vulnerability. Here is my finding:

---

## Analysis

I explored the entire codebase systematically — all Java source files, Velocity templates, configuration files, and scripts.

### Primary Finding: Reflected Cross-Site Scripting (CWE-79)

The `RequestInputFilter` defines an allowlist of permitted HTTP query parameter names (`p[]` array), with additional value validation only for parameter subsets (`lp[]` for LAS IDs, `bp[]` for booleans, special validators for BBOX, format, view, reinit, log_level, template, image, and WMS).

**The `openid` and `auth_url` parameters are in the allowlist but have NO value validation whatsoever.** They are not in the `lp[]`, `bp[]`, or any other value-validator group.

Meanwhile, Velocity templates output these parameters directly into JavaScript/HTML context without any escaping:

**File `V7UI.vm` (lines 107–128):**
```javascript
LAS.params = {
#if (( $request.getParameter('openid') ) && ($request.getParameter('openid') != ""))                      
    'openid' :'$request.getParameter('openid')',
#end
    'auth_url' : [
#foreach ($auth_url in $request.getParameterValues('auth_url'))
    "$auth_url",
#end],
#if ($request.getParameter('catid') && $request.getParameter('catid')!="")
    'catid' :'$request.getParameter('catid')',
...
#if  ($request.getParameter("dsid") && $request.getParameter("dsid")!="")
    'dsid' : '$request.getParameter("dsid")',
...
#if  ($request.getParameter("varid") && $request.getParameter("varid")!="")
    'varid' : '$request.getParameter("varid")',
```

**File `zoom.vm` (lines 34–35):**
```javascript
#if($request.getParameter('openid')!='')
var openid = "$request.getParameter('openid')";
```

The `$request.getParameter(...)` in Velocity returns the raw parameter value with NO HTML/JavaScript escaping. Since the `RequestInputFilter` has no value validation for `openid` or `auth_url`, an attacker can inject arbitrary JavaScript.

**Attack example:**
```
?openid=');alert(document.cookie);//
```
This would render in V7UI.vm as:
```javascript
'openid' :'');alert(document.cookie);//',
```

While `catid`, `dsid`, and `varid` are validated against regex `[/A-Za-z0-9._-]+` (which excludes quotes/angle brackets), `openid` and `auth_url` have zero value-level validation — only name-level allowlist checking.

### Additional Context

The `RequestInputFilter.java` also has a code-level defect at line 368 where `lasRequest` (a local variable) is referenced before its declaration at line 381 — this is a compilation error in the unfixed version, indicating the security control is broken.

### Why Not Other CWEs

- **SQL Injection**: The `AuthenticationFilter` uses `PreparedStatement` with parameterized queries, properly protecting against injection.
- **Path Traversal**: The `GetAnnotations.java` has a `../` check (though limited), and the `validateTemplateAndImage` method blocks `../`, `/`, and `%` in template parameters.
- **XXE**: `JDOMUtils.XML2JDOM` sets `setExpandEntities(false)`, which provides some protection against entity expansion-based attacks.
- **SSRF**: URLs processed come from backend responses, not directly from user-controlled parameters.
