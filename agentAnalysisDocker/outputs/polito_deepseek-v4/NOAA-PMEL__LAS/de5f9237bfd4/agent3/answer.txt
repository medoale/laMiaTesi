## Final Security Audit Report — LAS (Live Access Server)

### Summary

The LAS application contains **multiple critical vulnerabilities** enabling unauthenticated remote code execution via Server-Side Template Injection (SSTI), SQL injection, XML External Entity (XXE) injection, and XPath injection. The README explicitly confirms CVE-2025-59782, a validation bypass in the input filter, but the issues extend far beyond that single bug.

---

### Vulnerability 1: Validation Bypass in `RequestInputFilter.validateTemplateAndImage()` (CVE-2025-59782)

**File:** `RequestInputFilter.java`, lines 419–466

**Bug:** In the `template` parameter validation loop (line 422-444), the check on line 432 uses `if ( v.equals(vm[i]) ) return true;` — it compares the i-th user-supplied value against the i-th whitelist entry. If the first user value happens to match the first whitelist entry (`admin.vm`), the function returns `true` immediately, skipping validation for all subsequent template values and all subsequent checks (the `image` parameter block at lines 446–464 is never reached). This allows an attacker to smuggle a second `<las_template>` element (in the XML body via the `xml` parameter) with an arbitrary template path.

Additionally, even within a single `template` value, the `..` and `/` character checks (lines 428-429) pass before the whitelist match on line 432, so a path-traversal attempt like `../admin.vm` is blocked — but the core bug is the premature `return true`.

**Impact:** Attackers can bypass the input filter entirely by providing a parameter set where at least one `template` value matches `vm[0]` (`admin.vm`), then providing malicious payloads in other parameters or the XML body.

**CWE:** CWE-754 (Improper Check for Unusual or Exceptional Conditions) / CWE-20 (Improper Input Validation)

---

### Vulnerability 2: Unvalidated XML Body (`xml` Parameter)

**File:** `RequestInputFilter.java`, lines 361–391

**Bug:** The HTTP `xml` (or `lasxmldoc`) parameter content is decoded (line 367) and parsed into a `LASUIRequest` (line 383) that is stored in the request attributes for downstream processing. This XML body is **never validated for malicious content** by the filter. There is a check for a "ferret expression" (lines 368-373), but this only checks one specific property. The XML can carry arbitrary `<property>`, `<symbol>`, `<range>`, `<region>`, `<constraint>`, and `<dataObjects>` elements that flow directly into:

- **SSTI/RCE** via Velocity template merging
- **SQL injection** via database constraint generation  
- **XXE** via JDOM parsing

**CWE:** CWE-20 (Improper Input Validation)

---

### Vulnerability 3: XML External Entity (XXE) Injection → Arbitrary File Read

**Files:**
- `JDOMUtils.java` (lines 42–44, 72–73)
- `MyResolver.java` (lines 20–47)

**Bug:** `JDOMUtils.XML2JDOM()` configures a `SAXBuilder` with `setExpandEntities(false)` and `setEntityResolver(new MyResolver())`. The custom `MyResolver` entity resolver resolves `file://` scheme URIs by reading the file and returning its content (lines 32–39 of `MyResolver.java`). An attacker can craft a malicious XML entity referencing a local file:

```xml
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<lasRequest>&xxe;</lasRequest>
```

This file content is then processed as part of the XML and can be reflected in error messages, log output, or application responses.

**Impact:** Unauthenticated remote attackers can read arbitrary files from the server filesystem.

**CWE:** CWE-611 (Improper Restriction of XML External Entity Reference)

---

### Vulnerability 4: Server-Side Template Injection (SSTI) → Remote Code Execution

**Files:**
- `FerretTool.java` — calls `mergeCommandTemplate()` → `ve.mergeTemplate()`
- `TemplateTool.java` — lines 190–215 — Velocity template engine
- `DatabaseTool.java` — lines 379–407 — same Velocity merge pattern
- `Task.java` — `Runtime.getRuntime().exec(cmd, env, workDir)`

**Bug:** The `mergeCommandTemplate()` method in both `TemplateTool` and `DatabaseTool`:
1. Puts the entire `LASBackendRequest` object into the Velocity context as `las_backendrequest` (line 207-208 of `TemplateTool.java`, line 400 of `DatabaseTool.java`)
2. Puts user-controlled symbols/properties into the Velocity context as `symbols` (line 205-207 of `TemplateTool.java`)
3. Merges a Velocity template containing these user-controlled values (line 211 of `TemplateTool.java`, line 403 of `DatabaseTool.java`)

The result is written to a `.jnl` (Ferret script) file, which is then executed via `Runtime.getRuntime().exec()` in `Task.java`.

The user controls the template filename itself via `getProperty("operation","service_action") + ".vm"` (DatabaseTool.java line 125), meaning an attacker can select which `.vm` template gets loaded.

Velocity supports powerful directives like `#set`, `#foreach`, `$class.inspect()`, and method calls on context objects. Since `las_backendrequest` (the full `LASBackendRequest` object) is in context, an attacker can call arbitrary methods on it via Velocity syntax like:

```
$las_backendrequest.getClass().forName('java.lang.Runtime').getRuntime().exec('id')
```

The merged output becomes a Ferret script written to a file, and `Task.exec()` runs it as a shell command.

**Impact:** Complete remote code execution on the server as the Tomcat process user.

**CWE:** CWE-917 (Improper Neutralization of Special Elements used in Template Engines) / CWE-78 (Improper Neutralization of Special Elements used in an OS Command)

---

### Vulnerability 5: SQL Injection via Region Constraints

**Files:**
- `LASBackendRequest.java` — methods `getAxisAsConstraint()`, `axisConstraint()`, `getRegionAsConstraint()`
- `DatabaseTool.java` — executes the merged SQL

**Bug:** The region bounds (x_lo, x_hi, y_lo, y_hi, z_lo, z_hi, t_lo, t_hi) are extracted from user-controlled XML elements and concatenated into SQL WHERE clauses without parameterization. The `axisConstraint()` method (not fully shown but called on line 1231 of LASBackendRequest.java) builds strings like:

```sql
WHERE longitude BETWEEN <user_value> AND <user_value>
```

The user values come directly from <range type="x" low="..." high="..."> elements in the XML body, which bypass the input filter entirely.

**Impact:** Attackers can execute arbitrary SQL commands against the backend database.

**CWE:** CWE-89 (Improper Neutralization of Special Elements used in an SQL Command)

### Vulnerability 6: XPath Injection

**File:** `LASUIRequest.java`, lines 37–46 (`addVariable()`) and lines 243–248 (`setOperation()`)

**Bug:** User-supplied `dsID` and `varID` parameters are directly concatenated into XPath expressions:

```java
link.setAttribute("match", "/lasdata/datasets/dataset[@ID='"+dsID+"']/variables/variable[@ID='"+varID+"']");
```

```java
String operation_xpath = "/lasdata/operations/operation[@ID='"+ID+"']";
```

No sanitization or escaping is applied to these values before XPath evaluation.

**CWE:** CWE-643 (Improper Neutralization of Data within XPath Expressions)

### Vulnerability 7: Arbitrary Template File Inclusion

**File:** `DatabaseTool.java`, line 125

```java
String sql = lasBackendRequest.getProperty("operation","service_action") + ".vm";
```

`getProperty("operation","service_action")` returns a value from the user-controlled XML's `<property_group type="operation">` element. The attacker sets `service_action` to control which `.vm` template file is loaded. This enables loading unintended templates from the filesystem (within the template directory).

**CWE:** CWE-73 (External Control of File Name or Path)

### Vulnerability 8: Unsafe Type-Specific Region Constraints

**Files:**
- `LASBackendRequest.java` — `getAxisAsConstraint()`, `getDatabaseTime()`, `getXlo()/getXhi()` etc.

**Bug:** When the `time_type` database property is `"string"`, date values are concatenated with quotes. But numeric coordinate values (x, y, z) are also concatenated unsafely. The values come from `<region>` elements parsed from the user-controlled XML body.
