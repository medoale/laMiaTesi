## Analysis

This commit modifies three files that collectively fix a critical security gap in Qdrant's logger configuration endpoints (`GET /logger` and `POST /logger`).

### Changes Summary

**File 1: `/work/src/actix/api/service_api.rs`** — The main fix:
- **`GET /logger`**: Added `ActixAccess(access)` parameter and an authorization check via `access.check_global_access(AccessRequirements::new())`. Before: no authorization at all — any unauthenticated caller could read the full logger configuration.
- **`POST /logger`**: Added `ActixAccess(access)` parameter and an authorization check via `access.check_global_access(AccessRequirements::new().manage())`. Before: any unauthenticated caller could modify the logger config. Also added `config.on_disk.log_file = None;` to prevent changing the log file path via the API.

**File 2: `/work/src/tracing/on_disk.rs`** — Cosmetic error message improvements clarifying that the log file path can only be set through the config file.

**File 3: `/work/tests/consensus_tests/auth_tests/test_jwt_access.py`** — Added test entries and test functions for the two logger endpoints, ensuring that the authorization rules are properly enforced.

### Security Vulnerabilities Fixed

**1. Missing Authorization (CWE-862)**
The `GET /logger` and `POST /logger` handlers had **zero access control**. Every other service endpoint in the same file (`/telemetry`, `/metrics`, `/stacktrace`, etc.) uses the `ActixAccess` framework with `check_global_access()` to enforce authentication. The logger endpoints were simply overlooked.

- Before: Any unauthenticated caller could read the current logger configuration (log levels, file paths, format settings, buffer sizes).
- Before: Any unauthenticated caller could change the logger configuration at runtime.

**2. External Control of File Name or Path (CWE-73)**
The `POST /logger` endpoint accepted a `log_file` field in the request body, which was passed directly to `on_disk::new_layer()`. That function opens the specified file with `fs::OpenOptions::new().create(true).append(true).open(log_file)`, then writes log data to it. This means:

- Before: Any unauthenticated caller could specify an arbitrary file path, and the server would create or append to that file with log content. This enables arbitrary file writes, log injection/poisoning, and potential overwriting of critical system files.
- The fix nullifies `config.on_disk.log_file = None` before calling `update_config`, preventing the log file path from being changed via the API at all — it can only be set through the startup config file.

### Conclusion

This commit **fixes security vulnerabilities** — specifically, **Missing Authorization** (the endpoints had no access control) and **External Control of File Name or Path** (the log file path was user-controlled, enabling arbitrary file writes).
