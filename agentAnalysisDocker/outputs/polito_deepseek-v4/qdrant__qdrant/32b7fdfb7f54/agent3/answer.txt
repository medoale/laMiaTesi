## Summary

I identified a **Server-Side Request Forgery (SSRF)** vulnerability in Qdrant's snapshot recovery functionality. The vulnerability exists in the URL download path used when recovering snapshots from remote locations.

## Root Cause

The reqwest HTTP client is constructed in `/work/src/common/http_client.rs` (line 65) with **no redirect policy, no proxy configuration, and no internal IP filtering**. The default reqwest policy allows up to **10 redirects**. The download function in `/work/lib/storage/src/content_manager/snapshots/download.rs` (line 43) performs `client.get(url.clone()).send().await?` on a fully user-supplied URL with no URL validation beyond scheme matching (`http` / `https` / `file`).

## Attack Paths

1. **`PUT /collections/{name}/snapshots/recover`** — accepts `SnapshotRecover` with `location: Url`. The URL is passed directly to `download_snapshot()` in `recover.rs` (line 112).

2. **`PUT /collections/{collection}/shards/{shard}/snapshots/recover`** — accepts `ShardSnapshotRecover` with `location: ShardSnapshotLocation`. When the location is `Url(url)`, it calls `download_snapshot()` in `snapshots.rs` (line 183).

3. **`POST /collections/{collection}/shards/{shard}/snapshot/partial/recover_from`** — accepts `PartialSnapshotRecoverFrom` with `peer_url: Url`, constructs a URL via `format!("{peer_url}/collections/{collection_name}/shards/{shard_id}/snapshot/partial/create")`, and performs a POST with user-controlled body (snapshot manifest).

All three paths require `manage` global access, but any administrator with valid credentials can exploit them to reach internal services (cloud metadata endpoints at `169.254.169.254`, Kubernetes internal services, other container endpoints on the same network).

## Impact

- **Cloud metadata exfiltration**: Requesting `http://169.254.169.254/latest/meta-data/` returns cloud instance credentials (AWS, GCP, Azure).
- **Internal network scanning**: Reach internal APIs, databases, and services otherwise inaccessible from outside the cluster.
- **API key leakage** (documented in `http_client.rs` line 46-50): When an API key is provided in the recovery request, it is sent as a header to the attacker-controlled URL.
- **Redirect bypass**: Starting from a valid external HTTPS URL that redirects to an internal IP bypasses the scheme check in `download_snapshot`, since only the original URL's scheme is validated.
