## Analysis

### What changed

**file_01 (documentation):** Adds documentation for two new security limits on `PdfWriter` incremental mode — `incremental_clone_object_count_limit` (default 500,000) and `incremental_clone_object_id_limit` (default 1,000,000).

**file_02 (core code — `PdfWriter`):** This is the substantive fix. Two key changes:

1. **Constructor (`__init__`)**: Two new keyword-only parameters `incremental_clone_object_count_limit` and `incremental_clone_object_id_limit` are added, stored as instance attributes (with `None`/non-int values defaulting to `sys.maxsize`).

2. **New method `_collect_incremental_clone_object_ids()`**: Instead of blindly trusting the PDF trailer's `/Size` field, this method collects the *actual* object IDs from the xref table (`reader.xref`), then checks two limits before proceeding:
   - Whether the **number** of actual objects exceeds the count limit.
   - Whether the **maximum object ID** exceeds the ID limit.
   If either is exceeded, a `LimitReachedError` is raised.

3. **Modified `clone_reader_document_root()`**: The old code — which is the crux of the vulnerability — was:
   ```python
   self._objects = [None] * (cast(int, reader.trailer["/Size"]) - 1)
   for i in range(len(self._objects)):
       o = reader.get_object(i + 1)
   ```
   This allocated `[None] * (attacker-controlled_size - 1)` and then iterated over that huge range. The new code instead calls `_collect_incremental_clone_object_ids()` and only allocates/iterates over the actual object IDs found in the xref table.

**file_03 (tests):** Adds tests confirming:
- A PDF with a trailer `/Size` of 5,000,000 but only 3 actual objects is now handled safely (no crash, no massive allocation).
- The count-limit and ID-limit checks raise `LimitReachedError` as expected.

### Vulnerability assessment

This is **unambiguously a security fix** for a denial-of-service vulnerability.

An attacker can craft a PDF that declares an enormous `/Size` (e.g., 5,000,000 or more) in its trailer dictionary while containing only a handful of real objects. When `PdfWriter(clone_from=..., incremental=True)` processes such a file, the old code would:

1. Allocate a list of `None` elements equal in length to the `/Size` — potentially consuming gigabytes of memory.
2. Iterate over that entire range (millions of iterations), performing `reader.get_object()` calls for each index — causing CPU exhaustion.

This is a classic **resource exhaustion via allocation without limits**.

### CWE classification

The most accurate and specific CWE is:

- **CWE-770: Allocation of Resources Without Limits or Throttling** — The code directly allocates a Python list of size `reader.trailer["/Size"] - 1` without imposing any upper bound, where `/Size` is attacker-controlled data from the PDF file. This is a child of CWE-400 and more specific.

CWE-20 (Improper Input Validation) is also technically present as the root cause (trusting the `/Size` trailer value without validation), but CWE-770 is the more specific and precise classification for the actual harm prevented.

Only one CWE is genuinely needed here — CWE-770 — as it captures both the input validation gap and the resource exhaustion consequence.
