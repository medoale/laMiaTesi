### Change 1: SVG Sanitizer — SSRF Fix (File 01)

**File:** `packages/Webkul/Core/src/Traits/Sanitizer.php`

**Before:**
```php
$sanitizer = new MainSanitizer;
$dirtySVG = Storage::get($path);
Storage::put($path, $sanitizer->sanitize($dirtySVG));
```

**After:**
```php
$sanitizer = new MainSanitizer;
$sanitizer->removeRemoteReferences(true);
$dirtySVG = Storage::get($path);
Storage::put($path, $sanitizer->sanitize($dirtySVG));
```

**Vulnerability:**
The `enshrined\svgSanitize` library's `removeRemoteReferences()` method strips external references from SVG elements (e.g., `<image xlink:href="http://...">`, `<use href="http://...">`). Without this call, when a malicious SVG is uploaded and sanitized, the sanitizer library will attempt to **resolve and fetch the external URLs** referenced in the SVG. This is a classic **Server-Side Request Forgery (SSRF)** vector through SVG file uploads.

An attacker could craft an SVG like:
```xml
<svg xmlns="http://www.w3.org/2000/svg" xmlns:xlink="http://www.w3.org/1999/xlink">
  <image xlink:href="http://169.254.169.254/latest/meta-data/"/>
</svg>
```
On upload, the sanitizer would attempt to dereference `http://169.254.169.254/latest/meta-data/` (the AWS metadata endpoint), leaking cloud credentials.

**Impact:** SSRF via SVG upload — an attacker can make the server issue arbitrary HTTP requests to internal or external systems.

**CVSS-like severity:** High — External attacker can upload SVG via product reviews (unauthenticated) or search (unauthenticated), or via TinyMCE (authenticated admin).

**CWE: CWE-918 (Server-Side Request Forgery)**

### Change 2: Installer Middleware — Authentication Bypass (Files 04, 05)

**File:** `packages/Webkul/Installer/src/Http/Middleware/CanInstall.php`

This middleware is registered **globally** in `bootstrap/app.php` and also in middleware group `'install'`. It runs on every request.

**Before:**
```php
if ($this->isAlreadyInstalled() && ! $request->ajax()) {
    return redirect()->route('shop.home.index');
}
```

**After:**
```php
if ($this->isAlreadyInstalled()) {
    if (! $request->ajax()) {
        return redirect()->route('shop.home.index');
    }
    return response()->json([
        'message'=> trans('installer::app.installer.middleware.already-installed'),
    ], 403);
}
```

**Vulnerability:**
The old condition checked `$this->isAlreadyInstalled() && ! $request->ajax()`. When the application **was already installed** AND the request **was AJAX** (i.e., `$request->ajax()` returns `true`), the `! $request->ajax()` became `false`, making the entire condition `false`. This meant no redirect occurred, and the request **passed through** to the installer controller.

This allowed an attacker to send an AJAX POST request to `admin-config-setup` (route: `/install/api/admin-config-setup`) **after** the application was installed, and overwrite the admin credentials. The old `updateOrInsert()` would update the admin record with the attacker's credentials (email, name, password).

The fix changes this to a nested structure where an installed check always blocks the request: for non-AJAX with a redirect, for AJAX with a 403 JSON response.

**Defense-in-depth (file 04):** The `InstallerController::adminConfigSetup()` method changed from `DB::table('admins')->updateOrInsert(...)` to `DB::table('admins')->insert(...)`. If the admin record with `id=1` already exists, `insert` will fail with a duplicate key exception, preventing overwrite even if somehow the middleware is bypassed.

**CWE: CWE-287 (Improper Authentication)** — The authentication mechanism (middleware) existed but was improperly implemented, allowing bypass for AJAX requests.
