After thorough analysis of the Nautobot repository (a Django-based Network Source of Truth and Automation Platform), I found multiple security issues. The most concrete and clearly exploitable vulnerability is:

## Vulnerability: Server-Side Request Forgery (SSRF) via Webhooks

**Location:** `/work/nautobot/extras/models/models.py` (lines 991-995) and `/work/nautobot/extras/tasks.py` (lines 177-246)

**Details:** The `Webhook.payload_url` field is defined as a plain `CharField` (max_length=500) with **no URL validation whatsoever** — no `URLValidator`, no `EnhancedURLValidator`, no `LaxURLField`. Contrast this with `ExternalIntegration.remote_url` in the same project which properly uses `LaxURLField` with `EnhancedURLValidator`. 

When a webhook is triggered, the `process_webhook` Celery task (`extras/tasks.py:178`) makes an HTTP request directly to the user-specified `payload_url`:

```python
params = {
    "method": webhook.http_method,        # user-controlled
    "url": webhook.payload_url,           # user-controlled, unvalidated
    "headers": headers,                   # user-controlled headers via Jinja2 template
    "data": body.encode("utf8"),          # user-controlled body via Jinja2 template
}
prepared_request = requests.Request(**params).prepare()
# ...
response = session.send(prepared_request, proxies=settings.HTTP_PROXIES)
```

An attacker with permission to create/modify Webhooks can make the Nautobot server send arbitrary HTTP requests to **internal services**, including:
- Cloud metadata endpoints (e.g., `http://169.254.169.254/latest/meta-data/`)
- Internal Redis/MySQL/PostgreSQL HTTP management interfaces
- Internal Kubernetes API servers
- Other internal microservices
- The Nautobot server itself (`http://localhost:8080/...`)

The attacker controls the HTTP method, headers, and body, making this a versatile SSRF vector. The response status code and content are also leaked back to the attacker (logged and potentially observable through error messages).
