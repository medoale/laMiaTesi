## Summary of Changes

The commit modifies 4 files to add path traversal protection for DAG file names:

1. **`internal/service/frontend/api/api.go`** — Adds a global middleware `validateDAGFileNameMiddleware` that validates the `FileName` field in all API request objects before they reach the handler. It calls `core.ValidateDAGName()` which only allows characters matching `^[a-zA-Z0-9_.-]+$`, rejects `..` and `.`, and caps length at 40 characters.

2. **`internal/service/frontend/api/api_test.go`** — Adds `TestDAGFileNameRejectsEncodedTraversal` which tests that URL-encoded path traversal attempts like `..%2F..%2Ftmp%2Fsecret` are rejected (status 400). Uses a raw HTTP client to bypass Go's URL normalization.

3. **`internal/service/frontend/sse/topic.go`** — Previously, `TopicTypeDAG` and `TopicTypeDAGHistory` identifiers were returned as-is without validation. Now they are validated through `core.ValidateDAGName()`, rejecting traversal sequences.

4. **`internal/service/frontend/sse/sse_test.go`** — Adds `TestParseTopicRejectsDAGTraversalIdentifiers` verifying that path traversal in topic identifiers like `dag:../../tmp/secret.yaml` are rejected.

## Vulnerability Analysis

**Before the fix**, the DAG file store's `locateDAG()` function (in `internal/persis/filedag/store.go`) would detect a path separator (`/`) in the name and call `findDAGFile()` directly, which calls `filepath.Abs()` on the user-supplied path. This means:

- A GET `/api/v1/dags/../../etc/passwd/spec` would read `/etc/passwd` as a YAML DAG spec
- A DELETE `/api/v1/dags/../../tmp/malicious` would delete `/tmp/malicious.yaml`
- An SSE subscription to `dag:../../etc/secret.yaml` would attempt to load and stream that DAG's data

The `CreateNewDAG` path was already partially protected via `generateFilePath()` which uses `filepath.Base()`, but all other DAG operations (Delete, GetSpec, UpdateSpec, Rename, Execute, etc.) relied on `locateDAG()` which follows traversal sequences. These operations were all exploitable until this fix.

The test in file 02 specifically verifies that even URL-encoded traversal (`%2F` for `/`) is caught — demonstrating awareness that attackers would try encoding schemes to bypass router-level normalization.
