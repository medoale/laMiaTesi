## Analysis

### Context

This is **malcontent**, a malware scanning tool by Chainguard that detects supply-chain compromises using YARA rules and archive analysis. It transparently extracts nested archives during scanning.

### The Changed Files

**file_01** — Test file in the `action` package. It adds helper `createBrokenNestedArchive` and two new tests:
- `TestNestedFailureRetention` — verifies that when a broken nested archive can't be extracted with `ExitExtraction=false`, the original archive file is *retained* in the extraction directory so it can still be scanned as a regular file.
- `TestNestedFailureRetentionError` — verifies that with `ExitExtraction=true`, the error is propagated.

**file_02** — Production code: `/work/pkg/archive/archive.go`, `extractNestedArchive` function. This is the core change.

### The Vulnerability (Before)

In the before code (lines 192–204 of `archive.go`):

```go
err = extract(ctx, archivePath, fullPath)
if err != nil {
    if c.ExitExtraction {
        return fmt.Errorf("failed to extract archive: %w", err)
    }
    logger.Debugf("ignoring extraction error for %s: %s", f, err.Error())
}

extracted.Store(f, true)

if err := os.Remove(fullPath); err != nil {
    return fmt.Errorf("failed to remove archive file: %w", err)
}
```

When a nested archive fails to extract (and `ExitExtraction=false`, i.e., "keep going despite errors"):
1. The error is logged at `Debugf` level (inconspicuous).
2. The file is **unconditionally deleted** via `os.Remove(fullPath)` on line 202.
3. The deleted content is never scanned.

**Security impact:** A malware author can craft a nested archive (e.g., a tar.gz containing another broken archive) whose inner content cannot be extracted. The vulnerable code deletes that inner file entirely, so the YARA rules and scanner never inspect it. Malicious payloads hidden inside broken/degenerate nested archives silently evade detection — the tool reports a clean result while the malware remains on disk.

### The Fix (After)

```go
err = extract(ctx, archivePath, fullPath)
if err != nil {
    if c.ExitExtraction {
        return fmt.Errorf("failed to extract archive: %w", err)
    }
    logger.Warnf("extraction failed for %s, retaining archive for scanning: %s", f, err.Error())
}

extracted.Store(f, true)

// only attempt to remove the archive file if we don't encounter an extraction error
// any archives which cannot be extracted will be scanned like non-archive files
if err == nil {
    if err := os.Remove(fullPath); err != nil {
        return fmt.Errorf("failed to remove archive file: %w", err)
    }
}
```

The key change: `os.Remove` is now conditional on `err == nil`. If extraction failed, the file is preserved in the extraction directory and will be scanned as a regular non-archive file by the scanning infrastructure that walks the directory.

### CWE Classification

The root cause is **improper handling of an exceptional condition**. The error return value from `extract()` is checked — but only for the purpose of deciding logging vs. early exit. The check is **incomplete**: the same error is not used to prevent the destructive deletion that should only happen when extraction succeeded. This is a textbook case of:

- **CWE-703: Improper Check or Handling of Exceptional Conditions** — The software properly detects an exceptional condition (extraction failure) but does not handle it correctly in all code paths, leading to the destruction of evidence that should have been scanned.

No other CWE applies more specifically: this is not a path traversal (CWE-22), not an information exposure (CWE-200), not a resource exhaustion (CWE-770), and not a pure logging issue (CWE-778) — the log level change is merely diagnostic. The core defect is the failure to guard a destructive operation with the error check.
