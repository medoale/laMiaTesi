**What I looked at:**

- **Archive extraction** (tar, zip, deb, rpm, cpio, gzip, bz2, zlib, zstd, upx, oci): Excellent path traversal prevention with `IsValidPath`, `ValidateResolvedPath`, symlink resolution, TOCTOU re-validation post-creation for symlinks. All extraction is size-bounded. UPX exec.Command uses `--` separator and validated paths.

- **File reading** (file.go): `MaxBytes = 1<<32` (4GB). This is an intentional design choice to handle large files that could be legitimate binaries. `io.LimitReader` is used, so it won't exceed 4GB even on huge files. The 4GB allocation is concerning for small-memory systems but is bounded and intentional — not a vulnerability in the context of a malware scanner that needs to read potentially large binaries.

- **Buffer pool** (pool.go): `clear(buf)` zeroes the slice elements correctly in Go. The `cap > len` concern about stale data is valid only if someone accesses `buf` beyond its `len`, which never happens through normal Go slice operations. All callers use `buf[:size]` which constrains to the correct length. The backing array beyond `len` is inaccessible through safe Go code. Not exploitable.

- **UPX exec.Command**: Both calls (in `upx.go` and `programkind.go`) properly validate the UPX path via `UPXInstalled()` which checks file existence and executable bit. The `--` argument separator prevents flag injection. Filenames starting with `-` are rejected. The `MALCONTENT_UPX_PATH` environment variable is a documented, intentional configuration mechanism.

- **TOCTOU in programkind.go**: Line 391 calls `EvalSymlinks` but discards the result. Lines 396 (Stat) and 406 (Open) operate on the original path. A TOCTOU race is theoretically possible but extremely narrow and requires local write access to the directory being scanned. The impact is limited to reading a different file's first 64KB or potentially stalling on a FIFO. This is the closest thing to a real vulnerability but is mitigated by the tool running in CI/scan contexts on user-controlled paths.

- **Compile package**: The `regexp.MustCompile` on line 173 uses `regexp.QuoteMeta` on rule names so the pattern is valid. The ReDoS concern on the `rulePattern` is about the pattern's own structure, not user input — rule names are controlled by the internal `badRules` and `rulesWithWarnings` maps, not by attacker input. Not exploitable.

- **Cache integrity**: The cache file at `~/.cache/malcontent/rules-<sha256>.cache` requires write access to the user's home cache directory. If an attacker has that level of access, they already own the system. The hash includes yara-x version and rule file contents, so cache poisoning requires a SHA-256 preimage attack (computationally infeasible).

- **Render/report output**: `sanitizeUTF8` strips BiDi characters and replaces newlines. YAML marshaling via `gopkg.in/yaml.v3` properly escapes strings. No XSS vector exists since output goes to terminal, JSON, or YAML files — not rendered in a browser.
