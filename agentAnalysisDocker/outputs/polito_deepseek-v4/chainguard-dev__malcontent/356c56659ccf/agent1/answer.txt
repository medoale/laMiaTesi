// any archives which cannot be extracted will be scanned like non-archive files

**The vulnerability:** In the "before" code, when extraction of a nested archive fails but `ExitExtraction` is `false`, the code would **still delete the original archive file** (`os.Remove(fullPath)`) unconditionally. This means:

1. If a nested archive inside an outer archive fails to extract (e.g., it's a corrupt zip/gzip but still valid enough to be detected as an archive by extension), the original inner archive file would be **deleted**.
2. The content of that inner archive would then be **invisible to subsequent scanning** — malware embedded in a nested archive that fails extraction would simply be silently deleted, bypassing the security scanner entirely.
3. An attacker could craft a nested archive that triggers extraction failure (e.g., a gzip that decompresses to invalid content or a slightly corrupt zip) and the scanner would just delete it without scanning it, allowing malicious content hidden inside a problematic nested archive to evade detection.

This is a **security bypass / evasion** vulnerability: an attacker can hide malicious content inside nested archives that are designed to fail extraction, and the "before" code would silently delete those archives instead of retaining them for scanning as regular files. The fix makes the code only delete the archive file if extraction succeeded (`if err == nil`), so failed nested archives are retained and can still be scanned.

This falls under **CWE-223: Omission of Security-relevant Information** (the scanner fails to process and report on content it should scan), or more accurately **CWE-280: Improper Handling of Insufficient Permissions or Privileges** or **CWE-703: Improper Check or Handling of Exceptional Conditions** — the code unconditionally removes the archive even when extraction fails.
