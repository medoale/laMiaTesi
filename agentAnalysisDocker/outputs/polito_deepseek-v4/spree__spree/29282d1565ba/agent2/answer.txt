## Analysis of Changes

The commit introduces three sets of changes spanning three files:

### File 1 — New API test (`file_01`)
A new RSpec test for `Spree::Api::V2::Storefront::CheckoutController` validating that guest users **cannot** set `bill_address_id` to pre-existing addresses — whether they belong to another user or have `user_id: nil`.

### File 2 — The core fix (`file_02` — `address_book.rb`)
This is the security-critical change in `Spree::Order::AddressBook`. Both `bill_address_id=` and `ship_address_id=` were modified:

**Before:**
```ruby
if address && address.user_id == user_id
```

**After:**
```ruby
if address && user_id.present? && address.user_id == user_id
```

The critical addition is `user_id.present?`. In Ruby, `nil == nil` evaluates to `true`. This means when `order.user_id` is `nil` (a guest user), the old code treated `address.user_id == nil` as a match — allowing a guest user to **link their order to any address in the database that has `user_id: nil`**. An attacker could:

1. Start a guest checkout session.
2. Craft a request to the checkout `update` endpoint with `bill_address_id` or `ship_address_id` pointing to an address belonging to another guest session (or an orphaned address).
3. The old code would accept it because `nil == nil` is `true`.
4. This could lead to misdelivery of goods, information exposure of other users' addresses, or address-based fraud.

The fix also adds:
- An early `return if bill_address_id == id` guard to skip unnecessary re-assignment (optimization).
- `reset_bill_address` / `reset_ship_address` instead of `bill_address.reload` / `ship_address.reload`, ensuring the cached association is properly cleared even in the failure path (avoiding stale data).

### File 3 — New model tests (`file_03`)
Unit test additions in `order_spec.rb` that explicitly verify:
- Addresses not belonging to the user are rejected (set to `nil`).
- Guest users (`user: nil`) cannot assign any address via `bill_address_id=` / `ship_address_id=`, even addresses with `user_id: nil`.

### Classification

This is an **Insecure Direct Object Reference (IDOR)** vulnerability. The `bill_address_id` and `ship_address_id` parameters are user-controlled keys (direct references to `Spree::Address` objects), and the authorization check failed for guest users because `nil == nil` returns `true` in Ruby.

**CWE-639: Authorization Bypass Through User-Controlled Key** is the most specific and accurate classification. It is a subtype of CWE-284 (Improper Access Control), but CWE-639 captures the exact nature of the flaw: a direct object reference with insufficient authorization verification.
