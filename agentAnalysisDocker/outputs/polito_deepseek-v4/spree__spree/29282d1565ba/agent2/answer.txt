## Analysis

This commit fixes a security vulnerability in the `Spree::Order::AddressBook` concern (`/work/core/app/models/spree/order/address_book.rb`).

### The Vulnerability

The `bill_address_id=` and `ship_address_id=` setter methods perform an authorization check before assigning an address to an order:

```ruby
# Before (vulnerable — still in the working tree):
def bill_address_id=(id)
  address = Spree::Address.find_by(id: id)
  if address && address.user_id == user_id
    self['bill_address_id'] = address.id
    bill_address.reload
  else
    self['bill_address_id'] = nil
  end
end

# After (fixed):
def bill_address_id=(id)
  return if bill_address_id == id
  address = Spree::Address.find_by(id: id)
  if address && user_id.present? && address.user_id == user_id
    self['bill_address_id'] = address.id
  else
    self['bill_address_id'] = nil
  end
  reset_bill_address
end
```

The critical change is the addition of `user_id.present?` to the authorization condition.

### Root Cause: `nil == nil` Bypass

In Ruby, `nil == nil` evaluates to `true`. When an order belongs to a **guest user** (`order.user_id` is `nil`), and the target address also has `address.user_id = nil` (i.e., it belongs to another guest user — or no specific user), the original check `address.user_id == user_id` evaluates to `nil == nil` → `true`, bypassing the authorization entirely.

This means a guest attacker who can supply an arbitrary address ID (a direct object reference) via the Storefront Checkout API could:

1. **Steal another guest user's address** — by guessing or enumerating address IDs that belong to other guest sessions.
2. **Access personal information** — addresses typically contain name, street address, phone number, and zip code, which would become associated with the attacker's order and potentially visible.
3. **Use a stolen address for shipping** — the attacker could receive goods shipped to someone else's address, or use the address for fraudulent purposes.

### The Fix

The fix adds `user_id.present?` to the condition:

```ruby
if address && user_id.present? && address.user_id == user_id
```

This ensures that:
- For **authenticated users** (`user_id` is not nil): the address must belong to that user (`address.user_id == user_id`)
- For **guest users** (`user_id` is nil): `user_id.present?` is `false`, so the entire condition short-circuits to `false`, and the address assignment is rejected (set to `nil`)

The commit also adds an early return guard (`return if bill_address_id == id`) to avoid redundant work when setting the same ID, and replaces direct `reload` calls with `reset_bill_address`/`reset_ship_address` — but these are clean-up/optimization changes, not the security fix itself.

### Classification

This is **CWE-639: Authorization Bypass Through User-Controlled Key** — the most specific applicable CWE. The user controls a direct object reference (the address ID) through the API, and the authorization check is improperly implemented, allowing access to addresses the user should not be able to access. The specific flaw is that the equality check `address.user_id == user_id` does not account for the case where both values are `nil`, making it trivially bypassable for guest users.
