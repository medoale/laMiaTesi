Based on my thorough analysis of the entire Spree Commerce codebase across ~38 files in storefront controllers, 30+ API controllers, 15+ permission set files, authentication/authorization infrastructure, and core business logic, I have identified multiple genuine security vulnerabilities.

## Summary of Key Vulnerabilities Confirmed

### 1. OAuth Access Tokens Stored in Plaintext (CWE-522)
**File:** `api/config/initializers/doorkeeper.rb:45-47`
```ruby
hash_token_secrets fallback: :plain
```
All OAuth access tokens are stored in plaintext in the database. Application client secrets use BCrypt, but the more valuable access tokens do not. Database compromise = all active API tokens stolen.

### 2. CanCanCan Authorization Bypass for Application-Only Tokens (CWE-862)
**File:** `api/app/controllers/spree/api/v2/platform/resource_controller.rb:64-68`
```ruby
def scope
  return super if spree_current_user.present?
  super(skip_cancancan: true)
end
```
When Platform API is called via a `client_credentials` token (no user), `accessible_by` with CanCanCan is completely skipped. Any application with `:read` scope can list ALL resources: users, orders, credit cards, etc.

### 3. `add_role` / `remove_role` with Zero Authorization (CWE-269)
**File:** `core/app/models/concerns/spree/user_roles.rb:19-37`
```ruby
def add_role(role_name, resource = nil)
  role = Spree::Role.find_by(name: role_name)
  role_users.find_or_create_by!(role: role, resource: resource)
end
```
No check prevents any code path from calling `user.add_role('admin')`. The same applies to `remove_role`.

### 4. RoleManagement Permission Set Allows Privilege Escalation (CWE-284)
**File:** `core/app/models/spree/permission_sets/role_management.rb:12-17`
```ruby
can :manage, Spree::Role     # allows CREATE new roles
can :manage, Spree::RoleUser # allows CREATE RoleUser records
cannot [:update, :destroy], Spree::Role, name: ['admin']  # case-sensitive, only catches lowercase 'admin'
```
A user with RoleManagement can create a role named `Admin` (bypassing case-sensitive protection) or create a `RoleUser` record linking anyone to the admin role.

### 5. CSRF Protection Disabled for Line Item Creation (CWE-352)
**File:** `storefront/app/controllers/spree/line_items_controller.rb:9`
```ruby
skip_before_action :verify_authenticity_token, only: :create
```
Cross-Site Request Forgery completely disabled for adding items to a cart.

### 6. State Parameter Injection in Checkout (CWE-20)
**File:** `storefront/app/controllers/spree/checkout_controller.rb:297-302`
```ruby
def set_state_if_present
  if params[:state] && params[:state] != 'complete'
    redirect_to ... if @order.can_go_to_state?(params[:state]) && !skip_state_validation?
    @order.state = params[:state]  # Assigned even if can_go_to_state? returns false!
  end
end
```
User-controlled `params[:state]` is assigned to the order's state, forcing it to any non-`'complete'` value, potentially bypassing state machine transitions.

### 7. No Strong Parameters in Contacts Controller (CWE-20)
**File:** `storefront/app/controllers/spree/contacts_controller.rb:11`
```ruby
@contact = Spree::Contact.new(params[:contact])
```
Raw user params passed to model constructor with zero filtering.

### 8. Digital Links Token-Only Access (CWE-639)
**File:** `storefront/app/controllers/spree/digital_links_controller.rb:36-38`
```ruby
def digital_link
  @digital_link ||= current_store.digital_links.find_by!(token: params[:id])
end
```
Any user with the token can download digital assets — no user ownership check.

### 9. Auto-Created OAuth Tokens Without Consent (CWE-287)
**File:** `core/lib/spree/core/controller_helpers/auth.rb:23-30`
```ruby
def current_oauth_token
  create_access_token = ->(user) { Spree::OauthAccessToken.create!(resource_owner: user) }
  @current_oauth_token ||= get_last_access_token.call(user) || create_access_token.call(user)
end
```
Any authenticated user silently gets a persistent OAuth token with no OAuth flow, no application, and no scopes.

### 10. Password Grant Without Client Authentication (CWE-287)
**File:** `api/config/initializers/doorkeeper.rb:8-10`
```ruby
skip_client_authentication_for_password_grant { true }
```
The code itself acknowledges this is a FIXME. Anyone can call the password grant with just username/password, no `client_id`/`client_secret`.

### Multiple Additional Issues (CWE-200, CWE-601, etc.)
