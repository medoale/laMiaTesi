### Title
**Mass Assignment of `user_id` Permits Order Ownership Transfer and Unauthorized Access**

### Affected Files

1. **`/work/core/lib/spree/permitted_attributes.rb`** (line 93–94): `user_id` listed in `@@checkout_attributes`
2. **`/work/core/lib/spree/core/controller_helpers/strong_parameters.rb`** (line 19–26): `permitted_checkout_attributes` includes `user_id`
3. **`/work/storefront/app/controllers/spree/checkout_controller.rb`** (line 45): Storefront checkout uses `permitted_checkout_attributes` in `update_from_params`
4. **`/work/api/app/controllers/spree/api/v2/storefront/checkout_controller.rb`** (line 42): API v2 checkout also passes `permitted_checkout_attributes`
5. **`/work/core/app/models/spree/order/checkout.rb`** (line 241–278): `update_from_params` permits `user_id` and calls `update(attributes)` which sets it

### Root Cause

`Spree::PermittedAttributes` defines `@@checkout_attributes` (line 92–96) as:

```ruby
@@checkout_attributes = [
  :coupon_code, :email, :shipping_method_id, :special_instructions, :use_billing, :use_shipping,
  :user_id, :bill_address_id, :ship_address_id, :accept_marketing, :signup_for_an_account, :currency,
  :internal_note
]
```

The attribute `:user_id` should **never** be a permitted checkout parameter. Associating an order with a user is an **authentication/authorization concern**, not a user-supplied parameter. The permitted list propagates into:

- **Storefront HTML checkout** (`Spree::CheckoutController#update`, line 45):
  ```ruby
  if @order.update_from_params(params, permitted_checkout_attributes, request.headers.env)
  ```

- **API v2 Storefront checkout** (`Spree::Api::V2::Storefront::CheckoutController#update`, line 38–44):
  ```ruby
  result = update_service.call(
    order: spree_current_order,
    params: params,
    permitted_attributes: permitted_checkout_attributes,
    request_env: request.headers.env
  )
  ```

Both paths ultimately reach `Spree::Order::Checkout#update_from_params` (line 249–272):

```ruby
attributes = if @updating_params[:order]
               @updating_params[:order].permit(permitted_params).delete_if { |_k, v| v.nil? }
             else
               {}
             end
# ...
success = update(attributes)
```

The `permit(permitted_params)` call allows `:user_id` because it's in the permitted list, and `update(attributes)` directly sets `user_id` on the order record with **no authorization check** beyond the generic `spree_authorize! :update` which only verifies the current user holds the order token, not that they're allowed to change ownership.

### Attack Scenario

**Prerequisites:** None (works for unauthenticated guest users).

**Step 1 — Create a guest cart:**
```
POST /api/v2/storefront/cart
→ 201 Created, returns token: "abc123"
```

**Step 2 — Add items (any guest, no authentication):**
```
POST /api/v2/storefront/cart/abc123/add_item?variant_id=1&quantity=1
```

**Step 3 — Begin checkout with arbitrary user_id:**
```
PATCH /api/v2/storefront/checkout/abc123
Authorization: Bearer abc123
Content-Type: application/json

{
  "order": {
    "user_id": 42,
    "email": "existing-user@example.com",
    "bill_address_attributes": {
      "firstname": "Attacker",
      "lastname": "Name",
      "address1": "123 Fake St",
      "city": "Anytown",
      "country_id": 1,
      "zipcode": "12345",
      "phone": "555-0000"
    },
    "ship_address_attributes": {
      "firstname": "Attacker",
      "lastname": "Name",
      "address1": "123 Fake St",
      "city": "Anytown",
      "country_id": 1,
      "zipcode": "12345",
      "phone": "555-0000"
    }
  }
}
```

**Result:** `order.user_id` is now `42`. The order has been silently transferred to user ID 42. There is **no validation** checking:
- That the current user's ID matches the provided `user_id`
- That `user_id` is a legitimate operation in this context
- That the requesting user has any relationship to the target user

**Step 4 — Privilege escalation:**
- If user 42 is logged in and visits their checkout, they see the attacker's items and addresses
- If user 42 proceeds through checkout, their **saved payment methods** and **saved addresses** become available on the attacker-created order (via `assign_default_credit_card` at line 302–307 of `/work/core/app/models/spree/order/checkout.rb`)
- The attacker's guest token (`abc123`) would also still work on the Storefront HTML checkout until `load_order` runs and detects the user mismatch

**Step 5 — Further vectors:**
- **Guest->user order frame-up:** Create an order with illicit items and attach it to a victim's user_id
- **User->user order hijacking:** If user 41 is logged in and has an ongoing cart, they could change `user_id` to 42. On the next request, `load_order` (checked at line 169–192 of the checkout controller) would compare user 41 (logged in) to 42 (on the order) and block access, but the damage is already done: the order now belongs to user 42 and user 41 continues to have access during the request lifecycle.
- **Bypass guest checkout restrictions:** Stores that disable guest checkout require login — by setting a `user_id` via mass assignment, the guest bypasses this restriction without actually authenticating as that user.

### The `load_order` Guard is Insufficient

The `load_order` method (checkout_controller.rb, line 150–210) checks `user_id` **only at request start**, before the `update` action runs. The injection happens **inside** `update_from_params` during the same request. So:

1. A guest order has `user_id = nil` at request start → `load_order` permits access
2. `update_from_params` sets `user_id = 42` mid-request → the change is persisted
3. The order completes the request now `user_id = 42`
4. On the *next* request, `load_order` detects the mismatch and blocks it, but by then the damage is done

### Recommended Fix

Remove `:user_id` from `@@checkout_attributes` in `/work/core/lib/spree/permitted_attributes.rb`:

```ruby
@@checkout_attributes = [
  :coupon_code, :email, :shipping_method_id, :special_instructions, :use_billing, :use_shipping,
  :bill_address_id, :ship_address_id, :accept_marketing, :signup_for_an_account, :currency,
  :internal_note
]
```

User-to-order association should only be set by:
- `@order.associate_user!(current_user)` during login/token association (already implemented at checkout_controller.rb line 207)
- `@order.associate_user!(try_spree_current_user)` in `load_order` (already implemented)
- The cart association flow in `Spree::Api::V2::Storefront::CartController`

These existing code paths already handle user association correctly. The `:user_id` mass assignment parameter undermines them all.
