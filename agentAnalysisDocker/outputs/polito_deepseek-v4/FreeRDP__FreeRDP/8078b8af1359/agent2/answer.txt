## Analysis of All Changes

The changes are in FreeRDP's SSPI (Security Support Provider Interface) implementation across five security packages: CredSSP, Kerberos, NTLM, Negotiate, and Schannel.

### The Common Pattern

All changes move the call to `sspi_SecureHandleInvalidate(phCredential)` or `sspi_SecureHandleInvalidate(phContext)` to **before** the null check on the retrieved pointer (or before freeing the underlying object). This is the critical security fix.

**Key insight about `sspi_SecureHandleGetLowerPointer`:** It decodes the pointer from `dwLower` using bitwise NOT (`~`), and returns `nullptr` if `dwLower` is 0. Meanwhile, `sspi_SecureHandleInvalidate` sets `dwLower = 0` and `dwUpper = 0`.

### Why This Fixes a Use-After-Free / Double-Free Vulnerability

Consider the **before** code pattern (using `creadssp_FreeCredentialsHandle` as example):
```c
static SECURITY_STATUS SEC_ENTRY credssp_FreeCredentialsHandle(PCredHandle phCredential)
{
    SSPI_CREDENTIALS* credentials = nullptr;
    if (!phCredential)
        return SEC_E_INVALID_HANDLE;
    credentials = (SSPI_CREDENTIALS*)sspi_SecureHandleGetLowerPointer(phCredential);
    if (!credentials)
        return SEC_E_INVALID_HANDLE;
    sspi_CredentialsFree(credentials);  // Frees the memory
    return SEC_E_OK;  // BUT the handle is NOT invalidated!
}
```

After `sspi_CredentialsFree(credentials)` is called, the `SecHandle` still points to the now-freed memory via its `dwLower` field (encoded). If another call is made using the same handle (e.g., a second call to `FreeCredentialsHandle`, or any API call that reads the lower pointer), `sspi_SecureHandleGetLowerPointer` will decode the stale pointer and return freed memory — a classic **use-after-free** vulnerability, or if `FreeCredentialsHandle` is called twice, a **double-free**.

## Summary

This commit fixes a **use-after-free** vulnerability across five SSP (Security Support Provider) packages in FreeRDP/WinPR's SSPI implementation. In the vulnerable (before) code, when `FreeCredentialsHandle` or `DeleteSecurityContext` is called, the underlying credential/context memory is freed but the `SecHandle` structure (`dwLower`/`dwUpper` fields) is **not** invalidated. This means:

1. A subsequent call to any function that dereferences the handle will decode the stale pointer from `dwLower` and access freed memory (use-after-free).
2. Double calls to `FreeCredentialsHandle` or `DeleteSecurityContext` on the same handle would double-free the same memory.

The fix adds calls to `sspi_SecureHandleInvalidate()` (which zeroes out `dwLower` and `dwUpper`) **before** or at the point of freeing the underlying object, ensuring the handle cannot be used to reach freed memory.

The exact vulnerable files/functions (before fix):
- `winpr/libwinpr/sspi/CredSSP/credssp.c`: `credssp_FreeCredentialsHandle`
- `winpr/libwinpr/sspi/Kerberos/kerberos.c`: `kerberos_DeleteSecurityContext`, and error cleanup paths in `kerberos_InitializeSecurityContextA` / `kerberos_AcceptSecurityContext`
- `winpr/libwinpr/sspi/NTLM/ntlm.c`: `ntlm_FreeCredentialsHandle`, `ntlm_DeleteSecurityContext`
- `winpr/libwinpr/sspi/Negotiate/negotiate.c`: `negotiate_DeleteSecurityContext`, `negotiate_FreeCredentialsHandle`
- `winpr/libwinpr/sspi/Schannel/schannel.c`: `schannel_FreeCredentialsHandle`, `schannel_DeleteSecurityContext`
