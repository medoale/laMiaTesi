### What the change does

Every changed function adds a call to **`sspi_SecureHandleInvalidate(phCredential)`** or **`sspi_SecureHandleInvalidate(phContext)`** at a specific point:

1. **Before the null-pointer check** on the retrieved pointer — so the handle is invalidated even on early-return paths (e.g., if the retrieved pointer is `NULL`)
2. **Before the underlying object is freed** (`sspi_CredentialsFree`, `credentials_unref`, `kerberos_ContextFree`, `ntlm_ContextFree`, etc.)

In the **before** code, the handle was left in a valid state pointing to freed (or freed-and-reallocated) memory after the cleanup function returned successfully. In some cases (file_02), the invalidation happened *after* the free, leaving a window where the handle was valid but the backing memory was already gone.

### Why it's a security fix

The `PCredHandle`/`PCtxtHandle` structure contains pointers to the underlying credential or context object. When that object is freed but the handle is **not invalidated**, any subsequent call to other SSPI functions using that stale handle will dereference freed memory. This is a classic **Use After Free** vulnerability:

- An attacker could potentially force a handle to be freed while retaining a copy
- After freeing, the handle still looks valid (pointers not zeroed out)
- Passing the handle to another SSPI function dereferences the stale pointer → **crash or exploitation**

Moving the invalidation *before* the null check also ensures the handle is zeroed out even if the internal object pointer is `NULL` (e.g., corrupted state), providing defense-in-depth.

### CWE Classification

- **CWE-416 (Use After Free)** — The handle contains pointers to freed memory; dereferencing it constitutes a use-after-free condition.
