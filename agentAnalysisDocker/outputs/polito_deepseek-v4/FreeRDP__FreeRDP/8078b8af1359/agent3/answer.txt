## Summary

I found a path traversal vulnerability in the FreeRDP drive channel's `contains_dotdot()` function at `/work/channels/drive/client/drive_file.c` (line 93).

**The Bug**: The `contains_dotdot()` function is meant to prevent `..` path traversal sequences in file paths received from the RDP server. However, it fails to detect `..` sequences under two conditions:

1. **When `..` appears at the end of the suffix path** (no trailing `/` or `\` after `..`): The check at line 111 (`tst + 2 < path + path_length`) is false when `..` is at the very end of the path, causing the inner `tst[2]` check to be skipped entirely.

2. **When `..` appears at the start of the suffix and the base_path doesn't end with `/`**: Line 109 checks `*(tst - 1) == '/'` when `tst` points to the beginning of the suffix. This reads the last character of the base_path instead, which is typically a non-separator character, causing the entire condition to be false and the inner check block to be skipped.

**Impact**: A malicious RDP server can craft file operation requests (CreateFile, CreateDirectory, Rename, QueryDirectory) with paths like `../foo` or `..` as the suffix. These bypass the `contains_dotdot` check and reach OS filesystem APIs (`CreateFileW`, `CreateDirectoryW`, `MoveFileExW`, `FindFirstFileW`) which resolve the `..` path component, allowing the server to read, write, create, and delete files outside the intended shared directory on the client's machine.

**Example**: If the shared drive is `/home/user/Shared` and the server sends a CreateFile request with path `../malicious.exe`, the resulting path `/home/user/Shared/../malicious.exe` resolves to `/home/user/malicious.exe`, allowing the malicious server to write files outside the shared directory.
