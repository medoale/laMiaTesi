## Analysis

**File:** `crypto/vm/tonops.cpp` (TON Blockchain Virtual Machine opcode implementations)

**The change:** A single null-check guard is added to the `exec_get_in_msg_param` function. After calling `get_param(st, inmsgparams_idx).as_tuple()`, the result `t` is now checked for null before being passed to `tuple_index(t, idx)`.

**The vulnerability (before the fix):** The function `exec_get_in_msg_param` retrieves an element from the c7 register tuple at index `inmsgparams_idx` (17) via `get_param(st, inmsgparams_idx).as_tuple()`. If that element does not exist or is not a tuple, `as_tuple()` returns a **null `Ref<Tuple>`**. The code then immediately calls `tuple_index(t, idx)` on this null reference, causing a **NULL pointer dereference** — undefined behavior (typically a crash or memory corruption).

**Why this is a security vulnerability:** This code runs inside the TON Virtual Machine (TVM) when executing smart contracts. An attacker can craft a transaction with a malformed c7 register (specifically, making element 17 null or non-tuple) that triggers one of the INMSG_* opcodes (`INMSG_BOUNCE`, `INMSG_BOUNCED`, `INMSG_SRC`, etc. — all 11 opcodes bind to this function). This causes the validator node to crash or enter an undefined state, constituting a **denial of service** attack against blockchain validators.

**Evidence of the pattern:** Many similar functions in the same file already have identical null checks (e.g., `get_param` on line 122-124, `get_unpacked_config_tuple` on lines 132-139, `get_prev_blocks_info` on lines 264-270), confirming this was an oversight that left a null-dereference path exploitable before the fix.
