## Final Security Review Findings

### Vulnerability Found: CRLF Injection in HTTP Header Handling (CWE-113)

**Location:** `/work/http/http.cpp`

**Affected functions:**
- `get_header()` (line 67–73): Parses raw HTTP header lines by splitting on `:` and trimming the value portion. **No CR/LF validation is performed.**
- `HttpRequest::add_header()` (line 183–223): Stores a parsed header into a request object. **No CR/LF validation is performed.**
- `HttpResponse::add_header()` (line 793–828): Stores a parsed header into a response object. **No CR/LF validation is performed.**
- `HttpHeader::store_http()` (line 77–82): Serializes the header by appending `name`, `: `, `value`, `\r\n` **verbatim** with no sanitization.

**Existing but unused validation:**
- `HttpHeader::basic_check()` (line 861–873): Correctly rejects CR, LF, space, tab, and colon in header names; rejects CR and LF in header values. **However, this function is never called from any code path in the `http/` directory.** It is only called from `rldp-http-proxy/rldp-http-proxy.cpp` (3 call sites at lines 277, 518, 1213).

**Attack chain:**
1. An attacker sends an HTTP request (or a backend server returns an HTTP response) with a header value containing CRLF characters — e.g., `Foo: bar\r\nInjected-Header: malicious\r\n`
2. `get_header()` splits on the first `:` and stores `"Foo"` / `"bar\r\nInjected-Header: malicious"` without any CRLF check
3. `add_header()` stores this into the request/response object without any CRLF check
4. When `store_http()` serializes the response back to the client, it writes the unsanitized value verbatim — the embedded CRLF sequences split the HTTP response, allowing the attacker to inject arbitrary HTTP headers and body content
5. This enables HTTP response splitting, which can lead to cache poisoning, cross-site scripting, and request smuggling

**Impacted components:** The in-tree HTTP server (`HttpServer` → `HttpInboundConnection` → `send_answer()` → `response->store_http()`) and the HTTP proxy (`http-proxy.cpp`) both forward unsanitized headers. Only the RLDP-HTTP proxy is protected via its own local `basic_check()` calls.

**Exploitability:** The HTTP proxy listens on a configurable port and accepts connections from arbitrary clients. An attacker who controls (or man-in-the-middles) the upstream backend server can return crafted response headers with CRLF injection, poisoning the client connection through the proxy.

**Impact:** HTTP response splitting → cache poisoning, XSS, and HTTP request smuggling against backend servers.

**Fix:** Call `HttpHeader::basic_check()` inside `get_header()` (line 72 of `http.cpp`) after constructing the `HttpHeader` but before returning it, or inside both `add_header()` implementations.
