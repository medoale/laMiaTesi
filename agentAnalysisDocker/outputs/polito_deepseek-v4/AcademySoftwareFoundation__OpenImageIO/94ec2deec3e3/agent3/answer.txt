### Key Vulnerability in IFF Parser

The `IffInput::readimg()` function does this:
```cpp
// line 575
m_buf.resize(m_header.image_bytes());  // raw multiplication: pixel_bytes * width * height

// line 656-657 (in tile processing loop)
uint8_t* out_dy = m_buf.data()
                  + (py * m_header.width) * m_header.pixel_bytes();
                  // ^--- py is uint16_t (65535 max), width is uint32_t
                  //     32-bit overflow possible if width > 65537
```

While `image_bytes()` on 64-bit uses 64-bit `size_t` (so the allocation is correctly sized for the claimed image), the pointer offset calculation `(py * width)` uses **32-bit arithmetic** that can wrap when `width > 65537`. This causes writes at wrong offsets within the buffer — a form of data corruption. On 32-bit builds, both the allocation and the offset use 32-bit arithmetic, creating a more serious overflow scenario (small allocation + out-of-bounds writes).

These validate width/height against configurable limits and prevent oversized allocations.

#### 2. ❌ **Missing `check_open()`** — critical gap in these parsers:
- **IFF** — `uint32_t` width/height with **raw multiplication** in `IffFileHeader::image_bytes()`, `scanline_bytes()`, and pointer offset calculations ← **Potential CWE-190**
- **JPEG2000** — `int` width/height with **raw multiplication** in `bufsize = w * h * ch * buffer_bpp` ← **Confirmed CWE-190 → CWE-122**
- DDS — `uint32_t` width/height, but uses safe `ImageSpec::scanline_bytes()` for sizing
- PSD — complex structs, needs deeper analysis
- GIF — `int` width from giflib (bounded by uint16_t in practice)

- FITS — uses safe `m_spec.scanline_bytes()`
- DICOM — uses safe `m_spec.scanline_bytes()`
- WebP — wraps libwebp
- HEIF — wraps libheif
- R3D — wraps R3DSDK

#### 3. 🔴 **CRITICAL: JPEG2000 Parser Integer Overflow → Heap Buffer Overflow** (CWE-190 → CWE-122)
- **File**: `/work/src/jpeg2000.imageio/jpeg2000input.cpp` line 395
- **Code**: `const int bufsize = w * h * ch * buffer_bpp;`
- **Problem**: All four operands are `int` (32-bit signed). An attacker crafts a JPEG2000 codestream with dimensions such as 32769×32768×4×1 byte → true product = 4,295,098,368 bytes → `int` overflows to **131,072 bytes**. `m_buf.resize(131072)` succeeds, but `ojph_read_image()` then writes the full pixel data (~4 GB) into this tiny buffer, resulting in **massive heap buffer overflow**.
- **No `check_open()` call** — dimensions are read from the codestream's SIZ marker without any upper limit validation.

#### 4. 🟡 **IFF Parser Potential Integer Overflow** (CWE-190)
- 32-bit overflow in pointer offset calculation `(py * m_header.width)` for widths > 65537
- On 64-bit: data corruption (wrong pixel positions), not OOB (buffer is sized correctly)
- On 32-bit: could lead to heap overflow when `image_bytes()` overflows uint32_t
