## Security Analysis

I have thoroughly analyzed the commit diff and the repository code. This is a DDS (DirectDraw Surface) image file parser in OpenImageIO. The commit makes several interrelated changes that fix a security vulnerability.

### Changes identified:

**1. Integer type widening: `int`/`unsigned int` → `size_t`** across the entire file:
- `internal_seek_subimage()`: `unsigned int& w,h,d` → `size_t& w,h,d`; `unsigned int ofs, len` → `size_t ofs, len`
- `internal_readimg()`: `int w,int h,int d` → `size_t w,size_t h,size_t d`
- Loop counters and local variables throughout

**2. Offset calculation overflow fix in `read_native_scanline()`** (line 1036 before → line 1061 after):
```cpp
// BEFORE (line 1036):
memcpy(data, &m_buf[0] + z * m_spec.height * size + y * size, size);
// AFTER (line 1061):
size_t offset = size_t(z) * m_spec.height * size + size_t(y) * size;
memcpy(data, &m_buf[0] + offset, size);
```

**3. Added dimension validation via `check_open()` in `seek_subimage()`** (lines 906-933 after):
- Cube maps: limits to 16384 per face, checks square aspect
- Volume textures: limits to 4096×4096×4096
- 2D textures: limits to 32768×32768

### Why this is a security vulnerability fix:

**Primary vulnerability — Integer overflow to out-of-bounds memory access (CWE-680/CWE-190):**

In `read_native_scanline()`, the expression `z * m_spec.height` multiplies two `int` values using 32-bit signed arithmetic. A crafted DDS file can specify dimensions (stored as `uint32_t` in the header, assigned to `int` `ImageSpec::height`) large enough that `z * m_spec.height` overflows `INT_MAX` (2,147,483,647). The overflowed (typically negative) `int` result is then promoted to `size_t` and used as a pointer offset in `memcpy`, causing an out-of-bounds memory read from an arbitrary location relative to the buffer. This can leak sensitive memory or crash the process.

Similarly, in `internal_seek_subimage()`, `w * h * d * m_Bpp` is performed in 32-bit unsigned arithmetic (`unsigned int`). With large enough dimensions, this wraps modulo 2³², producing an incorrect file offset. The subsequent `ioseek(ofs, SEEK_SET)` then reads attacker-controlled data from a wrong file position, leading to out-of-bounds writes into the destination pixel buffer via subsequent decompression/copy operations.

**Defense-in-depth — Dimension validation:**
The `check_open()` calls add bounds checking (e.g., 2D textures limited to 32768×32768). This constrains the input so that even without the type fix, the overflow conditions would be harder to trigger. It also prevents memory exhaustion attacks.

### Classification:

The most specific CWE is **CWE-680: Integer Overflow to Buffer Overflow**, since the integer overflows directly cause out-of-bounds memory access. The root mechanism is **CWE-190: Integer Overflow or Wraparound**. Both genuinely apply — CWE-680 is the specific child pattern of CWE-190.
