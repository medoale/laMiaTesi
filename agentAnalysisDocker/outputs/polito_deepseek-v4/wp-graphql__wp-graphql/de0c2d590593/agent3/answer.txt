## Evidence

The vulnerability exists in `/work/plugins/wp-graphql-smart-cache/src/Document.php`, method `save()` (lines 413–472).

### Attack Flow

1. An unauthenticated attacker sends a POST request to `/graphql` with `Content-Type: application/json` and a body containing both `query` and `queryId` parameters:
   ```json
   {
     "query": "query MyQuery { posts { nodes { id title } } }",
     "queryId": "my-custom-alias"
   }
   ```

2. **No authentication barrier.** In `Router::validate_http_request_authentication()` (line 658), the check `if ( ! is_user_logged_in() )` returns `null` (no error) for unauthenticated users — the function explicitly skips CSRF validation for guests.

3. Processing reaches `WPHelper::parseRequestParams()` (line 65), which fires `apply_filters( 'graphql_request_data', $parsed_body_params, $request_context )`.

4. The `Document::graphql_query_contains_query_id_cb()` callback (line 206) detects both `query` and `queryId` are present and calls `$this->save( $parsed_body_params[ $query_id_key ], $parsed_body_params['query'] )` (line 214).

5. **No capability check.** `save()` calls `wp_insert_post()` (line 447) with `post_status => 'publish'` and `post_type => 'graphql_document'`. There is **no** `current_user_can()` or equivalent authorization call. The `wp_insert_post()` function itself does not enforce user capabilities — that responsibility is left to the caller. (Compare with the WPGraphQL mutation path at `PostObjectCreate.php` line 244, which explicitly checks `current_user_can($post_type_object->cap->create_posts)` — proving the developers understood this check is necessary.)

6. A published `graphql_document` post is created, and its hash + the user-supplied alias are added as terms on the `graphql_query_alias` taxonomy via `wp_add_object_terms()` (line 469) — also without any capability check.

### Impact

- **Allow-list bypass:** If the site admin configures the "Allow/Deny Mode" setting to `only_allowed` (Grant::GLOBAL_ALLOWED), the `AllowDenyQueryDocument` validation rule (line 74–91) blocks any query not found in the persisted list. However, an attacker can **pre-register their own queries** using this unauthenticated `save()` path, then execute them freely through the allow-list.
- **Unauthorized persisted query creation:** Any visitor can create persisted GraphQL documents of type `graphql_document`.
- **Unauthorized taxonomy term creation:** Terms on `graphql_query_alias` are created without `manage_categories` or `edit_posts` capability.
- **Resource exhaustion:** Unlimited `graphql_document` posts can be created.

### No Prior Authorization Check

Contrast with the **GraphQL mutation path** (`createGraphqlDocument`):
- `PostObjectCreate::mutate_and_get_payload()` line 244: `current_user_can( $post_type_object->cap->create_posts )`
- This throws `UserError` if the user lacks `edit_posts` capability.

But the `save()` method (triggered via the `graphql_request_data` filter) bypasses **both** the mutation capability check and the GraphQL validation layer entirely, running before the GraphQL operation is even parsed or executed.
