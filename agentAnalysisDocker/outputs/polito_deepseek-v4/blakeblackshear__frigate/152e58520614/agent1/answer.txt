## Analysis

This commit touches **12 files** across a full-stack application (Frigate NVR). The changes fix **multiple security vulnerabilities**:

### 1. CWE-620: Unverified Password Change (Most critical)
**Before:** The `PUT /users/{username}/password` endpoint (`file_02`, line 785-788) allowed any authenticated user (including "viewer" role) to change a password — including their own — **without providing the current password**. Viewers were only blocked from changing *other* users' passwords. The code simply called `hash_password(body.password)` and `User.set_by_id(username, {User.password_hash: password_hash})` with zero verification of the old password.

**After:** The endpoint now requires `old_password` verification when:
- Any user changes their own password
- A non-admin changes any password

Only an admin changing *another* user's password can bypass this. The API body model (`file_03`) and frontend (`file_11`) all enforce this.

### 2. CWE-613: Insufficient Session Expiration
**Before:** JWT tokens contained no `iat` (issued-at) claim, and the User model had no `password_changed_at` field. After a password change, existing (potentially stolen) JWT tokens continued to work and could be refreshed freely until they expired (up to 24 hours by default).

**After:** 
- JWT encoding now includes `iat: int(time.time())` (file_02, line 389)
- User model adds `password_changed_at = DateTimeField(null=True)` (file_05), with a database migration (file_07)
- During JWT refresh, `token_iat` is compared against `password_changed_at` — tokens issued before the password change are rejected (file_02, lines 654-670)

### 3. CWE-732: Incorrect Permission Assignment for Critical Resource
**Before:** The JWT secret file was written with plain `open(jwt_secret_file, "w")` which uses default umask-dependent permissions (potentially world-readable) and could follow symlinks.

**After:** Uses `os.open()` with `O_WRONLY | O_CREAT | O_EXCL, 0o600` — creating the file with owner-only read/write permissions and preventing symlink attacks via `O_EXCL` (file_02, lines 314-318).

### 4. CWE-521: Weak Password Requirements
**Before:** No password strength validation existed on either backend or frontend.

**After:** Backend `validate_password_strength()` enforces minimum 8 chars, uppercase, digit, and special character (file_02, lines 362-383). Frontend `SetPasswordDialog` validates the same requirements client-side and shows requirements checklist (file_11).

Additional hardening includes: reducing JWT refresh window from 12 hours to 30 minutes (`file_01`, `file_04`), making logout publicly accessible so users can clear cookies even with expired tokens (file_02, line 706), and issuing a fresh JWT after self-password change (file_02, lines 869-882).

**Conclusion:** Yes, this commit is a security vulnerability fix addressing multiple CWEs.
