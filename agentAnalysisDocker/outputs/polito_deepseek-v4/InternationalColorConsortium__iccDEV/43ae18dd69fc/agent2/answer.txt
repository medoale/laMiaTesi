### Overview

### File 01: `IccTagLut.cpp` — `CIccCLUT::Init` (single-value overload)

**Before:**
```cpp
bool CIccCLUT::Init(icUInt8Number nGridPoints, icUInt32Number nMaxSize, icUInt8Number nBytesPerPoint)
{
    memset(&m_GridPoints, 0, sizeof(m_GridPoints));
    if (m_nInput > 16) return false;
    memset(m_GridPoints, nGridPoints, m_nInput);     // sets all dims to nGridPoints
    return Init(&m_GridPoints[0], nMaxSize, nBytesPerPoint);
}
```

**After:** adds `if (nGridPoints < 2) return false;` before the `memset`.

The pointer-based second overload already contains `if (pGridPoints[i] < 2) return false;`, so this change is **defense-in-depth** — it fails early rather than propagating an invalid grid-point count through `memset` and into the second overload. It does not fix a new independently exploitable vulnerability, but it's part of the same hardening theme.

### File 02: `iccFromCube.cpp` — Parsing and table construction

This file contains the real security fixes. Three distinct issues are addressed:

#### 1. Integer overflow in `m_sizeLut3D * m_sizeLut3D * m_sizeLut3D` (CWE-190)

**Before** (`parse3DTable`, line 218):
```cpp
icUInt32Number num = m_sizeLut3D * m_sizeLut3D * m_sizeLut3D;
```
`m_sizeLut3D` is a signed `int`. Multiplying three signed `int` values can overflow — signed overflow is **undefined behavior** in C++. Even treating the result as unsigned 32-bit, for values above ~1626 the product exceeds 2³²−1, wrapping to a small incorrect number. This `num` value controls the loop iterations that write into the destination buffer.

**After:** uses `uint64_t` multiplication with an explicit overflow check:
```cpp
uint64_t temp = (uint64_t)m_sizeLut3D * (uint64_t)m_sizeLut3D * (uint64_t)m_sizeLut3D;
if (temp > UINT_MAX) return false;
icUInt32Number num = (icUInt32Number)temp;
```

#### 2. Improper input validation (CWE-20)

**Before** (parsing `LUT_3D_SIZE`, line 147):
```cpp
m_sizeLut3D = atoi(line.c_str() + 12);
```
`atoi` returns an `int` with no range checking. It accepts negative values (`-5`) and silently truncates values beyond `INT_MAX`. The only subsequent check is `if (!cube.sizeLut3D())`, which rejects `0` but passes negative numbers (truthy). The fix uses `atoll` and validates `temp >= INT_MAX || temp <= 0`.

Additionally, `parse3DTable` in the before code had no guard against `m_sizeLut3D < 2` or `nSizeLut <= 0` — only a check for `m_sizeLut3D == 0`.

#### 3. Unchecked return value (CWE-252)

**Before** (main, lines 409–410):
```cpp
pCLUT->Init(cube.sizeLut3D());    // return value discarded!
bool bSuccess = cube.parse3DTable(pCLUT->GetData(0), pCLUT->NumPoints()*3);
```
If `Init` fails (e.g. due to truncation of a large `m_sizeLut3D` to `uint8_t` → 0, or by passing `nGridPoints < 2`), `m_pData` is `NULL`. `GetData(0)` returns `&NULL[0]` = `NULL`, and `parse3DTable` dereferences it — a **null pointer dereference** (crash). The fix checks the return value of `Init` and exits early.

Furthermore, in the before code, `pMpeCLUT->SetCLUT(pCLUT)`, `pTag->Attach(pMpeCLUT)`, and `profile.AttachTag(...)` all execute **before** the `bSuccess` check, attaching a failed/incomplete LUT to the profile before detecting the error. The fix moves the failure checks before these operations.

### Vulnerability Classification

| Issue | CWE |
|---|---|
| Integer overflow in `m_sizeLut3D^3` multiplication and `atoi` parsing | **CWE-190** (Integer Overflow or Wraparound) |
| Missing input validation on `LUT_3D_SIZE` parsed value | **CWE-20** (Improper Input Validation) |

The most specific CWE for the core problem is **CWE-190**: the 32-bit multiplication `m_sizeLut3D * m_sizeLut3D * m_sizeLut3D` wraps around, producing a loop count (`num`) that disagrees with the actual buffer allocation. This is a textbook integer overflow that can lead to undersized allocation and subsequent heap buffer overflow during the loop's write operations. The `atoi`→`atoll` change and the bounds check on the parsed value are secondary input-validation fixes (CWE-20) that prevent the overflow from being reachable in the first place.
