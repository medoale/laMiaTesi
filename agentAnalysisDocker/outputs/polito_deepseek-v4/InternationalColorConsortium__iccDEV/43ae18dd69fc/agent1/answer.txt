## File 02: iccFromCube.cpp

**Diff:**
1. Added `#include <climits>`
2. Changed `m_sizeLut3D = atoi(...)` to `int64_t temp = atoll(...)` with bounds check `temp >= INT_MAX || temp <= 0`
3. Added size validation `m_sizeLut3D < 2 || nSizeLut <= 0` check
4. Changed multiplication `m_sizeLut3D * m_sizeLut3D * m_sizeLut3D` (32-bit) to use `uint64_t` with overflow check: `if (temp > UINT_MAX) return false`
5. Changed `!m_sizeLut3D` to the more comprehensive check
6. Moved the error handling for `!bSuccess` to earlier, before the tag is attached, preventing use of a partially-initialized LUT.

The core vulnerability here is **integer overflow**. The original code did `m_sizeLut3D * m_sizeLut3D * m_sizeLut3D` as a 32-bit `int` multiplication, then assigned it to an `icUInt32Number`. A carefully crafted Cube file with a large `LUT_3D_SIZE` value (e.g., 1625, since 1625³ ≈ 4.29 billion > 2³²) would cause integer overflow, wrapping the result to a small value. This small value would bypass the `nSizeLut != num*3` check, leading to a buffer over-read (the code would read far more data into the `toLut` buffer than actually fits). This is **CWE-190 (Integer Overflow or Wraparound)** leading to **CWE-119 (Buffer Overflow)** — specifically a heap buffer overflow.

Note this is a `memset` — it sets bytes, not array elements! If `nGridPoints = 0`, all bytes become 0, which means `m_GridPoints[i] = 0` for all `i`, and the second overload would catch `0 < 2`. Hmm, but wait — `m_GridPoints` is `icUInt8Number` (array of unsigned chars), and `memset` sets each *byte* in memory. Since `icUInt8Number` is 1 byte, setting each byte to `nGridPoints` would work as expected. So yes, the second overload catches this.

So file_01 is really just a minor hardening/defense-in-depth change, not fixing a vulnerability that was reachable.

**File 02, however, is clearly fixing a security vulnerability.** The original code:
1. Uses `atoi` which truncates a large value to `int`, then assigns to `int m_sizeLut3D`. If the Cube file specifies `LUT_3D_SIZE 2000000000`, `atoi` returns it as `int`, which then gets cubed in 32-bit, overflowing and producing a small number.
2. The overflow in `m_sizeLut3D * m_sizeLut3D * m_sizeLut3D` (32-bit) could produce a small value that passes the `nSizeLut != num*3` check, while the actual number of entries in the file is much larger, leading to reading past the end of the `toLut` buffer (heap buffer overflow).

The fix uses `atoll` (64-bit), checks bounds against `INT_MAX`, does multiplication in 64-bit, and checks for overflow against `UINT_MAX`.

This is an integer overflow (CWE-190) leading to a heap buffer overflow (CWE-122 / CWE-119).
