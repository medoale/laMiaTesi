## Analysis

This commit adds **step-level settings** (`amendment_creation_enabled`, `amendment_reaction_enabled`, `amendment_promotion_enabled`) to the Decidim amendments feature, replacing a coarse global toggle with granular per-step controls. The core security fix is in the authorization layer:

**Before the fix** — The `amend_action?` method in `decidim-core/app/permissions/decidim/permissions.rb` unconditionally allowed `:create`, `:reject`, `:promote`, and `:accept` actions on the `:amendment` subject, with **no check** on whether:
- `amendments_enabled` was actually set to `true` at the component level
- The step-level settings permitted the specific action

Combined with the controller's `enforce_permission_to` calls that did **not** pass `current_component:` context, the permission system could not even access the component settings to perform such checks even if they existed. This meant any authenticated user could directly POST to the API endpoints to create, accept, reject, or promote amendments regardless of how the component was configured.

**After the fix** — The permission method:
1. Returns `disallow!` unless `component.settings.amendments_enabled` is true
2. Checks `component.current_settings.amendment_creation_enabled` for `:create`
3. Checks `component.current_settings.amendment_reaction_enabled` for `:accept`/`:reject`
4. Checks `component.current_settings.amendment_promotion_enabled` for `:promote`

The controller now passes `current_component: @form.component`, and a `component` method was added to the form base class. The helper methods were also updated to gate UI buttons behind the same checks.

This is a textbook **Missing Authorization** (CWE-862) vulnerability: the authorization checks were completely absent for these actions. No other CWE applies — the remaining changes (CSS styling, cell refactoring, i18n, test updates) are supporting infrastructure for this feature and are not independently security-relevant.
