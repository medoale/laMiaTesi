## Analysis

This commit spans 24 files and adds granular amendment feature settings (`amendment_creation_enabled`, `amendment_reaction_enabled`, `amendment_promotion_enabled`) to the Proposals component's step-level configuration in what is clearly the **Decidim** participatory democracy framework.

### The security vulnerability

The core security fix is concentrated in **file_09** and **file_13**:

**File 13 — `Permissions` class (`amend_action?` method)**

**Before** (lines 83-92):
```ruby
def amend_action?
  return unless permission_action.subject == :amendment
  return allow! if permission_action.action == :create
  return allow! if permission_action.action == :reject
  return allow! if permission_action.action == :promote
  return allow! if permission_action.action == :accept
  amendment = context.fetch(:amendment, nil)
  toggle_allow(amendment&.amender == user)
end
```

The permission system **unconditionally allowed** all four amendment operations (`create`, `reject`, `promote`, `accept`) regardless of whether the component's settings had those features enabled. No check on `amendments_enabled` (a global setting that already existed), and no check on any step-level sub-settings.

**After** (lines 83-98):
```ruby
def amend_action?
  return unless permission_action.subject == :amendment
  return disallow! unless component.settings.amendments_enabled

  case permission_action.action
  when :create
    return allow! if component.current_settings.amendment_creation_enabled
  when :accept,
      :reject
    return allow! if component.current_settings.amendment_reaction_enabled
  when :promote
    return allow! if component.current_settings.amendment_promotion_enabled
  end

  amendment = context.fetch(:amendment, nil)
  toggle_allow(amendment&.amender == user)
end
```

Now the permission system:
1. Refuses all amendment operations if the global `amendments_enabled` setting is false.
2. Checks `amendment_creation_enabled` before allowing creation.
3. Checks `amendment_reaction_enabled` before allowing accept/reject.
4. Checks `amendment_promotion_enabled` before allowing promotion.

**File 09 — `AmendmentsController`**

**Before**: `enforce_permission_to` calls did not pass `current_component`, so the permission system had no access to the component context to check its settings.

**After**: All four endpoints now pass `current_component: @form.component`, supplying the necessary component context for the permission checks in file_13.

**File 10** adds the `component` method to the form object so that `@form.component` is available.

### Why this is a security fix

The component already had settings intended to control whether amendments could be created, accepted/rejected, or promoted. However, these settings were **not enforced server-side**. Only the UI layer (buttons, links) might have hidden these operations, but a malicious user who knew the API endpoints could craft direct HTTP requests to:

- Create amendments even when `amendment_creation_enabled` was off
- Accept/reject amendments even when `amendment_reaction_enabled` was off
- Promote amendments even when `amendment_promotion_enabled` was off
- Perform any amendment operation even when `amendments_enabled` was off globally

This is a textbook **Missing Authorization** vulnerability: the intended authorization policy (based on component settings) was simply never checked.

### Classification

**CWE-862: Missing Authorization** — The software does not perform an authorization check when an actor attempts to perform an action. Here, the amendment feature settings existed but were never consulted by the authorization logic, allowing bypass of the intended restrictions.

No other CWE applies more specifically. This is not CWE-863 (Incorrect Authorization) because the check wasn't flawed — it was entirely absent for this dimension of the policy.
