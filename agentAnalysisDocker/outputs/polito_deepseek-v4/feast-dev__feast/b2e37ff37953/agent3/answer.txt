## Findings Summary

### 1. Path Traversal — `/read-document` endpoint (CWE-22)
**File:** `sdk/python/feast/feature_server.py`, lines 385–398

The HTTP endpoint `POST /read-document` accepts a user-supplied `file_path` and reads it directly from the filesystem with **no path sanitization whatsoever**. There is no check against the working directory, no traversal blocking, and no allowlist. Any file on the server can be read — `/etc/passwd`, `/proc/self/environ`, configuration files, private keys, etc.

```python
@app.post("/read-document")
async def read_document_endpoint(request: ReadDocumentRequest):
    # ...
    if not os.path.exists(request.file_path):
        return {"error": f"File not found: {request.file_path}"}
    with open(request.file_path, "r", encoding="utf-8") as file:
        content = file.read()
    return {"content": content, "file_path": request.file_path}
```

### 2. Path Traversal — `/save-document` endpoint (CWE-22)
**Files:** `feature_server.py` lines 400–418, `ui_server.py` lines 85–103

These endpoints take a user-supplied `file_path` and write a JSON labels file derived from it. Although there is a check ensuring the resolved path starts with `os.getcwd()`, a determined attacker may bypass this restriction via symlinks within the working directory, enabling arbitrary file writes within the repository scope.

### 3. Insecure Deserialization via `dill.loads()` (CWE-502)
**Multiple files across the codebase**

The `dill` library is a superset of `pickle`, and `dill.loads()` can execute arbitrary Python code during deserialization. It is used in production code to deserialize user-defined transformation functions from protobuf registry data without any integrity verification:

| `transformation/pandas_transformation.py` | 150 |
| `stream_feature_view.py` | 276 |
| `dqm/profilers/ge_profiler.py` | 158 |
| `infra/common/serde.py` | 36 |
| `transformation/substrait_transformation.py` | 163 |
| `infra/compute_engines/ray/nodes.py` | 527 |
| `infra/offline_stores/contrib/ray_offline_store/ray.py` | 1991 |

An attacker who can inject malicious serialized data into the registry (via `feast apply` or by compromising the registry backend) can achieve **arbitrary remote code execution** when the deserialization occurs.

### 4. Unsafe YAML Deserialization (CWE-502)
**File:** `infra/compute_engines/kubernetes/main.py`, lines 70–73

Uses `yaml.load(f, Loader=yaml.Loader)` instead of `yaml.safe_load()`. The default `yaml.Loader` can execute arbitrary Python code via crafted YAML payloads (e.g., `!!python/object/apply:os.system`). If an attacker can write to `/var/feast/feature_store.yaml` or `/var/feast/materialization_config.yaml`, this yields code execution.

### 5. SQL Injection — MSSQL source (CWE-89)
**File:** `infra/offline_stores/contrib/mssql_offline_store/mssqlserver_source.py`, lines 263–270

Uses Python f-strings to construct SQL queries with the `table_name` and `database` variables from `data_source.table_ref`, without any parameterization or escaping. If the data source table reference is attacker-controlled, SQL injection is possible.
