### Vulnerability 1: ListObjects Authorization Bypass (CWE-285 — Improper Authorization)

**Location**: `pkg/gateway/operations/listobjects.go`, lines 39-60

**Root Cause**: The `RequiredPermissions` method decides whether to check for `fs:ListBranches` or `fs:ListObjects` based entirely on user-controlled query parameters (`delimiter` and `prefix`). However, the subsequent handler logic (`ListV1`/`ListV2`) decides whether to actually list branches or objects based on a different condition — whether `ResolvePath(prefix)` produces a ref with a path component (`WithPath`).

**The Mismatch**:
```
RequiredPermissions logic:
    if delimiter == "/" && prefix does NOT contain "/" → check fs:ListBranches
    else → check fs:ListObjects

Handler logic:
    if prefix does NOT resolve to ref+path (no "/") → list branches
    if prefix resolves to ref+path (has "/") → list objects
```

**Exploitation**: A user granted `fs:ListObjects` (but NOT `fs:ListBranches`) can list all branches by sending:
```
GET /repo?list-type=2&prefix=main
```
- `RequiredPermissions`: `delimiter=""` → falls to `else` → checks `fs:ListObjects` → ALLOWED (user has it)
- Handler: `ResolvePath("main")` returns `{Ref:"main", WithPath:false}` → lists branches

The converse direction (listing objects with only `fs:ListBranches`) is properly blocked because the `prefix` must contain `/` to list objects, and `prefix` containing `/` causes `RequiredPermissions` to check `fs:ListObjects`.

---

### Vulnerability 2: DeleteObjects Missing Authorization Gate (CWE-862 — Missing Authorization)

**Location**: `pkg/gateway/operations/deleteobjects.go`, line 26-28

**Root Cause**: `DeleteObjects.RequiredPermissions` returns `permissions.Node{}` (zero-value, empty). In `handler.go` (lines 267-272), the `authorize` function checks:
```go
if len(perms.Nodes) == 0 && len(perms.Permission.Action) == 0 {
    // has not provided required permissions → skip authorization entirely
    return &operations.AuthorizedOperation{...}
}
```
Since both fields are 0/empty, **no authorization check is performed** at the middleware level for `DeleteObjects` requests. Compare with the singular `DeleteObject` (deleteobject.go:16-23) which properly requires `fs:DeleteObject`.

While the handler does perform per-object authorization internally (lines 77-93), any authenticated user can trigger full processing — XML body parsing, path resolution, and up to 1000 authorization service calls — without any base-level permission check on the repository.

---

### (Not a vulnerability) x-amz-copy-source path traversal

The `getPathFromSource` function in `putobject.go` does decode and split the copy source into repo/ref/path components. The path component could contain `../` sequences. However, lakeFS treats paths as **opaque keys** in a flat key-value store — no filesystem path normalization (`path.Clean`, etc.) exists anywhere in `pkg/graveler/` or `pkg/catalog/`. A key like `foo/../../bar` is stored and retrieved as the literal byte sequence `foo/../../bar`. There is no directory traversal risk because there are no directories to escape from — only flat key lookups.
