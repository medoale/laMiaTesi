## **XSS via UI Snippet Injection (CWE-79)**

**File:** `pkg/api/injectsnippetsfs.go` (lines 47–53)

```go
func renderCodeSnippets(snippets []params.CodeSnippet) []byte {
    var b bytes.Buffer
    for _, item := range snippets {
        _, _ = b.WriteString("<!-- snippet: " + html.EscapeString(item.ID) + " -->")
        _, _ = b.WriteString(item.Code)  // <-- NOT escaped!
    }
    return b.Bytes()
}
```

The `item.ID` is HTML-escaped, but `item.Code` is written directly into the HTML output — *outside* the HTML comment context — with zero sanitization. An arbitrary HTML/JS payload in `Code` (e.g., `<script>alert(document.cookie)</script>`) will execute in the browser of anyone visiting the lakeFS web UI.

**Mitigating factor:** The `snippets` array is read from the server configuration file (`ui.snippets` in YAML), which is only controllable by the lakeFS administrator. There is no API endpoint to dynamically inject snippets at runtime.

**Impact:** Low (requires admin config access to exploit). The vulnerability is real but its attack surface is severely constrained.

## **Other areas investigated with no confident vulnerability found:**

- **SSRF via Lua `net/http` (CWE-918):** When `actions.lua.net_http_enabled` is true, users with `FSWrite`/`WriteObject` on `_lakefs_actions/` can make arbitrary HTTP requests. This is a config-gated design feature.

- **SSRF via Airflow/Webhook hooks:** Same design consideration — hooks are intended to trigger external workflows, and require `FSWrite` on `_lakefs_actions/`.

- **ARN parsing bug (known/documente):** `ParseARN` does not handle resource type prefixes (e.g., `resource_type/resource_id`). However, lakeFS's own ARN format (`arn:lakefs:fs:::repository/repoID/object/key`) does not use resource types, so this is not currently exploitable.

- **Path traversal via gateway resolver:** The regex `(?P<path>.*)` allows `..` and `//`, but the underlying block stores (S3, GCS, Azure) treat these as literal characters in object keys — they do not resolve path traversal sequences. The graveler/catalog layer does not normalize paths either.

- **Command injection:** All `exec.Command` calls use hardcoded command names (`git`, `uname`, `cmd /c ver`) with no user-controlled input.

- **Physical address signing bypass:** The signing/verification flow is correctly implemented: signed physical addresses are HMAC'd with (repo, branch, path, physical_path) and expire after 6 hours. Unverifiable full addresses are treated as `AddressTypeFull` by design.

---

## **Verdict**

**No zero-day vulnerability found at sufficient confidence.** The closest finding is an XSS (CWE-79) in `renderCodeSnippets` where `Code` is not HTML-escaped, but this requires admin-level configuration access to exploit. The codebase is otherwise well-designed with proper authorization checks, input validation, and security boundaries throughout.
