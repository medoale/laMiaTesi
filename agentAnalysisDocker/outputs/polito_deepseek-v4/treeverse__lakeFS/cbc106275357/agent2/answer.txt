## Analysis

This commit fixes two related path traversal vulnerabilities in the lakeFS local block adapter (`pkg/block/local/adapter.go`):

### Vulnerability 1 — Prefix-based bypass in `verifyRelPath`

The original check was:
```go
strings.HasPrefix(filepath.Clean(p), l.path)
```
This only checks whether the cleaned path *starts with* the adapter's base path as a string prefix, **not** whether it is actually a subdirectory. For example, if `l.path = "/data/lakefs"`, a path like `/data/lakefs_backup/evil.txt` starts with the string `/data/lakefs` and would **incorrectly pass** the check, even though the file is completely outside the `lakefs` directory.

The fix appends a separator:
```go
strings.HasPrefix(filepath.Clean(p), l.path+string(filepath.Separator))
```

### Vulnerability 2 — Cross-namespace traversal in `extractParamsFromObj`

The original code joined the adapter path, storage namespace, and identifier, then checked only whether the result was somewhere under the **adapter's** base path:
```go
p := path.Join(l.path, ptr.StorageNamespace[len(DefaultNamespacePrefix):], ptr.Identifier)
if err := l.verifyRelPath(p); err != nil { ... }
```

This allowed an attacker with access to one repository's storage namespace to use `../` sequences in the `Identifier` to escape that specific namespace and read/write files belonging to **other namespaces** under the same adapter. The test `TestPathTraversalDataAccess` in `file_02` demonstrates this concretely:

- Adapter path: `/tmpDir/lakefs`
- Namespace: `local://repo1/namespace`
- Identifier: `subdir/../../other/secret.txt`
- Resolved path (cleaned): `/tmpDir/lakefs/repo1/other/secret.txt`
- Old `verifyRelPath`: passes — it starts with `/tmpDir/lakefs`
- But this file is in `repo1/other/`, **not** in `repo1/namespace/` — a cross-namespace escape.

The fix introduces a **two-level** check:
1. First, verify the namespace path itself is under the adapter's base path.
2. Then, verify the final resolved path is either equal to the namespace path or under it — not just anywhere under the adapter.

Both are classic **path traversal** vulnerabilities: the program fails to properly restrict the pathname to a restricted directory, allowing an attacker to access files outside the intended scope.
