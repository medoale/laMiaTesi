**Why this is a security vulnerability fix:**

The commit description explicitly mentions "Poisoned Pipeline Execution (PPE) attacks." In a CI/CD pipeline, an attacker who can submit a pull request could pre-create a `.coverage` file (serialized PHP data) in the test directory. When PHPUnit runs the PHPT test and code coverage is enabled, it would:

1. See the `.coverage` file already exists
2. Read and `unserialize()` it (see `cleanupForCoverage()` on line 614 of the before.txt)
3. Even though `unserialize()` uses `['allowed_classes' => false]`, the file is loaded from a predictable path

The attack vector is: An attacker prepares a malicious `.coverage` file in a PR, the CI pipeline runs PHPUnit on that PR, PHPUnit `unserialize()`s the attacker-controlled file. This is a classic **Poisoned Pipeline Execution** attack — a supply-chain security issue where untrusted input from a PR can influence the CI pipeline's execution.

Even with `allowed_classes => false`, `unserialize()` can still be exploited via PHP's built-in classes (like `__warnings` and other gadget chains that don't require classes). Moreover, the `.coverage` file could contain data that produces malicious coverage data that leads to incorrect CI results or other downstream impacts.

The fix is a defense-in-depth check that prevents the PHPT test from running at all if the coverage file pre-exists, effectively blocking the pre-planted file attack.
