### What this commit does

This is a security fix for PHPUnit 8.5.52. The commit adds a new check in `PhptTestCase::__construct()` (in `src/Runner/PhptTestCase.php`) that prevents a PHPT test from executing when a corresponding `.coverage` file already exists before the test runs.

### Why this is a security vulnerability fix

The attack chain works as follows:

1. **Derived predictable paths**: `PhptTestCase::getCoverageFiles()` derives the `.coverage` file path directly from the PHPT test filename — `dirname(realpath($this->filename)) . DIRECTORY_SEPARATOR . basename($this->filename, 'phpt') . 'coverage'`. This is fully deterministic.

2. **Unserialize on attacker-controlled data**: When code coverage is enabled and a PHPT test runs, `cleanupForCoverage()` (line 605-627) reads the `.coverage` file using `file_get_contents()` and then calls **`unserialize()`** on its contents (line 614):
   ```php
   $buffer = @file_get_contents($files['coverage']);
   if ($buffer !== false) {
       $coverage = @unserialize($buffer, ['allowed_classes' => false]);
   }
   ```

3. **Attack scenario (Poisoned Pipeline Execution)**: An attacker submits a pull request containing both a PHPT test file and a pre-crafted `.coverage` file with the matching filename. When the CI/CD pipeline runs the tests with code coverage enabled, PHPUnit finds the pre-existing `.coverage` file, unserializes it, and passes the data to the code coverage engine (`$result->getCodeCoverage()->append(...)`). This allows the attacker to poison the pipeline's results — manipulating coverage data to, for example, hide untested code paths, fake coverage statistics, or potentially exploit downstream processing of the crafted deserialized payload.

4. **The fix**: By adding `ensureCoverageFileDoesNotExist()` early in the constructor (before any test logic runs), the code now throws an exception immediately if the `.coverage` file already exists, effectively blocking the attack before any deserialization occurs.

While `unserialize()` uses `['allowed_classes' => false]` which prevents PHP object injection, deserializing untrusted arrays/data is still a well-recognized risk — the attacker can craft arbitrary PHP data structures that influence the behavior of the coverage processing pipeline.

The changelog entry explicitly names this: *"To prevent Poisoned Pipeline Execution (PPE) attacks using prepared `.coverage` files in pull requests"*.

The core mechanism by which the attack operates is **deserialization of untrusted data** — the `.coverage` file from an untrusted source is passed to `unserialize()` without verifying its authenticity or origin. This maps specifically to:
