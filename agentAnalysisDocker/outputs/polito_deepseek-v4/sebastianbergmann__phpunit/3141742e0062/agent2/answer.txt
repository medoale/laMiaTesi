**Understanding the vulnerability (Poisoned Pipeline Execution / PPE attack):**

1. **The attack scenario**: PHPUnit supports PHPT (PHPT = PHPT Test) files for testing PHP itself. When code coverage collection is enabled for a PHPT test, the process works as follows:

   - `getCoverageFiles()` computes paths for two temporary files: a `.coverage` file and a `.php` job file. These are placed in the same directory as the `.phpt` test file, with the same basename but different extensions.
   
   - `renderForCoverage()` writes the test's PHP code to the `.php` job file, then creates a wrapper script (the template) that runs the test in a subprocess. The wrapper script collects code coverage and **serializes the coverage data to the `.coverage` file**.
   
   - `cleanupForCoverage()` uses `@unserialize()` to read the `.coverage` file, extracts the coverage data, then deletes both `.coverage` and `.php` files.

2. **The vulnerability in the before code**: In the constructor (`PhptTestCase::__construct`), there is **no check** for whether the `.coverage` file already exists before the test runs. An attacker who can submit a pull request containing a PHPT test file could also pre-place a `.coverage` file (which contains serialized PHP data) in the same directory. When PHPUnit processes this PHPT test in a CI/CD pipeline with coverage enabled:

   - PHPUnit will render and run the test, which overwrites the `.coverage` file (via the template's `file_put_contents('{coverageFile}', serialize($output))`).
   - `cleanupForCoverage()` reads it with `@unserialize()` — but the attacker-controlled coverage data could contain crafted serialized objects that exploit PHP's unserialization to achieve code execution.
   - Even though `['allowed_classes' => false]` is passed to `unserialize()`, the pre-existing `.coverage` file could influence execution flow.

   But more importantly, there's a simpler attack: by placing a pre-crafted `.coverage` file, before the test even runs, the `file_exists($files['coverage'])` check in `cleanupForCoverage()` would read the attacker's file. Even though `allowed_classes` is false, **the more critical issue is that the attacker could provide arbitrary `.coverage` content that gets `unserialize()`d**, and while `allowed_classes=false` prevents instantiation of arbitrary classes, there are still potential gadget chains in PHP with `__unserialize()` or `__destruct()` on built-in classes that can be exploited.

   However, the **primary security issue** as described in the changelog is about **Poisoned Pipeline Execution (PPE)** — the attacker places a pre-crafted `.coverage` file before the test runs, so that when `cleanupForCoverage()` reads it, it processes attacker-controlled serialized data. The fix prevents this by checking **before the test runs** if the `.coverage` file already exists, and if so, refusing to execute the test entirely.

3. **The fix**: The new `ensureCoverageFileDoesNotExist()` method in the constructor checks whether the `.coverage` file already exists before the test runs. If it does, it throws an Exception and refuses to execute the test, preventing the attacker from pre-placing a malicious `.coverage` file.
