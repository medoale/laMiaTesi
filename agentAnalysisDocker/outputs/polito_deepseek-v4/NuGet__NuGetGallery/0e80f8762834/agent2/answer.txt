## Security Analysis

This commit is a **security vulnerability fix**. It addresses multiple overlapping vulnerabilities across the NuGet Gallery and Catalog codebases.

### 1. CWE-345: Insufficient Verification of Data Authenticity — Nuspec identity spoofing

The old code in two places (file 03 — `DnxCatalogCollector.GetNuspec()` and file 07 — `Utils.GetNuspec()`) manually searched zip archive entries for any file ending in `.nuspec`. In `DnxCatalogCollector`, it first tried `{id}.nuspec`, then fell back to **any** `.nuspec` file in the archive. In `Utils.GetNuspec()`, it returned the first `.nuspec` file not in a subdirectory.

A malicious `.nupkg` could include a forged nuspec with a different package identity (ID, version, or both), and the old code would accept it as genuine. The attacker could make a package appear to be a different, trusted package in the catalog.

The fix:
- Uses `PackageArchiveReader.GetNuspec()` (from the official NuGet.Packaging library) which correctly identifies the authoritative nuspec
- Cross-checks the package ID from the nupkg against the expected ID from the catalog leaf — mismatches throw an `InvalidOperationException`
- Adds `CheckNuspecCount()` (file 17) to reject packages with more than one nuspec file

### 2. CWE-22: Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal') — URI/path construction

The old code had three path-traversal vectors:

- **`Storage.ResolveUri(string relativeUri)`** in `NuGet.Services.Storage/Storage.cs` (file 10): Used `new Uri(BaseAddress.GetLeftPart(UriPartial.Path).TrimEnd('/') + "/" + relativeUri.TrimStart('/'))` **without any validation** of the relative URI. The diff shows it was refactored to a static `Storage.ResolveUri(Uri baseAddress, string relativeUri)` with the new `AssertSimpleBlobName()` guard.

- **`AzureStorage.ResolvePathedUri(string filename)`** in `AzureStorage.cs` (file 14): Used `Path.Combine(_path, filename)`, which resolves `..` path traversal sequences. Changed to manual string concatenation with validation.

- **`Storage.GetName(Uri uri)`** (file 10): Had no check for encoded directory separators like `%2F` (encoded `/`) or `%5C` (encoded `\`), allowing an attacker to craft a URI that escapes the intended blob container. The old code also didn't verify that the URI actually starts with the base address.

The fix adds `AssertSimpleBlobName()` (file 15) which rejects:
- Fragments (`#`) and query strings (`?`)
- Empty path segments
- Segments starting or ending with `.`
- Segments containing `\` or `/` (including encoded variants)

### 3. CWE-172: Encoding Error — Unicode normalization and URL encoding bypass

- **Unicode normalization in package IDs** (file 17): The new `CheckPackageIdForBannedCharacters()` rejects surrogate characters (e.g., `\U0001F600`), characters whose lowercase/uppercase expansion changes length (e.g., German `ß` → "SS"), and non-ASCII characters that case-fold to ASCII (e.g., Kelvin sign `\u212A` → "K"). These could enable ID confusion — two package IDs that look different but normalize to the same string, or that bypass validation checks.

- **URL-encoded path separators** (file 15): The old `GetName()` passed raw `uri.ToString()` to string manipulation, so `%2F` and `%5C` were never detected. The new code explicitly checks for `%2F` and `%5C` in `uri.AbsoluteUri` before processing, and `AssertSimpleBlobName()` checks decoded path segments for `\` and `/`.

### 4. CWE-20: Improper Input Validation — Missing model validation

The `OrganizationsController.Add()` method (file 16) did **not** check `ModelState.IsValid` before processing the submitted form. Client-side validation could be bypassed, allowing invalid organization names or emails to be sent to the server. The fix adds `if (!ModelState.IsValid) { return View(model); }` at the top of the action method.

CWE-20 is the general category, but the more specific CWE-345, CWE-22, and CWE-172 above describe the actual vulnerabilities more precisely.
