## Analysis

**Repository:** Craft CMS 5

**Changed files:**
1. `CHANGELOG.md` (file_01) — Documents the security fix: "Fixed a moderate-severity authorization bypass vulnerability (GHSA-jq2f-59pj-p3m3)"
2. `src/controllers/UsersController.php` (file_02) — The actual code fix with two changes

### Change 1: `actionSavePermissions()` — Missing authorization guard

**Before (vulnerable):**
```php
public function actionSavePermissions(): Response
{
    $this->requireCpRequest();
    // No authorization check!
    $currentUser = static::currentUser();
    $user = $this->editedUser(...);
```

**After (fixed):**
```php
public function actionSavePermissions(): Response
{
    $this->requireCpRequest();
    if (!$this->showPermissionsScreen()) {
        throw new ForbiddenHttpException('User not authorized to perform this action.');
    }
    $currentUser = static::currentUser();
    $user = $this->editedUser(...);
```

The `showPermissionsScreen()` method (defined in `EditUserTrait.php`) checks whether the current user is entitled to view/manage the permissions screen based on:
- The CMS edition (Team or Pro)
- Whether the user is an admin (on Team)
- Whether the user has the `assignUserPermissions` permission (on Pro+)
- Whether the user can assign any user groups

**Without this check**, any authenticated user with control panel access could call `users/save-permissions` and modify another user's permissions, including potentially escalating their own privileges, even if they have no business assigning permissions.

### Change 2: `_saveUserGroups()` — Missing authorization guard

**Before (vulnerable):**
```php
private function _saveUserGroups(User $user, User $currentUser): void
{
    $groupIds = $this->request->getBodyParam('groups');
    // No check on whether the current user can assign groups at all!
```

**After (fixed):**
```php
private function _saveUserGroups(User $user, User $currentUser): void
{
    if (!$currentUser->canAssignUserGroups()) {
        return; // silently skip
    }
    $groupIds = $this->request->getBodyParam('groups');
```

The `canAssignUserGroups()` method (defined in `User.php`) checks if the user is admin or has any `assignUserGroup:*` permission. Without this guard, a user with NO group-assignment permissions could still have their group assignments processed. While the per-group loop below would throw `ForbiddenHttpException` for groups they cannot assign, the missing gate meant group *removals* (submitting a reduced list) could silently succeed for groups the user had no business removing.

### Vulnerability Classification

This is an **authorization bypass** — the system failed to check whether the requesting user was authorized to perform the action before processing it. The most accurate CWE is:

**CWE-862: Missing Authorization** — The code path did not perform any authorization check before executing functionality that modifies user permissions and group assignments. This is distinct from CWE-285 (Improper Authorization) because the authorization check was entirely absent rather than incorrectly implemented.
