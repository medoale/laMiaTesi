## Analysis

**The `StringM<MAX>::from_str` implementation at line 1977-1980:**

```rust
fn from_str(s: &str) -> core::result::Result<Self, Self::Err> {
    let b = escape_bytes::unescape(s.as_bytes()).map_err(|_| Error::Invalid)?;
    Ok(Self(b))  // <--- BUG: no length check against MAX
}
```

`StringM<MAX>` is a type parameterized by a `MAX` constant (a `u32`) that represents the maximum allowed length of the string in bytes. The internal storage `Vec<u8>` can hold any number of bytes.

The `from_str` implementation:
1. Unescapes the input string into a `Vec<u8>` called `b`
2. Wraps it directly in `Ok(Self(b))` **without checking if `b.len() <= MAX`**

In contrast, the `TryFrom<Vec<u8>>` implementation for `StringM<MAX>` (lines 2070-2079) **does** perform the proper length check:
```rust
fn try_from(v: Vec<u8>) -> Result<Self, Error> {
    let len: u32 = v.len().try_into().map_err(|_| Error::LengthExceedsMax)?;
    if len <= MAX {
        Ok(StringM(v))
    } else {
        Err(Error::LengthExceedsMax)
    }
}
```

This means a caller can bypass the length constraint by using `from_str()` instead of `try_from()`:
- `StringM::<3>::from_str("abcd")` would succeed, creating a `StringM<3>` containing 4 bytes
- The fix (changing `Ok(Self(b))` to `b.try_into()`) would route through `TryFrom<Vec<u8>>`, which properly checks the length

**Security impact:** XDR is a binary protocol used by the Stellar network. `StringM<MAX>` types appear throughout the protocol definitions (e.g., `name: StringM<60>`, `doc: StringM<1024>`). Bypassing the maximum length constraint could cause:
- Memory corruption or out-of-bounds write in downstream consumers that assume the length bound is enforced
- Protocol-level attacks where oversized strings are accepted when they should be rejected
- Potential buffer overflows in C or other native language bindings that use this library
- Denial of service via resource exhaustion (creating unexpectedly large allocations)

The most fitting CWE is **CWE-787 (Out-of-bounds Write)** because a downstream component relying on the `MAX` bound to allocate a fixed-size buffer would be vulnerable to writing beyond that buffer. However, since the type itself stores a `Vec<u8>` (heap allocated), the overflow doesn't corrupt adjacent memory within Rust's safe abstractions — it corrupts the *logical* protocol invariant. A secondary CWE could be **CWE-20 (Improper Input Validation)** for the missing length check.

The most precise classification given the language-level safety of Rust is **CWE-1329 (Reliance on Component That Is Not Updateable)** — but this doesn't fit well either.

The best fit considering the nature of XDR protocol parsing and the bypass of a size constraint is **CWE-20 (Improper Input Validation)**, or more specifically for protocol/string length issues: **CWE-130 (Improper Handling of Length Parameter Inconsistency)**. However, since the impact can propagate to out-of-bounds writes in downstream consumers (e.g., C bindings), **CWE-787 (Out-of-bounds Write)** remains the most severe associated CWE.

Given that the vulnerability is specifically a **missing bounds check on the length parameter** that allows creation of a `StringM<MAX>` with more bytes than `MAX` permits, I'll classify it as:

**CWE-787: Out-of-bounds Write**

This is because the type's `MAX` constraint is a documented length bound that consumers may rely on for buffer sizing. A `StringM<3>` containing 4 bytes of data violates that bound, and downstream code that trusts the `MAX` bound (e.g., copying into a fixed-size `[u8; MAX]` array) would overflow.
