**Vulnerability found: Improper Input Validation (CWE-20) in `ReadXdr for bool`**

The `ReadXdr for bool` implementation at lines 871-879 of both `src/curr/generated.rs` and `src/next/generated.rs` reads a `u32` value from the wire but performs **no validation** that the value is `0` or `1` as required by RFC 4506 (XDR Standard, Section 4.10):

```rust
fn read_xdr<R: Read>(r: &mut Limited<R>) -> Result<Self, Error> {
    r.with_limited_depth(|r| {
        let i = u32::read_xdr(r)?;
        let b = i == 1;
        Ok(b)
    })
}
```

Any arbitrary `u32` value (0 through `u32::MAX`) is accepted without error. Values other than exactly `1` are silently mapped to `false`. The XDR specification mandates that only `0` (false) or `1` (true) are valid — values like `2`, `3`, or `0xFFFF_FFFF` are illegal and must be rejected.

This is Improper Input Validation (CWE-20). In a blockchain/consensus context, this creates a divergence risk: the reference C++ Stellar implementation (stellar-core) may reject such invalid bool values as malformed, while this Rust library would accept them. If the bool field appears in a signed/payload portion of a protocol message, the hash and signature verification would bind to a different byte sequence than what the library interprets, leading to consensus safety failures (different nodes accepting/rejecting the same message).
