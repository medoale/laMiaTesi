## Final Vulnerability Analysis

### ⚠️ Vulnerability 1: Arbitrary Class Instantiation via PHPCode Grid Operator (CWE-665)

- **File**: `src/DataObject/GridColumnConfig/Operator/PHPCode.php`
- **Method**: `buildInstance()` (line 81-92)
- **Route trigger**: Authenticated grid proxy endpoints
- **Severity**: **High** (authenticated, leads to potential RCE)
- **Confidence**: **High**

**Root Cause**: The `PHPCode` operator takes a `phpClass` property from the grid configuration (user-supplied JSON) and instantiates it via `new $phpClass($this->config, $this->context)` on line 86. There is no allowlist or validation of the class name.

```php
private function buildInstance(): OperatorInterface
{
    $phpClass = $this->getPhpClass();  // from $config->phpClass, user-controlled
    
    if ($phpClass && class_exists($phpClass)) {
        $operatorInstance = new $phpClass($this->config, $this->context);  // arbitrary instantiation!
        return $operatorInstance;
    }
    // ...
}
```

**Attack Scenario**: An authenticated admin user saves a grid config via `gridSaveColumnConfigAction` with an operator element where `class` = `PHPCode` and `phpClass` = any existing PHP class. When the grid is loaded and the operator is applied (e.g., via `gridProxyAction`), the class is instantiated. If the constructor has side effects (e.g., writes files, executes commands, connects to services), this enables exploitation.

---

### ⚠️ Vulnerability 2: PHP Deserialization via PHP Grid Operator (CWE-502)

- **File**: `src/DataObject/GridColumnConfig/Operator/PHP.php`
- **Line**: 78
- **Severity**: **High** (authenticated, gadget-dependent RCE)
- **Confidence**: **Medium-High**

**Root Cause**: The `PHP` operator calls `Serialize::unserialize($result->value)` on the value from a data object field when configured in mode `'u'`. A user can store a crafted serialized payload in a data object text field (e.g., a `textarea` or `input` field), and if the grid config includes a PHP operator with `mode = 'u'`, `unserialize()` will be called on that stored value.

```php
} elseif ($this->mode === 'u') {
    $result->value = Serialize::unserialize($result->value);  // attacker-controlled data
}
```

**Attack Scenario**: An attacker (authenticated admin user with data edit and grid config permissions):
1. Creates/edits a data object with a text field containing a malicious serialized payload
2. Configures a grid view with a `PHP` operator in mode `'u'` chained to that field
3. Loads the grid view, triggering `unserialize()` on the stored payload

**Risk modifier**: The `Serialize::unserialize()` method (from `pimcore/pimcore` core) is a thin wrapper around PHP's native `unserialize()`. With available gadget chains from Symfony, Monolog, Doctrine, or other dependencies, this can lead to RCE.

---

### ⚠️ Vulnerability 3: Legacy Grid Config Deserialization (CWE-502)

- **File**: `src/Controller/Admin/DataObject/DataObjectController.php`
- **Line**: 796
- **Severity**: **High** (if file is writable, RCE)
- **Confidence**: **Medium**

**Root Cause**: The `getAction` reads a `.psf` (PHP Serialized Format) file from the filesystem and directly unserializes it:

```php
$configFile = PIMCORE_CONFIGURATION_DIRECTORY . '/object/grid/' . $object->getId() . '-user_' . $this->getAdminUser()->getId() . '.psf';
if (is_file($configFile)) {
    $gridConfig = Tool\Serialize::unserialize(file_get_contents($configFile));
```

The file path is predictable (based on object ID + user ID). If an attacker can write to this location (e.g., via another file upload vulnerability or shared hosting environment), they can plant a serialized payload.

---

### ⚡ Vulnerability 4: Script Proxy File Read via Admin Storage (CWE-22)

- **File**: `src/Controller/Admin/MiscController.php`
- **Lines**: 129-158
- **Severity**: **Medium** (authenticated, arbitrary file read)
- **Confidence**: **High**

**Root Cause**: The `scriptProxyAction` reads from the `admin` storage using a user-supplied path with no sanitization:

```php
$storageFile = $request->get('storageFile');
// ... no path validation ...
$storage = Storage::get('admin');
$scriptsContent = $storage->read($storageFile);
```

The `$storageFile` parameter is used directly as a path to the storage adapter. If the storage is backed by a local filesystem, this allows reading files in other directories via `../` traversal.

---

### ⚡ Vulnerability 5: Dashboard Config Deserialization (CWE-502)

- **File**: `src/Helper/Dashboard.php`
- **Line**: 64
- **Severity**: **Medium**
- **Confidence**: **Low-Medium**

**Root Cause**: Dashboard config files are serialized/unserialized with PHP's native serialization. The file path is `PIMCORE_CONFIGURATION_DIRECTORY . '/portal/dashboards_' . $this->getUser()->getId() . '.psf'`. While the file is written by the application, any vulnerability allowing filesystem write to this path would lead to deserialization RCE.

---

### ⚡ Vulnerability 6: Import Upload Weak Path Traversal Protection (CWE-22, CWE-73)

- **File**: `src/Controller/Admin/DataObject/DataObjectHelperController.php`
- **Lines**: 1133-1144
- **Severity**: **Medium** (authenticated, limited file write)
- **Confidence**: **Medium**

**Root Cause**: Uses `str_replace('..', '', $importId)` which is a weak filter that can be bypassed with URL-encoded or otherwise manipulated inputs. While `./` alone doesn't enable upward traversal, this is an incomplete protection mechanism.
