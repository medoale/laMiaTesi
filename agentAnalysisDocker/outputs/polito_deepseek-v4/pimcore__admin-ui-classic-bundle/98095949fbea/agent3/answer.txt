## Summary of Our Security Audit So Far

### Repository
- **Package**: `pimcore/admin-ui-classic-bundle` — the admin backend UI for Pimcore CMS (PHP/Symfony/ExtJS)
- **Key areas**: `src/Controller/Admin/` (18 controllers), `src/Helper/`, `src/DataObject/`, `templates/`

### Findings After Verification

#### 1. Insecure Deserialization — CONFIRMED (CWE-502)
Three locations use `Serialize::unserialize()` (a wrapper around PHP's native `unserialize()`) on data from the filesystem:

| File | Line | Source | Attack Surface |
|------|------|--------|----------------|
| `src/Helper/Dashboard.php` | 64 | `file_get_contents(PIMCORE_CONFIG_DIR . '/portal/dashboards_{userId}.psf')` | Authenticated user's dashboard config file |
| `src/Controller/Admin/DataObject/DataObjectController.php` | 796 | `file_get_contents(PIMCORE_CONFIG_DIR . '/object/grid/{objId}-user_{userId}.psf')` | Per-object grid config file |
| `src/DataObject/GridColumnConfig/Operator/PHP.php` | 78 | `Serialize::unserialize($result->value)` — processes grid column values during data rendering | Grid config processing pipeline |

**Exploitability**: The `.psf` files are written by the application itself (`Serialize::serialize()`), so direct remote exploitation requires a **prerequisite vulnerability** (e.g., arbitrary file write, path traversal, or file upload bypass) to plant a malicious payload. However, if any such file-write vector exists elsewhere in the stack, these `unserialize()` calls become RCE gadgets.

#### 2. SQL Injection — LARGELY MITIGATED
We traced every suspicious SQL concatenation:
- **`DataObjectHelperController`** (lines 116, 297): `$userIds` comes from `$user->getRoles()`, which always returns **integers** — not exploitable.
- **`AssetHelperController`** (lines 101, 201): Same pattern — integer IDs only.
- **`ClassificationstoreController::getPageAction`** (line 1466): `$sortKey` and `$tableSuffix` are checked against **whitelists** via `in_arrayi()`; `$storeId`, `$id`, `$pageSize` are cast to `(int)`. The whitelist makes injection impossible despite the direct concatenation.
- **`PortalController`** (lines 310-312): `$start`, `$end` are integers from `mktime()` — safe.
- **`SettingsController::deleteViews`** (line 1310): Uses `$db->quoteIdentifier()` — safe.

**Verdict**: No exploitable SQL injection found.

#### 3. Open Redirect — DISMISSED
- **`deeplink.html.twig`** (line 12): `{{ redirect | raw }}` is generated by Symfony's `generateUrl()` producing a **relative URL** (`/admin/login?deeplink=true`), not attacker-controlled input.
- **`PublicServicesController::customAdminEntryPointAction`** (line 29): All query params are passed to `generateUrl()` which maps to admin route names only — redirect always stays within the admin domain.

**Verdict**: No exploitable open redirect found.

#### 4. Other Potential Areas (not yet fully verified)
- **`templates/admin/misc/admin_css.html.twig`**: Custom view icons from perspective config rendered as CSS `url()` values — potential CSS injection / content injection.
- **`MiscController`** and **`TranslationController`**: Need to check for stored XSS paths or file operation issues.
- **`WorkflowController`**: Uses `Process` class for workflow transitions — needs review for command injection.

### Overall Status
The **most actionable finding** is **Insecure Deserialization (CWE-502)** across three files, with `Helper/Dashboard.php` being the most exposed since its file path pattern is well-known and the class is invoked for every authenticated user. The `PHP.php` operator is interesting because it deserializes data within the grid processing pipeline, potentially from database-stored values that could be attacker-influenced.
