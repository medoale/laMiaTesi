**Security Analysis:**

The core vulnerability being fixed is in **File 02**. Here's why it's a security issue:

When a user uploads a remote document URL (e.g., `doc_url` pointing to an external URL like `https://attacker.com/malicious.pdf`), the old code unconditionally called `resource_manager.set_thumbnail(...)`, which in turn called `create_document_thumbnail` task. In that task (tasks.py line 119-122), when `document.doc_url` is set but there's no asset, `doc_path` is set to `document.doc_url` (the user-supplied URL). Then at line 126, `asset_storage_manager.open(doc_path)` is called, which attempts to open and read from that URL.

This is a classic **Server-Side Request Forgery (SSRF)** vulnerability — the server is being tricked into making HTTP requests to arbitrary URLs provided by the user. An attacker could:

1. Read internal resources (e.g., `http://169.254.169.254/latest/meta-data/` to get cloud metadata, or `http://internal-service/` to probe internal network services)
2. Cause the server to download and process potentially large/malicious files (potential denial of service)
3. Use the server as a proxy to scan internal networks

Additionally, since the thumbnail task downloads the remote file and processes it locally, there could also be concerns about processing untrusted files with libraries (Pillow, fitz/PyMuPDF), which could lead to further exploitation, but the primary fix is about preventing the server from making outbound requests to attacker-controlled URLs.

The fix appropriately gates thumbnail generation behind `self.object.is_local`, which returns `False` when `doc_url` is present, preventing SSRF entirely for remote documents.
