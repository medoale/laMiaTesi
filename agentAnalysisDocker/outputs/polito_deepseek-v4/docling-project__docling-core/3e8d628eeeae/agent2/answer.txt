The commit makes two identical changes, both switching from `yaml.FullLoader` to `yaml.SafeLoader`:

2. **`/work/test/test_docling_doc.py:1976`** — In the `test_export_with_precision()` test function, which reads expected test data from a YAML file. Test data is typically trusted, but the fix applies the same hardening principle.

### Security Impact

In PyYAML, `yaml.FullLoader` supports the full YAML specification, including Python-specific tags such as `!!python/object`, `!!python/object/apply`, `!!python/name`, and `!!python/module`. These tags allow the deserialization of arbitrary Python objects during YAML parsing — a classic vector for achieving arbitrary code execution. An attacker who can craft a malicious YAML document can exploit this to execute arbitrary Python code on the server processing the document.

`yaml.SafeLoader`, by contrast, only supports standard, safe YAML types (dicts, lists, strings, numbers, booleans, None) and explicitly blocks all Python-object-constructing tags, thereby preventing this attack vector.

The fix is correct: `load_from_yaml()` only needs basic Python types because the deserialized dict is immediately passed to Pydantic's `model_validate()`, which handles validation on its own terms. There is no legitimate need for `FullLoader`'s ability to construct arbitrary objects.

### CWE Classification

The vulnerability is a textbook case of **CWE-502: Deserialization of Untrusted Data** — untrusted data is deserialized using a deserialization mechanism that can construct arbitrary objects, leading to possible code execution. This is the most specific and accurate classification.
