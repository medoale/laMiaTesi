## Analysis Summary

I explored all major modules of the `docling-core` library: types, serializers, utilities, CLI, search, and chunking. The most significant finding is in the HTML serialization code.

### Vulnerability: Improper Neutralization of HTML Output (Stored XSS)

In `/work/docling_core/transforms/serializer/html.py`, lines 153-154, the `HTMLTextSerializer.serialize()` method explicitly skips HTML escaping for `CodeItem` and `FormulaItem` instances:

```python
if not isinstance(item, (CodeItem, FormulaItem)):
    text = html.escape(text, quote=False)
    text = text.replace("\n", "<br>")
```

All other `TextItem` subtypes (paragraphs, headers, captions, etc.) have their `text` value properly HTML-escaped before being placed into HTML tags. However, `CodeItem` and `FormulaItem` are excluded from this escaping. Their `text` field is user-controlled data that comes directly from the deserialized document JSON.

The unescaped text then flows into HTML elements like:
- **CodeItem**: `<code>{text}</code>` or `<pre><code>{text}</code></pre>`
- **FormulaItem**: `<pre>{text}</pre>` or `<code>{text}</code>` (in the fallback paths at lines 305, 313)

**Attack scenario**: An attacker crafts a malicious JSON document containing a `CodeItem` with `text = "<script>alert(document.cookie)</script>"`. When a victim loads this document via `DoclingDocument.load_from_json()` and exports to HTML via `export_to_html()`, the script executes in the browser — a classic stored XSS.

Additionally, I verified that the `serialize_hyperlink` method at line 903 also places `str(hyperlink)` directly into an `href` attribute without HTML-attribute escaping, and the `html_head`/`css_styles` parameters allow arbitrary HTML injection. However, these secondary vectors require attacker control over API parameters, whereas the CodeItem/FormulaItem issue is exploitable through document content alone.
