## Analysis

This commit makes a single, consistent change across two files: switching from `yaml.FullLoader` to `yaml.SafeLoader` when deserializing YAML data.

### What changed

**File 01** (production code — `DoclingDocument` class):
- **Before:** `data = yaml.load(f, Loader=yaml.FullLoader)` 
- **After:** `data = yaml.load(f, Loader=yaml.SafeLoader)`

This is in a classmethod that loads/serializes a `DoclingDocument` from a YAML file on disk. The input data likely originates from user-supplied or untrusted sources.

**File 02** (test code — `test_export_with_precision`):
- **Before:** `exp_data = yaml.load(f, Loader=yaml.FullLoader)`
- **After:** `exp_data = yaml.load(f, Loader=yaml.SafeLoader)`

Same pattern, in a test helper that reads expected data from YAML files.

### Security significance

In PyYAML, the loader hierarchy is:

| Loader | Behavior |
|---|---|
| `UnsafeLoader` (deprecated) | Arbitrary Python object construction — full code execution risk |
| `FullLoader` | Constructs Python objects for many YAML tags — still allows arbitrary code execution via e.g. `!!python/object:os.system`, `!!python/object:subprocess.run`, `!!python/tuple`, `!!python/dict`, etc. |
| `SafeLoader` | Only standard YAML types (dict, list, str, int, float, bool, None) — **no arbitrary code execution** |

`FullLoader` is **not safe**. While it was intended as a middle ground between `UnsafeLoader` and `SafeLoader`, it still permits construction of arbitrary Python objects by tag resolution, which can lead to full remote code execution when an attacker controls the YAML input.

The fix correctly restricts deserialization to `SafeLoader`, which prevents an attacker from embedding malicious YAML tags that would cause arbitrary code execution during deserialization.

### Classification

This is a textbook case of **Insecure Deserialization** — CWE-502. The application deserializes untrusted YAML data without sufficiently restricting what types can be instantiated. `FullLoader` allows construction of arbitrary Python objects, which an attacker can leverage for code execution.

No other CWE fits more precisely. For instance, CWE-94 (Code Injection) is a broader category — the injection here occurs specifically *through deserialization*, making CWE-502 the correct, most specific classification.
