## Analysis

**File changed:** `src/detect-engine-alert.c`  
**Function:** `AlertQueueExpand` — dynamic expansion of Suricata's per-thread alert queue.

### The Bug (before the fix)

```c
uint16_t new_cap = det_ctx->alert_queue_capacity * 2;
```

`alert_queue_capacity` is a `uint16_t`, initially set to 15 (`PACKET_ALERT_MAX`).  
After many appends, it doubles repeatedly: 15 → 30 → 60 → … → 30720 → 61440.

At `61440`, the next call multiplies:

- `61440 * 2 = 122880`, but `uint16_t` wraps modulo 65536  
- Result: `122880 - 65536 = 57344` (a **smaller** value than the current capacity of 61440)

The code then:
1. Calls `SCRealloc(det_ctx->alert_queue, sizeof(PacketAlert) * 57344)` — allocating a **smaller** buffer.
2. Sets `det_ctx->alert_queue_capacity = 57344` (the wrapped value).
3. Returns `57344`. The caller in `AlertQueueAppend` sees expansion "succeeded" (returned value differs from `pos`) and writes at index `pos = 61440` — well past the end of the 57344-element buffer.

This is a **heap buffer overflow** driven by an **integer overflow**.

### The Fix

- Extracts the reallocation logic into `AlertQueueExpandDo` with a `DEBUG_VALIDATE_BUG_ON` check.
- In `AlertQueueExpand`, adds two guards:
  - Returns immediately if `alert_queue_capacity == UINT16_MAX` (already at maximum).
  - Saturation check: if `alert_queue_capacity > UINT16_MAX / 2`, caps at `UINT16_MAX` instead of doubling (preventing the overflow).
- Only doubles when it is safe from overflow (`new_cap = det_ctx->alert_queue_capacity * 2` when `<= UINT16_MAX/2`).

### Impact

An attacker who can craft network traffic that triggers enough distinct signature matches on the same packet could cause the alert queue to grow past 32768 entries, triggering the integer overflow. The resulting heap buffer overflow could be exploited for memory corruption, potentially leading to denial of service or arbitrary code execution in the Suricata process.

### Classification

Two CWEs genuinely apply:

1. **CWE-190: Integer Overflow or Wraparound** — the root cause. The `uint16_t` multiplication wraps without any guard.
2. **CWE-122: Heap-based Buffer Overflow** — the exploitable consequence. The overflow yields a mis-sized heap allocation, and a subsequent write exceeds the allocated bounds.

Both are present and the fix directly addresses both. CWE-190 is listed first as the most specific root cause.
