## Analysis

The diff shows changes to `AlertQueueExpand()` in what appears to be the Suricata IDS/IPS engine (`detect-engine-alert.c`).

### The Bug (before):

The original `AlertQueueExpand()` function does:
```c
uint16_t new_cap = det_ctx->alert_queue_capacity * 2;
```

`alert_queue_capacity` is of type `uint16_t`. The multiplication `det_ctx->alert_queue_capacity * 2` is performed in `uint16_t` arithmetic. If `alert_queue_capacity` is, say, 32768 or greater, then doubling it would produce a result that **wraps around** via unsigned integer overflow (modulo 2^16).

For example:
- If `alert_queue_capacity = 32768`, then `32768 * 2 = 65536`, which wraps to `0` (since `uint16_t` max is 65535, and 65536 ≡ 0 mod 65536).
- If `alert_queue_capacity = 49152`, then `49152 * 2 = 98304`, which wraps to `32768`.

This wrapped value is then passed to `SCRealloc()` as the new allocation size: `SCRealloc(det_ctx->alert_queue, (size_t)(sizeof(PacketAlert) * new_cap))`. Wait — actually the multiplication `sizeof(PacketAlert) * new_cap` uses `size_t` (the cast), but `new_cap` itself is already a tiny wrapped value. So the realloc would allocate a **much smaller buffer** than needed, but the code then sets `det_ctx->alert_queue_capacity = new_cap` to that wrapped value.

This means subsequent writes to the alert queue (in `AlertQueueAppend`) would write beyond the allocated buffer, causing a **heap buffer overflow**.

The overflow could also go to a value like `0`, causing a zero-size allocation, and subsequent writes would corrupt heap memory.

### The Fix (after):

The fix introduces `AlertQueueExpandDo()` and modifies `AlertQueueExpand()` to:
1. **Check for capacity already at `UINT16_MAX`** (line 289: `if (det_ctx->alert_queue_capacity == UINT16_MAX)`), returning early if so.
2. **Check for overflow before doubling** (lines 293-298): If `alert_queue_capacity > (UINT16_MAX / 2)`, cap at `UINT16_MAX` instead of multiplying.
3. **Separate the allocation logic** into `AlertQueueExpandDo()` which receives the safe `new_cap` value.

This prevents the unsigned integer overflow that led to the heap buffer overflow.

### Classification

This is an **integer overflow** (wraparound) vulnerability in a `uint16_t` multiplication that leads to a **heap buffer overflow**. The most specific CWE is:

- **CWE-190**: Integer Overflow or Wraparound — the `uint16_t` multiplication wraps around.
- **CWE-122**: Heap-based Buffer Overflow — the result is using a wrapped size to allocate, then writing beyond the small buffer.

However, the root cause is the integer overflow (CWE-190), which then results in a heap buffer overflow (CWE-122). Both genuinely apply, but CWE-190 is the more fundamental classification.
