## Analysis

This is HAProxy's HTTP/3 implementation (`src/h3.c`). The change is in the `h3_rcv_buf` function, which handles incoming data on QUIC streams. Let me analyze what the diff does and why it's a security fix.

### The change

In the function `h3_rcv_buf`, there is a code path that handles the case where a FIN (end-of-stream flag) is received on a bidirectional stream with **no body data at all** (`!b_data(b) && fin && quic_stream_is_bidi(qcs->id)`). 

**Before the fix**: The code immediately called `qcs_http_handle_standalone_fin(qcs)` to finalize the stream without any validation of the Content-Length header against the actual body size. If a request had `Content-Length: 100` but sent no body (immediate FIN), HAProxy would accept it as valid.

**After the fix**: Before finalizing, the code now checks:
```c
if ((h3s->flags & H3_SF_HAVE_CLEN) && h3_check_body_size(qcs, 1)) {
    qcc_abort_stream_read(qcs);
    qcc_reset_stream(qcs, h3s->err);
    goto done;
}
```
This calls `h3_check_body_size(qcs, 1)` with `fin=1`, which compares `h3s->data_len` (total DATA received, which is 0) against `h3s->body_len` (from the Content-Length header). The check `(fin && h3s->data_len < h3s->body_len)` detects the mismatch and returns a non-zero value, causing the stream to be aborted and reset with `H3_ERR_MESSAGE_ERROR`.

### Why this is a security vulnerability (CWE-444)

Per **RFC 9114 §4.1.2**, a request or response is **malformed** if the Content-Length header value does not equal the sum of the DATA frame lengths received. Without this fix, HAProxy would accept such malformed requests as valid.

This is a classic **HTTP request smuggling** scenario:
1. An attacker sends an HTTP/3 request with `Content-Length: 100` but immediately sends FIN with no DATA frames.
2. HAProxy (before the fix) accepts this as a complete, valid request and may forward it to a backend server (potentially over HTTP/1.1 or HTTP/2).
3. The backend server, seeing `Content-Length: 100`, waits for 100 more bytes of body, creating a window for the attacker to inject additional requests in the remaining body space.
4. This creates a disagreement between what HAProxy considers the boundary of one request and what the backend considers, enabling **request smuggling**.

The existing code already had content-length checks for the normal DATA frame processing path (lines 1790-1798), but the standalone-FIN path was missing this validation entirely.

**CWE-444: Inconsistent Interpretation of HTTP Responses ('HTTP Response Smuggling')** — or more precisely, **HTTP Request Smuggling** — is the correct classification because the vulnerability allows a front-end proxy to accept an HTTP message that violates protocol rules about Content-Length consistency, creating an interpretation difference between HAProxy and a downstream server.
