## Analysis

The changes span two files:

### file_01 — Source code (annotations plugin)
The `"freetext"` annotation handler builds a PDF `/DS` (default style) string by concatenating user-supplied data (the `color` property).  

**Before the fix:**
```javascript
line += " /DS(font: Helvetica,sans-serif 12.0pt; text-align:left; color:#" + color + ")";
```
The raw `color` value (from `anno.color || "#000000"`) was interpolated directly into the PDF content stream with **no escaping or sanitization**.

**After the fix:**
```javascript
var defaultStyle = "font: Helvetica,sans-serif 12.0pt; text-align:left; color:#" + color;
line += " /DS(" + escape(encryptor(defaultStyle)) + ")";
```
The entire style string is now passed through both `escape()` (PDF string escaping, which escapes `(`, `)`, `\`, etc.) and `encryptor()` (PDF encryption layer).

### file_02 — Test file
A new test was added to verify the escaping works correctly. It uses a malicious `color` value that attempts to close the `/DS(...)` parenthesis and inject arbitrary PDF actions:

```javascript
color: '000000) /AA <</E <</S /JavaScript /JS (alert("x"))>>>> ('
```

This payload targets injecting a PDF **"Additional Action"** (`/AA`) with a **"Mouse Enter"** trigger (`/E`) that executes **JavaScript** (`/S /JavaScript /JS (...)`). The test asserts that special characters like `)` and `(` are escaped to `\)` and `\(` in the output, confirming the injection is blocked.

### Security Impact
Without the fix, a user or application passing a crafted `color` value to `jsPDF` (via `createAnnotation` with `type: "freetext"`) could inject arbitrary PDF objects into the generated document — including JavaScript actions that execute when the annotation is interacted with in a PDF reader. This is a classic **injection vulnerability** where the PDF document format is the "code" being generated and user input is embedded without neutralization of its special syntax.

This is **CWE-94: Improper Control of Generation of Code ('Code Injection')**.
