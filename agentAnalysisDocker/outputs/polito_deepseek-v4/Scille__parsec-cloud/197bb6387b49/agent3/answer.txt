## Progress Update: Found SSRF in sequester webhook URL

### Finding: SSRF via unvalidated sequester webhook URL

**Summary**: The sequester webhook URL is stored as a plain `str` without any URL validation (Pydantic model `SequesterServiceConfigInWebhook` uses `webhook_url: str`), and is passed directly to `httpx.AsyncClient.post()` to make outgoing HTTP requests. An administrator with the bearer token (or an attacker who obtains it) can set an arbitrary URL, enabling Server-Side Request Forgery against internal services.

**Affected code**: 
- `/work/server/parsec/asgi/administration.py:572-579` — `SequesterServiceConfigInWebhook` with `webhook_url: str` (no URL validation)
- `/work/server/parsec/webhooks.py:104-118`, `180-195` — direct use in `httpx.AsyncClient.post(webhook_url, ...)`
- `/work/server/parsec/components/memory/vlob.py:137-148`, `276-291` — vlob create/update calls webhook
- `/work/server/parsec/components/memory/realm.py` — realm rotate key calls webhook
- `/work/server/parsec/components/postgresql/vlob_create.py:304`, `vlob_update.py:270` — TODO notes showing PostgreSQL path doesn't even implement sequester webhook yet

**Impact**: An attacker who can create/update sequester services (requires administrative access) can direct HTTP POST requests to arbitrary URLs, including internal services (cloud metadata endpoints, internal APIs, etc.). The POST body includes vlob blob data (encrypted but still metadata about organization structure).

**Severity**: Medium/High (requires admin token, but enables internal network probing and data exfiltration).
