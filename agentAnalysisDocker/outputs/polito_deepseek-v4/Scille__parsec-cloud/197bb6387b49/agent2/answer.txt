## Summary of Changes

The commit makes changes across 8 files, all related to shared secret key generation using X25519 Diffie-Hellman:

### The Core Issue (CWE-841 / CWE-327)

**Before the fix**: `generate_shared_secret_key` used `x25519_dalek::x25519()` (in rustcrypto backend) and `curve25519::scalarmult().expect(...)` (in libsodium backend). Neither version validated the **contributory behavior** of the resulting shared secret.

The problem: In X25519 (Curve25519 Diffie-Hellman), certain public keys (specifically, points of small order) can result in a shared secret of all zeros. This is known as the "contributory" or "small subgroup" attack. If an attacker provides a malicious public key (e.g., all zeros), the resulting shared secret will be all zeros, which the attacker can predict.

The critical point: `x25519_dalek::x25519()` does NOT check for contributory behavior — it returns the raw result regardless. Similarly, `curve25519::scalarmult()` returns a `Result` which was being `.expect()`'d, but this `Result` might not actually fail on small-subgroup inputs (it depends on the implementation — some libsodium wrappers do check, some don't). The fix changes the code to:

1. Use `x25519_dalek::StaticSecret` with `diffie_hellman()` + `was_contributory()` instead of the raw `x25519()` function.
2. Propagate `curve25519::scalarmult()` errors as `CryptoError::SharedSecretKey` instead of panicking with `.expect()`.
3. Add a new `CryptoError::SharedSecretKey` error variant.
4. Add `CorruptedSharedSecretKey` variants to both `ClaimInProgressError` and `GreetInProgressError`.
5. Update callers to handle the `Result` return type.
6. Add a test verifying that a zero-valued public key is rejected.
7. Enable the `static_secrets` feature on `x25519-dalek`.

### Security Impact

This is **absolutely a security vulnerability fix**. Here's why:

- In the invitation/greeting protocol (user onboarding), the claimer sends their public key and the greeter uses it to derive a shared secret key. An attacker-controlled public key could be a low-order point, resulting in a known (all-zero) shared secret.
- This shared secret key is then used to generate SAS (Short Authentication Strings) codes that are compared out-of-band to verify identity. If the shared secret is all zeros (predictable), the SAS codes can be predicted, defeating the out-of-band verification.
- More critically, the `generate_shared_secret_key` function is also used in server-side crypto (in `server/src/crypto.rs`), which could have broader implications.

Before the fix, an attacker could provide a malicious public key and the system would silently produce a weak/worthless shared secret key, potentially breaking the cryptographic guarantees of the invitation protocol.
