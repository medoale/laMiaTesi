## Analysis

### Change in `/work/apps/api/plane/app/views/asset/v2.py` — `ProjectAssetEndpoint.patch`

**Before (line 582):**
```python
asset = FileAsset.objects.get(id=pk)
```

**After:**
```python
asset = FileAsset.objects.get(id=pk, workspace__slug=slug, project_id=project_id)
```

The `@allow_permission` decorator checks that the user has a role in the project identified by `slug` and `project_id`. However, the database query only used the primary key `pk` (a user-supplied identifier). This means an attacker who is a member of Project A could send a PATCH to `/{slug}/projects/{projectA_id}/assets/{pk_from_projectB}` and operate on an asset from Project B. The permission check would pass (because they're in Project A), but the unscoped query would return the asset from Project B.

### Change in `/work/apps/api/plane/app/views/issue/attachment.py` — `IssueAttachmentEndpoint.delete`

**Before (line 63):**
```python
issue_attachment = FileAsset.objects.get(pk=pk)
```

**After:**
```python
issue_attachment = FileAsset.objects.filter(
    pk=pk, workspace__slug=slug, project_id=project_id, issue_id=issue_id
).first()
if not issue_attachment:
    return Response(status=status.HTTP_404_NOT_FOUND)
```

The `@allow_permission([ROLE.ADMIN], creator=True, model=FileAsset)` decorator's "creator" shortcut check at line 25 (`model.objects.filter(id=kwargs["pk"], created_by=request.user).exists()`) itself has no workspace/project/issue scoping — if the user was the creator, they pass regardless of which project the asset lives in. Then the unscoped query returns any asset by pk, and the code proceeds to **delete the S3 file and database record** (`asset.delete()` — a hard delete).

### Vulnerability Classification

Both changes fix the same class of vulnerability: **Insecure Direct Object Reference (IDOR)**. The object's primary key (`pk`) is directly user-controlled, but the authorization machinery only checks the user's role in the project/workspace from the URL parameters — it never verifies that the object being accessed actually belongs to that project/workspace. The fix adds the proper scope filters to the database query.

This is a textbook **CWE-639: Authorization Bypass Through User-Controlled Key**.
