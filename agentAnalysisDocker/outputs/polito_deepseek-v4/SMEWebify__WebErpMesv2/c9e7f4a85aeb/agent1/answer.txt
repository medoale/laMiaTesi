## Analysis

This commit modifies two Laravel controllers (`OrderLinesController` and `QuoteLinesController`), both with identical fixes to their `StoreImage` methods. Let me detail the changes and their security implications.

### Identical changes in both files

The `StoreImage` method handles file uploads (pictures) for order/quote line records. Three things changed:

**1. Validation field name fixed (broken before):**
```diff
- 'image' => 'image|mimes:jpeg,png,jpg,gif,svg|max:10240',
+ 'picture' => 'required|image|mimes:jpeg,png,jpg,gif,svg|max:10240',
```
The validation rule key was `'image'` but the actual HTML form field and all subsequent code uses `'picture'`. This means the validation **did not apply to the actual uploaded file** — it validated a non-existent/non-submitted field `'image'`, which would silently pass for any request. Any file type (including `.php`, `.exe`, `.html`, etc.) could be uploaded without any restriction.

**2. Attacker-controlled filename replaced with randomized filename:**
```diff
- $filename = time() . '_' . $file->getClientOriginalName();
+ $extension = $file->getClientOriginalExtension();
+ $filename = time() . '_' . uniqid() . '.' . $extension;
```
`getClientOriginalName()` returns a filename **entirely controlled by the HTTP client**. An attacker could supply:
- `../../../../shell.php` — path traversal to write outside the intended directory
- `malicious.php` — upload a PHP webshell (especially dangerous when validation was broken)
- `.htaccess` — overwrite server config
- `index.php` — overwrite an existing page

The fix replaces this with `getClientOriginalExtension()` (only the file extension, still from client input but far less dangerous) plus `uniqid()` to generate a pseudorandom, non-guessable filename. This eliminates both path traversal and filename injection.

**3. Proper file object reference:**
```diff
- $request->picture->move(...)
+ $file->move(...)
```
The old code accessed `$request->picture` as a dynamic property. While not a security vulnerability per se, it was inconsistent with the `$file` variable already obtained from `$request->file('picture')` and could lead to unexpected behavior.

### Security Verdict

This commit fixes two closely related high-severity vulnerabilities:

- **CWE-434: Unrestricted Upload of File with Dangerous Type** — The validation key mismatch (`'image'` vs `'picture'`) meant the MIME/extension restrictions were never applied to the actual uploaded file. An attacker could upload arbitrary file types. Combined with the attacker-controlled filename, this could easily lead to remote code execution if the upload directory is web-accessible (which `public_path()` implies it is).

- **CWE-22: Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')** — `getClientOriginalName()` is untrusted user input. Using it directly to construct the file destination path allowed path traversal sequences like `../` to write files outside the intended `images/order-lines` or `images/quote-lines` directory.

Both vulnerabilities are fixed: the validation now checks the correct field name, and the filename is now randomized using `uniqid()` with only the extension taken from the original name.
