The commit modifies the `StoreImage` method in two controllers:

Both changes are identical in nature. The before and after states (and diff) are in `/changes/file_01/` and `/changes/file_02/` respectively.

### Before (vulnerable code)

```php
$request->validate([
    'image' => 'image|mimes:jpeg,png,jpg,gif,svg|max:10240',
]);
if($request->hasFile('picture')){
    $file = $request->file('picture');
    $filename = time() . '_' . $file->getClientOriginalName();
    $request->picture->move(public_path('images/...'), $filename);
}
```

### After (fixed code)

```php
$request->validate([
    'picture' => 'required|image|mimes:jpeg,png,jpg,gif,svg|max:10240',
]);
if($request->hasFile('picture')){
    $file = $request->file('picture');
    $extension = $file->getClientOriginalExtension();
    $filename = time() . '_' . uniqid() . '.' . $extension;
    $file->move(public_path('images/...'), $filename);
}
```

### Security Vulnerabilities Fixed

1. **CWE-434 (Unrestricted Upload of File with Dangerous Type)** — The validation rule checked field `'image'` instead of `'picture'`. Since `'image'` was never present in the request, **no file-type validation was actually performed** on the uploaded file. This allowed an attacker to upload arbitrary file types. The fix corrects the field name to `'picture'` so the mime-type and extension checks take effect, and adds `required` to ensure a file must be present.

2. **CWE-22 (Path Traversal)** — The original code used `$file->getClientOriginalName()` (fully attacker-controlled) directly in the filename passed to `->move()`. An attacker could include `../` sequences in the filename (e.g., `../../app/shell.php`), causing the file to be written outside the intended `public_path('images/...')` directory. The fix replaces this with `$file->getClientOriginalExtension()` + `uniqid()`, giving the attacker no control over the path or base filename.

### Verdict

This is a security vulnerability fix.
