## Key Decisions
- API C++ components (Noise/plaintext auth, protobuf) have reasonable authentication architecture with auto-authentication after handshake; no obvious CVEs found in the handshake path.
- OTA password auth (SHA256 challenge-response) is well-designed; no bypass found.
- Dashboard WebSocket `open()` authentication gap is a real issue: `EsphomeCommandWebSocket.open()` has *no* auth check, only `on_message()` has `@authenticated` decorator.
- Path traversal in `DownloadBinaryRequestHandler.get()` will be classified as CWE-22 only if confirmed exploitable outside the build directory; the `replace("..", "")` bypass is trivial but the `Path.joinpath()` restricts traversal below the build directory.
- YAML `!include` tag path traversal: `_rel_path()` doesn't resolve or validate `..`, and `packages/` filename validation only checks extension. This is exploitable when an attacker can provide/control a YAML file in the config chain (e.g., via external_components or packages from an untrusted source).
- MQTT subscribe topic validation rejects `+`/`#` via `validate_topic_hashtag_allowlist` but list of wildcard patterns may be incomplete.
- Dashboard CSRF/XSRF protection is enabled only when password is set (`xsrf_cookies: settings.using_password`); when no password is configured, there is no CSRF protection.
- When `settings.on_ha_addon` is set, the `X-HA-Ingress` header bypasses all authentication.
