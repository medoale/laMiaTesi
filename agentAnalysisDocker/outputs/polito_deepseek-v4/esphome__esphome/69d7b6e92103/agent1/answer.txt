## Analysis

This commit is from ESPHome's protobuf message parsing code (`ProtoDecodableMessage`). The diff introduces four changes across two functions (`count_repeated_field` and `decode`), all of which fix the same class of vulnerability.

### The vulnerability

The original bounds checks used pointer arithmetic of the form:

```cpp
if (ptr + field_length > end)   // length-delimited field
if (ptr + 4 > end)              // fixed32 field
```

The problem is **integer overflow in pointer arithmetic**. Since `field_length` is `uint32_t`, the expression `ptr + field_length` can overflow/wrap around when `field_length` is a very large value (e.g., `0xFFFFFFFF`). On a 32-bit platform, this wraps the pointer around, making `ptr + field_length` appear smaller than `end`, and the bounds check passes incorrectly. An attacker who controls the protobuf binary input can craft a message with an enormous length field to bypass the bounds check entirely.

### The fix

Each check is rewritten to avoid overflow:

- `ptr + field_length > end` → `field_length > static_cast<size_t>(end - ptr)`
- `ptr + 4 > end` → `end - ptr < 4`

Now the remaining capacity (`end - ptr`) is computed first (as a `ptrdiff_t`, with no risk of overflow on either side of the subtraction), and the attacker-controlled length is compared directly against it. The `static_cast<size_t>` further ensures the comparison is well-defined.

### Consequence

Bypassing the bounds check leads to **out-of-bounds reads** — the code would read past the end of the buffer (`ptr += field_length` ends up well past `end`, and subsequent iterations read invalid memory). This can leak sensitive data or crash the device (denial of service). It is trivially triggerable by any client that sends a malformed protobuf message to the ESPHome API endpoint.

### Classification

The root cause is **Integer Overflow or Wraparound** in the pointer arithmetic used for bounds checking.
