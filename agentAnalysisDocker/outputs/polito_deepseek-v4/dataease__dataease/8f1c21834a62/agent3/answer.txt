After thoroughly exploring the repository, I have confirmed multiple security vulnerabilities in this DataEase BI tool (version 2.10.19). Below is a summary of the key findings:

---

### Vulnerability 1: SQL Injection via Multiple Vectors

**File:** `DatasetDataManage.java` (lines 434–519)  
The `previewSql` API accepts user-provided SQL as a base64-encoded string, decodes it, and executes it directly against the target datasource with no validation that the statement is a read-only query. The user controls the full SQL syntax.

**File:** `CalciteProvider.java` (lines 1193–1346)  
Table and schema names from `datasourceRequest.getTable()` are directly interpolated into SQL via `String.format()` for MySQL, Oracle, DB2, SQL Server, PostgreSQL, Redshift, ClickHouse, H2, and Impala. No parameterization or sanitization is applied.

**File:** `ExtWhere2Str.java`, `WhereTree2Str.java`, `CustomWhere2Str.java`  
Filter values from user requests (e.g. `ChartExtFilterDTO.getValue()`) are concatenated directly into SQL WHERE clauses without parameterized queries or escaping.

---

### Vulnerability 2: Unrestricted Upload of Dangerous File Type (JAR leading to RCE)

**File:** `DatasourceDriverServer.java` (lines 123–156) — endpoint `POST /datasourceDriver/uploadJar`  
Authenticated users can upload arbitrary `.jar` files. The only validation is a `.jar` extension check on the filename; no content verification or signature validation is performed.

**File:** `CalciteProvider.java` (lines 1535–1565) — `addCustomJdbcClassLoader`  
Uploaded JAR files are loaded into a custom classloader (`ExtendedJdbcClassLoader`) that can instantiate driver classes via `loadClass(driverClassName).newInstance()` at line 453. A malicious JAR's static initializer or driver class achieves arbitrary code execution in the JVM.

---

### Vulnerability 3: Use of Hard-coded Cryptographic Key (JWT Secret)

**File:** `LinkTokenUtil.java` (line 12)  
```java
public static final String defaultPwd = "link-pwd-fit2cloud";
```
This string is used as the HMAC256 secret for signing JWT tokens for shared resource links when no password is explicitly configured (also used as fallback in `DeLinkAop.java` line 67). Anyone who knows this default secret can forge valid JWT tokens, gaining unauthorized access to any shared dashboard, dataset, or panel.

---

### Vulnerability 4: Path Traversal in Static Resource Upload

**File:** `StaticResourceServer.java` (lines 44–65) — endpoint `POST /staticResource/upload/{fileId}`  
The `fileId` path variable is used directly in `basePath.resolve(fileId + extension)` with no sanitization for `../` sequences. An attacker can write files outside the intended `staticDir`.

**File:** `StaticResourceServer.java` (lines 127–142) — `saveSingleFileToServe`  
The `fileName` parameter passed to `basePath.resolve(fileName)` is not validated for path traversal sequences.
