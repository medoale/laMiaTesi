### **1. CWE-89: SQL Injection** (Primary — Most Severe)

**Location**: `DatasetDataManage.previewSql()` (lines 434–520) and `previewSqlWithLog()` (lines 401–425)

**Endpoint**: `POST /datasetData/previewSql` and `POST /datasetData/previewSqlCheck`

**Attack Vector**:
- The `PreviewSqlDTO` accepts a `sql` field (Base64-encoded) and a `datasourceId` (Long).
- At line 459, the SQL is Base64-decoded: `String s = new String(Base64.getDecoder().decode(dto.getSql()));`
- At line 460, it passes through `SqlparserUtils.handleVariableDefaultValue()` which performs string-based `${variable}` substitution using user-supplied `sqlVariableDetails`.
- At line 461, SQL comments are removed.
- The SQL is then wrapped as a subquery (`SELECT * FROM (userSql) LIMIT 100`) and executed against the target database.
- **No validation, no parameterization, no allowlist** of acceptable SQL constructs.
- At `CalciteProvider.jdbcFetchResultField()` line 527, the raw SQL string is executed verbatim: `resultSet = statement.executeQuery(datasourceRequest.getQuery());`
- The `datasourceId` in the request selects which database to target. The lookup via `dataSourceManage.getCoreDatasource(dto.getDatasourceId())` does not verify the caller has query-execute permission on that datasource.

**Impact**: An authenticated attacker can execute arbitrary SQL (SELECT, INSERT, UPDATE, DELETE, DROP, etc.) on any database that DataEase has a configured connection to. This yields full data exfiltration, data destruction, and potential lateral movement into the database network.

---

### **2. CWE-918: Server-Side Request Forgery (SSRF)**

**Location**: `ExcelUtils.downLoadRemoteExcel()` (lines 424–443), `ExcelUtils.downLoadFromFtp()` (lines 740–808), `HttpClientUtil.downloadFile()` (lines 372–413)

**Endpoint**: `POST /datasource/loadRemoteFile`

**Attack Vector**:
- `RemoteExcelRequest` contains a `url` field (no `@DePermit` annotation on this endpoint – see `DatasourceApi` line 176–178).
- At line 426, `downLoadRemoteExcel()` only checks if the URL starts with `"http"` or `"ftp"`.
- **No host allowlist, no IP blacklist, no DNS rebinding protection**.
- For HTTP(S) URLs, `HttpClientUtil.downloadFile()` makes a GET request and saves the response to disk.
- For FTP URLs, `downLoadFromFtp()` parses the URL, opens a raw `URLConnection`, and downloads the file.
- SSL verification is globally disabled: `HttpClientUtil.buildHttpClient(true)` at line 77 trusts all certificates: `builder.loadTrustMaterial(null, (X509Certificate[] x509Certificates, String s) -> true)`.
- The downloaded file is saved to disk at `path + UUID + suffix` and then read/parsed.

**Impact**: An attacker can make the DataEase server fetch arbitrary files from internal RFC1918 networks, cloud metadata endpoints (169.254.169.254), or internal services. The response content is saved, parsed, and returned to the attacker in structured form as Excel sheet data, making data exfiltration trivial.

---

### **3. CWE-89: SQL Injection** (Secondary — via Variable Substitution)

**Location**: `SqlparserUtils.transFilter()` (lines 691–722)

**Attack Vector**:
- `SqlVariableDetails` contains `operator`, `deType` (data type), and `value` (list of strings).
- For the `in` operator with numeric types (deType 2 or 3), line 698: `return String.join(",", sqlVariableDetails.getValue());` — values are joined raw with commas, **no quoting, no escaping**.
- For `between` operator with non-date types, line 712–716: raw values returned directly.
- For default (other) operators, line 719: raw value returned directly.
- These values get inserted into the SQL via string replacement (`sql.replace(matcher.group(), transFilter(...))` at line 94/98/101).
- An attacker can craft a variable value containing SQL metacharacters (e.g., `1 UNION SELECT ...`) to break out of the intended expression.

**Impact**: Even in contexts where the SQL template is fixed but variable values are user-controlled, numeric-type variables can be used to inject SQL.

---

### 4. (Lower Risk) Missing Authentication on `previewSql` and `loadRemoteFile`

- `previewSql` is exposed via `DatasetDataApi` with **no `@DePermit` annotation** — meaning any authenticated user can call it against any datasource.
- `loadRemoteFile` similarly has no `@DePermit` annotation.
- While the datasource lookup requires knowing a datasource ID, these IDs are sequential Long values that are enumerable.
