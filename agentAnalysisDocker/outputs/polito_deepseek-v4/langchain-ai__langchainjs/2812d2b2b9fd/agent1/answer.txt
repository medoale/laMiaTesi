## Analysis

### Overview

This commit modifies the `@langchain/community` package's `RecursiveUrlLoader`, specifically the `fetchWithTimeout` method in `recursive_url.ts`. The commit description in `file_01` explicitly states: **"Validate redirects in RecursiveUrlLoader to prevent SSRF bypasses."**

### The Vulnerability (Before the Fix)

In the **before** code (`file_03/before.txt`), the `fetchWithTimeout` method:

```typescript
private async fetchWithTimeout(resource: string, options): Promise<Response> {
    const { timeout, ...rest } = options;
    return this.caller.call(() =>
      fetch(resource, { ...rest, signal: AbortSignal.timeout(timeout) })
    );
}
```

- Used `fetch()` **without** `redirect: "manual"`, meaning `fetch` automatically followed HTTP redirects by default.
- The `validateSafeUrl()` check was performed **only before** calling `fetchWithTimeout` (in `getUrlAsDoc` and `getChildUrlsRecursive`), but **never during redirect following**.

This created a critical **SSRF bypass**:
1. A URL like `https://attacker.com/` would pass the initial `validateSafeUrl()` check (it's a public, valid URL).
2. The attacker's server responds with a `302 Redirect` to `http://169.254.169.254/latest/meta-data/` (AWS metadata) or `http://127.0.0.1/admin`.
3. `fetch()` would automatically and silently follow the redirect to the internal/private IP — no validation was performed on the redirect target.

### The Fix (After)

The **after** code (`file_03/after.txt`) completely rewrites `fetchWithTimeout`:

1. **`redirect: "manual"`** — Prevents automatic redirect following.
2. **Manual redirect loop** — Reads the `Location` header, resolves the new URL relative to the current one, and calls **`validateSafeUrl(currentUrl)`** on each intermediate URL before fetching it.
3. **`MAX_REDIRECTS = 10`** — Prevents infinite redirect loops.
4. The redundant `validateSafeUrl()` calls at the call sites (`getUrlAsDoc`, `getChildUrlsRecursive`) were removed since validation is now internal to `fetchWithTimeout`.

The test file (`file_02`) confirms the fix with explicit test cases for blocking redirects to:
- `127.0.0.1` (localhost)
- `169.254.169.254` (cloud metadata)
- `192.168.1.1` (private network)
- Infinite redirect loops

### Classification

This is a classic **Server-Side Request Forgery (SSRF)** vulnerability. The loader, running server-side, could be tricked into making requests to internal/private network addresses via HTTP redirects, bypassing the initial URL validation. No other CWE fits more specifically.
