### Vulnerability Summary

The commit fixes a **Server-Side Request Forgery (SSRF)** vulnerability in the `RecursiveUrlLoader` class.

**How the vulnerability worked (before the fix):**

The `fetchWithTimeout` method used the default `redirect: "follow"` behavior of the Fetch API:

```typescript
// BEFORE: fetch follows redirects automatically
private async fetchWithTimeout(resource, options) {
    return this.caller.call(() =>
        fetch(resource, { ...rest, signal: AbortSignal.timeout(timeout) })
        // ^^^ redirect: "follow" (default) — no validation of redirect targets
    );
}
```

The `validateSafeUrl()` function (from `@langchain/core/utils/ssrf`) was called on the *initial* URL in both `getUrlAsDoc()` and `getChildUrlsRecursive()`, but once `fetch()` followed an HTTP redirect (301, 302, 303, 307, or 308), the **redirect target was never validated**. An attacker controlling a target website could:

- Serve a redirect to `http://127.0.0.1/admin` — access local services on the server
- Serve a redirect to `http://169.254.169.254/latest/meta-data/` — exfiltrate cloud metadata (AWS/GCP metadata endpoint)
- Serve a redirect to `http://192.168.1.1/internal` — probe internal network resources

Additionally, there was no limit on redirect chains, enabling infinite redirect loops.

**How the fix works (after):**

1. Uses `redirect: "manual"` to prevent automatic redirect following
2. Manually walks redirect chains (up to 10 redirects)
3. Calls `validateSafeUrl()` on **every** URL, including each resolved redirect target, before fetching it
4. Removes the now-redundant `validateSafeUrl()` calls from `getUrlAsDoc()` and `getChildUrlsRecursive()` (since validation is now done inside `fetchWithTimeout` for all URLs)
