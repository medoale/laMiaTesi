## Analysis

### File 01: `DefaultHtmlErrorResponseBodyProvider.java`

**Before:** The cache was an unbounded `ConcurrentHashMap`:
```java
private final Map<HtmlErrorPage, String> cache = new ConcurrentHashMap<>();
```

**After:** Replaced with a bounded `ConcurrentLinkedHashMap` capped at 100 entries:
```java
private static final int MAX_CACHE_SIZE = 100;
private final Map<HtmlErrorPage, String> cache = new ConcurrentLinkedHashMap.Builder<HtmlErrorPage, String>()
    .maximumWeightedCapacity(MAX_CACHE_SIZE)
    .build();
```

A getter `getCache()` was also added for testing.

### File 02: `DefaultHtmlErrorResponseBodyProviderCacheMaxSizeTest.java`

A new test file that validates the cache stays bounded at 100 entries even when 110 distinct error-generating requests are made.

### Security Impact

The core issue is **Uncontrolled Resource Consumption**. The original code used an unbounded `ConcurrentHashMap` as a cache for error HTML pages. The `HtmlErrorPage` record keys include `locale`, `httpStatusCode`, `httpStatusReason`, `error`, `errorBold`, and `messages` — all of which vary per request. An attacker could craft thousands of distinct requests (e.g., varying query parameters, headers, paths) that produce different `HtmlErrorPage` keys, causing the cache to grow without bound and exhaust server heap memory — a **denial-of-service** condition.

The fix caps the cache at 100 entries, preventing unbounded memory growth. This directly mitigates the resource-exhaustion vector.

This is a security vulnerability fix: **CWE-400 (Uncontrolled Resource Consumption)**.
