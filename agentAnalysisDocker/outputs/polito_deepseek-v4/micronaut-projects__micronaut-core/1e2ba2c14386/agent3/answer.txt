After extensive analysis of the Micronaut framework repository, I found one confirmed vulnerability with a clear exploit path.

## Confirmed Vulnerability: CWE-918 — Server-Side Request Forgery (SSRF)

**Location:** HTTP client modules (`http-client`, `http-client-core`, `http-client-jdk`)

**Root Cause:** The HTTP client's URI resolution methods accept fully-qualified (absolute) URIs with **zero validation** of the target host, scheme, or port. There is no protection against connecting to private/internal IP addresses in any of the three HTTP client modules (Netty, JDK, or core).

**Vulnerable Code Paths:**

1. **`DefaultHttpClient.resolveRequestURI()`** (lines 1252–1260, `/work/http-client/src/main/java/io/micronaut/http/client/netty/DefaultHttpClient.java`): When a request URI has a scheme, it is returned directly for connection — no host/port validation.

2. **`DefaultHttpClient.resolveRedirectURI()`** (lines 1268–1286, same file): When a redirect `Location` header contains an absolute URL, it is used directly — no validation of the target.

3. **`DefaultHttpClient.proxy()`** (lines 1198–1229, same file): `ProxyHttpClient.proxy()` resolves the full URI from the incoming request and sends the request directly — no restriction on the target host.

4. **`AbstractJdkHttpClient.resolveRequestUri()`** (lines 351–359, `/work/http-client-jdk/src/main/java/io/micronaut/http/client/jdk/AbstractJdkHttpClient.java`): Same pattern in the JDK client.

5. **`ConnectionManager.doConnect()`** (lines 456–469, `/work/http-client/src/main/java/io/micronaut/http/client/netty/ConnectionManager.java`): Calls `Bootstrap.remoteAddress(host, port)` with the unvalidated host/port data from the `RequestKey`.

**No SSRF Protection:** Confirmed — grep for `PrivateNetwork`, `private.*network`, `SSRF`, `blockLoopback`, `blockPrivate` returns zero results across all three client modules.

**Exploit Scenarios:**
- A controller using `ProxyHttpClient` to proxy incoming requests forwards to any internal service
- A `@Client` annotation with user-controlled URI template parameters produces an internal-target URL
- Redirect following (enabled by default) follows a `Location: http://169.254.169.254/latest/meta-data/` to an internal cloud metadata service
- Server-side redirect via a malicious upstream endpoint targets internal hosts
